<decisions>
## Implementation Decisions

### Audit script semantics + wiring (Requirement 1)
- **D-01:** **Uniqueness scope = cross-slug only.** The audit flags a `youtube_id` only when 2+ different `slug` values use it. Same `youtube_id` on `full` and `tv` of the SAME slug is allowed (some artists post just the OP/ED — single video covers both versions). Matches the original Failure #1 scenario (5 different slugs sharing `gX9WX_NP5Ug`).
- **D-02:** **CSV format with header + pipe-separated multi-value cells.** Columns: `youtube_id, count, slugs, version_types`. Slugs and version_types are pipe-separated within their cell (since CSV uses comma). One row per duplicate group. Matches the existing audit-script convention used by `audit-catalog.ts`, `audit-corrupted-lyrics.ts`, `audit-lesson-coverage.ts`. Output path: `data/yt-id-audit.csv` (gitignored).
- **D-03:** **Wired as the final step in both batch shells.** Last line of `run-pending-batch.sh` and `overnight-orchestrator.sh`: `npx tsx scripts/seed/audit-yt-ids.ts || exit 1`. Exit-code propagation halts the batch on any duplicate. No retry, no auto-cleanup. Manual invocation (any time) supported by the same command.

### Transaction driver + failure handling (Requirement 2)
- **D-04:** **Try Drizzle's `db.transaction()` on the Neon HTTP serverless driver first.** If the smoke test (D-06) reveals HTTP doesn't support the multi-statement pattern needed for `songs` + `song_versions` upserts, fall back to the unpooled WebSocket pool (already used in repo via `neonConfig.fetchFunction` per commit `d5f5a96`). Lower upfront cost; verifies the assumption before committing to a driver swap.
- **D-05:** **Failure logging to stderr + end-of-batch summary.** Per failure: `[insert-fail] slug=<slug> error=<msg>` to stderr immediately. End of run: `N songs failed: foo, bar, baz` summary line. No JSON failure artifact (over-engineered for current scale; no auto-retry tooling exists). Batch continues for other songs after a single failure; only halts if every song failed (matches SPEC AC #9).
- **D-06:** **Vitest integration test against a test DB fixture.** Reuses the test-DB pattern from Phase 08.1 (`08.1-03-PLAN.md` integration layer). Test simulates a forced FK violation mid-transaction; asserts zero rows in both `songs` and `song_versions` for the failing slug, and matching rows for the passing slug. Repeatable, runs in CI-able time. Test file: `scripts/seed/__tests__/05-insert-db.test.ts` (or repo's existing test path convention).

### README format + scenarios (Requirement 3)
- **D-07:** **Scenario table + 'before you start' checklist + links into SOP.** Structure: (1) one-paragraph intro, (2) 'before you start' checklist (Python venv path, Node version, free RAM for WhisperX, env vars), (3) 5-row scenario table with intent + command(s), (4) links into SOP gate sections. Target ~70 lines (well under 100-line budget). Loads cheaply at session start.
- **D-08:** **5 scenarios as locked in SPEC.md:** "Add 1 new song" / "Add a batch of N songs" / "Resume pending_whisper backlog" / "Add only the TV cut for an existing song" / "Replace a geo-blocked or live-version YouTube ID". Reflects the operational reality of the last 2 months.
- **D-09:** **Pure pointers — no SOP content duplication.** Each command line links into the relevant SOP gate section (e.g. `See [Gate 5](SONG_INGESTION_SOP.md#gate-5--whisperx-timing-extraction-full--tv)`). One source of truth; README stays minimal; no drift risk if SOP gate purposes change.

### Claude's Discretion

- Vitest test scaffolding style (mock vs stub vs real test DB) — match Phase 08.1's existing conventions
- README markdown polish (table column widths, link anchor style)
- Error message wording for stderr output beyond the format `[insert-fail] slug=<slug> error=<msg>`

<specifics>
## Specific Ideas

- "Catalog velocity matters more than orchestration polish." User explicitly chose Gap 3 = README-only over a full `add-songs.ts` orchestrator (which was in the original CONTEXT.md plan as 7 sub-plans). Reasoning per product-philosophy memory: catalog velocity is bottlenecked by Claude-session time for inline lesson generation, not by tooling friction.
- "A streak-killer is the worst outcome." Both Requirements 1 and 2 are framed against streak-killer prevention (broken karaoke from wrong-video, broken `/songs/<slug>` page from half-written DB row). This shapes the test priority — D-06's Vitest rollback test is the highest-ROI test in the phase.
- "Pure pointers in the README." User wants one source of truth (the SOP) and a thin entrypoint into it. Bias: when in doubt during implementation, link instead of explain.
</specifics>

<deferred>
## Deferred Ideas

- **First-60-seconds preflight (Phase 14 candidate).** Songs with 60-second instrumental intros bore beginners and feel broken. A future "Gate 5b" would check if the song's intro has lyrics within the first 30 seconds and either reject or flag for premium-content tagging. Tracked from SPEC.md `<open_questions>`. Belongs in Phase 14 (UX Polish) since it's a user-perception-of-quality call, not a pipeline data-integrity issue.
- **`add-songs.ts` unified orchestrator (Gap 3 option B).** Was the centerpiece of the original CONTEXT.md (7 sub-plans). Deferred because catalog velocity isn't currently bottlenecked by orchestration tooling — Claude-session time for inline lesson generation is the real bottleneck. Revisit if velocity metrics show otherwise.
- **JSON `data/insert-failures.json` failure log + auto-retry tooling.** Considered and rejected for current scale (no auto-retry harness exists). Worth revisiting once batch sizes exceed ~25 songs/run or if failure rate exceeds ~5%.
- **Pre-commit git hook for the audit.** Considered and rejected — adds friction to every commit, requires per-machine setup. Post-batch enforcement is sufficient for current operator pattern.
- **GitHub Actions CI for the audit.** Considered and rejected — Phase 11.1 doesn't have other CI jobs; greenfield CI infra is over-scope for this phase. Revisit when broader CI work lands (likely Phase 16 Security Review or Phase 20 Code Quality).
- **Pruning the 50 manifest entries with no cached lesson.** Cleanup task surfaced during the 2026-04-26 audit. Mostly instrumentals/OST/cryptic-junk; not blocking any phase. Schedule as a 30-min cleanup whenever convenient.
- **Wrapping `vocabulary_items` writes in the same transaction as songs+song_versions.** Considered for Requirement 2 scope; rejected because vocab-backfill lives in a separate flow (Phase 7) and coupling would over-scope the change. Revisit if vocab-backfill consistency issues surface.
</deferred>
