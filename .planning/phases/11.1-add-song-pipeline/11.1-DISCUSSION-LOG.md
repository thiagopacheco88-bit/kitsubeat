## Audit script semantics + wiring

### Q1: Uniqueness scope — when does the audit flag a duplicate youtube_id?

| Option | Description | Selected |
|--------|-------------|----------|
| Cross-slug only | Flag only when same youtube_id is used by 2+ different slugs. Same youtube_id on full + tv of SAME slug allowed. Most permissive; matches original Failure #1 motivation. | ✓ |
| Cross-slug AND cross-version-same-slug | Flag any youtube_id with count > 1 including same-slug both-version pointing at same video. Stricter but creates noise for legitimate single-upload cases. | |
| Cross-slug + flag (don't error) on same-slug | Two-tier output: hard duplicates exit non-zero; soft duplicates flagged in CSV without failing. | |

**User's choice:** Cross-slug only.
**Notes:** Recognizes legitimate case where one YouTube video covers both full + TV of an artist's upload.

### Q2: CSV output format

| Option | Description | Selected |
|--------|-------------|----------|
| Header + youtube_id, count, slugs (pipe-sep), version_types (pipe-sep) | One row per duplicate group. Pipe-sep multi-values inside cells. Easy to grep/eyeball. | ✓ |
| One row per occurrence (denormalized) | Each duplicated row gets own line. More rows but no in-cell delimiters. | |
| JSON instead of CSV | Structured but breaks consistency with audit-catalog.ts / audit-corrupted-lyrics.ts / audit-lesson-coverage.ts (all CSV). | |

**User's choice:** Header + pipe-separated CSV.
**Notes:** Matches existing audit-script convention.

### Q3: Wiring location in batch shells

| Option | Description | Selected |
|--------|-------------|----------|
| Final step, propagate exit code | Last line: `npx tsx scripts/seed/audit-yt-ids.ts \|\| exit 1`. Batch fails loudly on dupes. | ✓ |
| After insert, before cleanup steps | Run after 05-insert-db.ts before other audits. Catches dupes earliest. | |
| Both per-song and end-of-batch | Audit after each song's DB insert AND at end. More thorough; adds N+1 audit runs. | |

**User's choice:** Final step, propagate exit code.

## Transaction driver + failure handling

### Q4: Neon driver strategy for db.transaction()

| Option | Description | Selected |
|--------|-------------|----------|
| Try HTTP serverless first, switch if it fails | Implement with current HTTP driver + db.transaction(); smoke test rollback; fall back to WebSocket if HTTP doesn't support multi-statement tx. | ✓ |
| Switch to WebSocket pre-emptively | Don't trust HTTP for transactions; switch 05-insert-db.ts to unpooled WebSocket pool now. | |
| Keep HTTP, use raw SQL BEGIN/COMMIT/ROLLBACK | Skip Drizzle's db.transaction() abstraction; raw SQL via sql.unsafe(). Loses typed query builder. | |

**User's choice:** Try HTTP serverless first, switch if it fails.

### Q5: Failure persistence

| Option | Description | Selected |
|--------|-------------|----------|
| stderr line + summary at end of batch | Per-failure: `[insert-fail] slug=foo error=<msg>` to stderr. End: `N songs failed: foo, bar, baz`. No file artifact. | ✓ |
| stderr + data/insert-failures.json | Also write JSON array of {slug, error, timestamp}. Enables retry tooling later but adds gitignore + cleanup. | |
| stderr + halt batch on first failure | Stop on first failure. Simplest but bad fit for overnight runs (contradicts SPEC AC #9). | |

**User's choice:** stderr line + summary at end of batch.

### Q6: How to verify rollback works

| Option | Description | Selected |
|--------|-------------|----------|
| Vitest integration test against test DB | Reuse Phase 08.1 test-DB pattern. Inject FK violation; assert zero rows for failing slug, passing slug intact. | ✓ |
| One-off manual smoke (no committed test) | Manually mock failure once, eyeball, document in PR. No regression guard. | |
| Both — unit test for tx wrapper + manual smoke | Unit test on wrapping logic plus manual end-to-end. More setup. | |

**User's choice:** Vitest integration test against test DB.
