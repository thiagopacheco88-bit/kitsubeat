**DB query shape** (adapt from `audit-catalog.ts:60-69`):
```typescript
const db = getDb();
const rows = await db
  .select({
    youtube_id: songVersions.youtube_id,
    slug: songs.slug,
    version_type: songVersions.version_type,
  })
  .from(songVersions)
  .innerJoin(songs, eq(songs.id, songVersions.song_id))
  .where(isNotNull(songVersions.youtube_id));
```
Read-only — never `INSERT`/`UPDATE`/`DELETE`. Matches the locked constraint "audit script must be read-only against the database" (SPEC § Constraints).

**Group-by-and-flag pattern** (cross-slug only — D-01):
```typescript
// Group by youtube_id; only flag groups whose distinct slugs > 1
const byYtId = new Map<string, { slugs: Set<string>; versionTypes: string[] }>();
for (const r of rows) {
  if (!r.youtube_id) continue;
  const g = byYtId.get(r.youtube_id) ?? { slugs: new Set(), versionTypes: [] };
  g.slugs.add(r.slug);
  g.versionTypes.push(`${r.slug}:${r.version_type}`);
  byYtId.set(r.youtube_id, g);
}
const dupes = [...byYtId.entries()]
  .filter(([, g]) => g.slugs.size > 1) // CROSS-SLUG ONLY (D-01)
  .map(([youtube_id, g]) => ({
    youtube_id,
    count: g.slugs.size,
    slugs: [...g.slugs].sort(),
    version_types: g.versionTypes.sort(),
  }));
```

**CSV write pattern with pipe-separated multi-values** (D-02):
Adapt the `csvLines.push([...].join(","))` shape from `audit-catalog.ts:153-170`. The novel bit (pipe-separator inside cells) has no in-repo precedent — implement directly:
```typescript
const csvLines: string[] = ["youtube_id,count,slugs,version_types"];
for (const d of dupes) {
  csvLines.push(
    [
      d.youtube_id,
      String(d.count),
      d.slugs.join("|"),         // pipe-separated within cell
      d.version_types.join("|"), // pipe-separated within cell
    ].join(","),
  );
}
writeFileSync(resolve(process.cwd(), "data/yt-id-audit.csv"), csvLines.join("\n"), "utf-8");
```

**Exit-code + summary pattern** (matches SPEC AC #2 + #3, D-03):

try {
  const db = getDb();

  const [songRow] = await db
    .insert(songs)

  insertedCount++;

**Target shape** (wrap every `db.insert(...)` call inside the transaction callback; replace `db` with `tx` inside):
```typescript
const failedSlugs: string[] = [];
// ...
try {
  const db = getDb();
  await db.transaction(async (tx) => {
    const [songRow] = await tx.insert(songs).values({ /* ... */ })
      .onConflictDoUpdate({ /* ... */ }).returning({ id: songs.id });
    if (!songRow) throw new Error("songs upsert returned no row");
    await tx.insert(songVersions).values({ song_id: songRow.id, /* ... */ })
      .onConflictDoUpdate({ /* ... */ });
  });
  insertedCount++;
  process.stdout.write(`  [OK] ${song.slug} — upserted\n`);
} catch (err) {
  // Per-failure stderr log (D-05 format)
  console.error(`[insert-fail] slug=${song.slug} error=${(err as Error).message}`);
  failedSlugs.push(song.slug);
  errorCount++;
}
```

### Neon driver + transactions (cross-cutting; load-bearing for Requirement 2)

**Source of truth:** `src/lib/db/index.ts:18-82` — current single Neon HTTP serverless client with cold-start retry wrapper (commit `d5f5a96`).

**Existing repo evidence (4 places) that HTTP driver does NOT support `db.transaction()`:**
1. `src/app/actions/review.ts:14` — `// No db.transaction() — neon-http has no callback transactions (Pitfall 4).`
2. `src/lib/db/queries.ts:741` — `Two separate db.execute calls — neon-http has no callback transactions (Pitfall 4 in RESEARCH.md); sequential is correct and safe for reads.`
3. `.planning/phases/11-cross-song-vocabulary/11-RESEARCH.md:309-315`:
   > **Pitfall 4: neon-http has no callback transactions**
   > **What goes wrong:** You can't wrap review-session mutations in `db.transaction(async tx => { ... })` — the Neon HTTP driver doesn't support callback-form transactions
   > **Why it happens:** HTTP serverless driver is stateless; transaction mode requires `neon` WebSocket driver, which isn't installed.
4. `.planning/phases/11-cross-song-vocabulary/11-01-SUMMARY.md:53,148` — pattern restated.

**Implication for Phase 11.1 plan:** The "try HTTP first, fall back to WebSocket" sequence in D-04 is a sanity-check formality. Plan should budget **direct WebSocket migration** for `scripts/seed/05-insert-db.ts` only. Do NOT touch the app's `getDb()`/`db` proxy — they stay HTTP. Two viable approaches:

**Approach A (recommended): script-local Pool**
Inside `05-insert-db.ts`, build a local pooled client without touching `src/lib/db/index.ts`:
```typescript
import { Pool } from "@neondatabase/serverless";
import { drizzle as drizzlePool } from "drizzle-orm/neon-serverless";
// at start of main():
const pool = new Pool({ connectionString: process.env.DATABASE_URL });
const dbTx = drizzlePool(pool); // supports dbTx.transaction(async tx => ...)
// ...use dbTx in the per-song loop, then await pool.end() at the end.
```
The WebSocket pool import path (`drizzle-orm/neon-serverless` + `@neondatabase/serverless` `Pool`) is the established Drizzle/Neon pattern; not used elsewhere in this repo yet.

**Approach B: extend `src/lib/db/index.ts`**
Add a sibling `getDbPool(): NeonDatabase` factory that returns a WebSocket-backed Drizzle. Heavier blast radius — only do this if multiple scripts need transactions.

**Cold-start retry wrapper (commit d5f5a96):** Currently global via `neonConfig.fetchFunction` (lines 39-78). The WebSocket Pool path uses `Pool` from `@neondatabase/serverless`, which respects `neonConfig` settings — verify the retry wrapper applies (or replicate via `pool.on('connect', ...)` if not). Cold-start handling is desirable for the seed script too.

**Apply to:** `scripts/seed/05-insert-db.ts` ONLY. Scripts that don't need transactions (`audit-yt-ids.ts`) keep `getDb()` (HTTP).
