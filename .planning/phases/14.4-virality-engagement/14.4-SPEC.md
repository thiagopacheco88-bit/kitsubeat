# Phase 14.4: Virality & Engagement — Specification

**Created:** 2026-05-08
**Ambiguity score:** 0.16 (gate: ≤ 0.20)
**Requirements:** 8 locked

## Goal

Layer functional virality + retention on top of the Phase 14 visual foundation: anonymized "now playing" learner counts on home SongCards, anonymized song-mastery ticker on home, daily streak-at-risk reminder + Sunday weekly recap email via Resend, and a free 7-day-milestone streak-saver token — with a single opt-IN master toggle (default off) governing all five behaviors.

## Background

Phases 14.1 (`/path`), 14.2 (`/`), 14.3 (`/songs/[slug]`) shipped the Phase 14 visual language across the three top-priority surfaces. Existing infra in the codebase that 14.4 builds on:

- `users` table (Phase 12) carries `streakCurrent`, `streakBest`, `lastStreakDate`, `streakTz`, `graceUsedThisWeek`, `streakWeekStart`. Pure `advanceStreak()` state machine in `src/lib/gamification/streak.ts` enforces grace-day policy (one auto-applied per ISO week) and 7/30/100 milestones.
- `subscriptions` table + `isPremium()` (`src/app/actions/userPrefs.ts`) — gate ready for premium expansion (not used in 14.4 — streak-saver is free).
- `song_plays` table (Phase 9) — first-play events with nullable `user_id` + `session_key`. `getAllSongs` already aggregates `learner_count` site-wide; nothing reads "last 30 min" yet.
- `user_verse_domination` (Phase 11.6) and `user_song_progress` (Phase 8) drive `deriveStars()`. Mastery is read-time-derived, not event-emitted.
- `users.email` does NOT exist — Clerk owns email; pulled per-send on email features.

Gap from current state to phase goal:

- No "now playing" surface or query.
- No activity-events emission, no mastery feed, no home ticker.
- No transactional email dependency installed (no Resend, no Postmark).
- No web push (deferred — email-only chosen for v1).
- No cron infrastructure or `CRON_SECRET` plumbing.
- No master social/notification opt-in column or settings surface.
- No streak-saver token column or grant/consume hooks in `advanceStreak`.

## Requirements

1. **Now-playing learner count**: Home SongCards render "X listening now" when at least 3 distinct learners played any version in the last 30 min.
   - Current: `getAllSongs` aggregates `learner_count` site-wide; no time-windowed live signal exists; SongCard has no live chip
   - Target: Home `SongCard` (Phase 14.2 redesign) renders chip with text "{N} listening now" when `COUNT(DISTINCT COALESCE(user_id, session_key))` from `song_plays` joined to song's `song_versions` rows where `played_at >= now() - interval '30 min'` is `>= 3`; suppressed otherwise. Single batched aggregate added to home-page query path; server cached 60 s
   - Acceptance: Seeded test DB with 5 `song_plays` rows in last 30 min for one song renders chip "5 listening now"; same DB with only 2 rows renders no chip; rows older than 30 min excluded; chip absent on every other route

2. **Recently-mastered ticker (home)**: Home renders last 10 song-mastery events across opt-in users, anonymized.
   - Current: No `activity_events` table; mastery is read-time-derived from `user_song_progress` stars; home does not render any activity feed
   - Target: New `activity_events` table (`id`, `user_id`, `event_type='song_mastered'`, `song_id`, `song_version_id`, `created_at`) inserted on the `saveSessionResults` write boundary when `deriveStars()` first transitions to 3 for a `(user, song)` pair (idempotent — `ON CONFLICT (user_id, song_id) DO NOTHING`). Home ticker reads last 10 events ordered by `created_at DESC` where the emitting user has `social_activity_enabled = true`; renders "{first_name} mastered {song_title} · {relative_time}". `first_name` pulled from Clerk on read (cached). Auto-scroll horizontal ticker; `prefers-reduced-motion` halts the scroll
   - Acceptance: Seeding 12 mastery events shows the most recent 10; events from a user with opt-in OFF do NOT render in others' feeds; events older than 7 days excluded; reduced-motion-active client renders the ticker as a static list

3. **Master social activity toggle (opt-IN, default off)**: Single boolean on `users` controls visibility, feed inclusion, and email sends.
   - Current: No social/notification preference column; no settings surface for it
   - Target: Migration adds `users.social_activity_enabled boolean NOT NULL DEFAULT false`. Toggle ON enables: (a) the user's own mastery events become visible to others in REQ-2 ticker; (b) the user receives daily reminder + weekly recap; (c) the user's `song_plays` count toward "X listening now" for others. Toggle OFF reverses all three. Toggle does NOT affect the user seeing others' counts/ticker (read access independent of opt-in)
   - Acceptance: New user row defaults to `false`; flipping to `true` then mastering a song surfaces an event to other users' tickers; flipping back to `false` hides future events but historical events persist in DB

4. **Daily reminder email (streak-at-risk only)**: Email sent at user-local 19:00 only when streak is active and not yet logged today.
   - Current: No email channel installed; no per-user scheduled trigger
   - Target: New `/api/cron/daily-reminder` route runs hourly, secured by `CRON_SECRET` header. For each user where `social_activity_enabled = true` AND `streakCurrent > 0` AND `lastStreakDate < today_in_user_tz` AND current hour-in-user-tz `== 19`, send email "Your {streakCurrent}-day streak ends in 5 hours" via Resend. Email pulled from Clerk per-send. Per-day idempotency: writes `email_sent_log` row keyed `(user_id, kind='daily_reminder', date)`; second send same day no-ops
   - Acceptance: Cron returns 401 without `CRON_SECRET`; with secret + seeded user (streak=7, lastStreakDate=yesterday, opt-in=true, TZ=Asia/Tokyo) at the hour matching 19:00 Asia/Tokyo → 1 Resend call queued; same user with opt-in=false → 0 calls; same user with `lastStreakDate=today` → 0 calls; cron rerun within same day → 0 calls (idempotent)

5. **Weekly recap email**: Sunday 18:00 UTC, opt-in users receive a structured 4-section recap.
   - Current: No recap email exists
   - Target: New `/api/cron/weekly-recap` route triggered Sunday 18:00 UTC, secured by `CRON_SECRET`. For each user with `social_activity_enabled = true`, send email containing in this order: (a) vocab learned this week (count of `user_vocab_mastery` rows whose `stage` advanced in the last 7 days); (b) songs touched (distinct `song_id` with at least one `user_exercise_log` row in the last 7 days); (c) streak status (`streakCurrent` and `streakBest`); (d) one next-up nudge (next due `user_vocab_mastery` row OR suggested next song from `/path`). Per-week idempotency: `email_sent_log` keyed `(user_id, kind='weekly_recap', week_start)`
   - Acceptance: Two consecutive Sunday cron runs send 2 distinct emails to the same opt-in user; user with opt-in=false receives 0; each email body contains all 4 sections in fixed order with non-zero or "—" placeholder values; rerun same week produces no duplicate sends

6. **Streak-saver token**: Free, granted at first 7-day milestone, max 1 stockpiled, auto-applies silently.
   - Current: `users` has streak fields but no recovery token; `advanceStreak()` only auto-applies grace day, then resets on larger gaps
   - Target: Migration adds `users.streak_saver_token integer NOT NULL DEFAULT 0 CHECK (streak_saver_token IN (0,1))`. Grant rule: when `advanceStreak()` returns `milestoneHit === 7` AND `streak_saver_token === 0` → set to 1 (no double-grant on subsequent 7-day passes after consume; one earn per "fresh streak" run). Apply rule: when `advanceStreak()` would reset (gap > grace allowance) AND `streak_saver_token === 1` → consume (set to 0), preserve `streakCurrent`, advance `lastStreakDate` to today, return new flag `streakSaverApplied: true`. UX: on next session start where `streakSaverApplied` was set since last visit, show toast "Your {N}-day streak was saved by a streak-saver token" (auto-dismiss 5 s; reduced-motion fallback = static banner)
   - Acceptance: User crossing streak=7 first time → token = 1; user already at token=1 hitting streak=7 again → token still 1 (no >1); user with token=1 and a 3-day gap → streak preserved AND token=0 AND `streakSaverApplied=true`; user with token=0 and a 3-day gap → streak resets normally; toast renders once and does NOT re-render on second session that day

7. **Settings surface for opt-in**: Single toggle row + reduced-anxiety copy.
   - Current: Settings page (Phase 12 prefs) has skip_learning, sound, haptics, theme; no social/notification row
   - Target: New "Social & notifications" section in `/settings` (or equivalent prefs page) with one toggle "Show my activity to others and email me reminders". Round-trips to `users.social_activity_enabled` via existing `updateUserPrefs` server action pattern. Helper text explicitly enumerates the 4 affected behaviors: visible mastery events, daily streak reminder, weekly recap, "X listening now" inclusion. No streak-shaming copy anywhere
   - Acceptance: Toggle row visible in settings; click flips DB column; helper text contains the 4 enumerated bullets; copy reviewed for absence of "don't lose your streak" / "you'll fail" / loss-frame language

8. **Email + cron infrastructure**: `resend` dep, two cron routes, secret-gated, dev-safe.
   - Current: No `resend` in `package.json`; no `/api/cron/*` routes; no `CRON_SECRET` env var; no `email_sent_log` table
   - Target: Add `resend` npm dep, `RESEND_API_KEY` and `CRON_SECRET` env vars. Two routes: `/api/cron/daily-reminder` (hourly) and `/api/cron/weekly-recap` (Sunday 18:00 UTC). Both require `Authorization: Bearer ${CRON_SECRET}` header. Migration creates `email_sent_log (user_id text, kind text, period_key text, sent_at timestamptz, PRIMARY KEY (user_id, kind, period_key))`. Dev safety: when `RESEND_API_KEY` absent, route logs the would-be-sent payload and returns 200 without calling Resend
   - Acceptance: Routes return 401 without correct header; without `RESEND_API_KEY` they log + return 200 with `dry_run: true`; with key + seeded users they call Resend and write `email_sent_log` rows; second run within idempotency window writes no new rows and sends no new emails

## Boundaries

**In scope:**
- "Now playing" learner-count chip on home SongCards (last 30 min, ≥3 floor, no avatars)
- Recently-mastered ticker on home (last 10 song-mastered events, anonymized first-name from Clerk, reduced-motion fallback)
- `users.social_activity_enabled` master opt-in toggle (default off) + Settings surface
- Daily streak-at-risk reminder email (user-local 19:00, Resend)
- Weekly recap email (Sunday 18:00 UTC, Resend)
- Streak-saver token (free, 7-day milestone earn, max 1, auto-apply with next-session toast)
- `/api/cron/daily-reminder` + `/api/cron/weekly-recap` routes with `CRON_SECRET` gating
- `email_sent_log` table for per-period idempotency
- `activity_events` table for mastery feed source

**Out of scope:**
- Follow-a-friend graph and per-friend feed filtering — INTENT listed; deferred to a future phase to keep 14.4 shippable
- Per-song weekly leaderboard — REQUIREMENTS.md explicitly defers social leaderboards to v3.0; would require moderation infrastructure
- Web push notifications + service worker + VAPID + `push_subscriptions` table — Round 1 chose email-only
- Avatar stack / opt-in lesson-page co-listener display — Round 2 explicitly deferred (bleeds into follow territory)
- Per-feature granular toggles in settings — Round 2 chose single master toggle for simplicity + privacy clarity
- Verse-mastery or level-up events in the activity ticker — Round 2 chose song-mastered only to avoid feed noise
- SMS reminder channel — single channel only (email)
- Mirroring `user.email` into our `users` table — pulled from Clerk per-send to keep Clerk as source of truth
- Daily reminder for users at streak=0 — only fires for streak-at-risk
- Premium tier modifications (more saves, ad-free emails, etc.) — streak-saver is free, single tier
- Anonymous / guest-user inclusion in mastery ticker — only authenticated opted-in users emit events
- Push to Slack / Discord / etc. — out of channel scope

## Constraints

- All social and email features default OFF (opt-IN) — INTENT lock; cannot be relaxed without revisiting that constraint.
- Reduced-motion fallback required for the home ticker (auto-scroll halts) and the streak-saver toast (static banner).
- Reduced-anxiety copy throughout — never use "don't lose your streak", "you failed", or any loss-frame language.
- Email volume must stay within Resend free tier (50K emails / month) at the current ~5K user level; recap = max 1 per user per week, daily = max 1 per user per day.
- All cron routes must be secured with `Authorization: Bearer ${CRON_SECRET}`; routes must return 401 on missing/invalid header.
- Cron routes must be safe to invoke without `RESEND_API_KEY` set (dev / local) — log + return without external calls.
- Email pulled from Clerk on send; no `users.email` column added.
- Home page must not regress its TTFB or bundle budget vs the Phase 14.2 baseline; new "now playing" + ticker queries batched into existing home query plan or behind a single new endpoint.
- Streak-saver grant must be idempotent — repeated `streakCurrent === 7` evaluations across sessions must NOT push the token above 1.
- `email_sent_log` is the single source of truth for "did we send this already" — no in-memory dedup.
