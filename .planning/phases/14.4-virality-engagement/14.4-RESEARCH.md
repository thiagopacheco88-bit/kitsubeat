## Summary

Phase 14.4 layers email/cron infrastructure, activity-event tables, and streak-saver state onto an existing Next.js 15 App Router codebase. All six sub-features are infrastructure-heavy with minimal new visual surface — the visual tokens are frozen and all chip/ticker/toast colors reuse existing Phase 14 CSS variables.

**The dominant planning risk is Vercel plan tier.** Hobby accounts block cron expressions that run more frequently than once per day at deploy time. The daily-reminder cron uses `0 * * * *` (hourly) which will **fail Hobby deployment** — not a runtime failure, a deploy failure. This is a harder blocker than CONTEXT D-04 anticipated (D-04 flagged maxDuration as the Hobby concern; the actual blocker is cron frequency). Vercel Pro is required for the daily-reminder route.

Resend's actual rate limit is **5 req/sec** (not 10 as noted in CONTEXT D-02). `p-limit` concurrency=5 at ~150ms average RTT produces ~33 req/sec theoretical max — which exceeds 5 req/sec. Actual safe concurrency for the Resend free tier is **1** and for paid is **concurrency ≤ 5 with backoff on 429**. D-02 must revise the concurrency model.

`unstable_cache` works in Next.js 15 App Router with `revalidate: N` (seconds). The `use cache` directive replaces it in Next.js 16 but that is out of scope here. TTL semantics for `revalidate: 60` and `revalidate: 3600` are confirmed as stale-while-revalidate (background refresh after TTL, never blocks the request).

**Primary recommendation:** Confirm Vercel Pro before starting Wave 1. Without Pro, the daily-reminder route must use the chunked-dispatch fallback documented in D-04 or be removed from scope.

### Pattern 1: Resend SDK — emails.send() with dry-run branch
**What:** Centralized email sender with dev-safety gate and `{ data, error }` pattern.
**When to use:** All email send calls from both cron routes route through this single helper.

```typescript
// Source: https://resend.com/docs/send-with-nodejs [VERIFIED: official docs]
import { Resend } from 'resend';

const resend = new Resend(process.env.RESEND_API_KEY);

// src/lib/emails/send.ts
export async function sendEmail(payload: {
  to: string;
  subject: string;
  html: string;
  text: string;
  kind: string; // for dry-run logging
  userId: string; // for dry-run logging
}): Promise<{ sent: boolean; dry_run?: boolean; id?: string }> {
  if (!process.env.RESEND_API_KEY) {
    console.info('[email-dry-run]', { kind: payload.kind, userId: payload.userId, subject: payload.subject });
    return { sent: false, dry_run: true };
  }

  const { data, error } = await resend.emails.send({
    from: 'KitsuBeat <noreply@kitsubeat.app>',
    to: payload.to,
    subject: payload.subject,
    html: payload.html,
    text: payload.text,
  });

  if (error) {
    console.error('[email-send-error]', { kind: payload.kind, userId: payload.userId, error });
    return { sent: false };
  }

  return { sent: true, id: data?.id };
}
```

**CRITICAL PITFALL — Rate Limit Correction:** Resend rate limit is **5 req/sec per team** [VERIFIED: official docs resend.com/docs/api-reference/introduction]. CONTEXT D-02 states "Resend free tier: 10 req/sec" — this is incorrect. `p-limit(5)` at ~150ms RTT = ~33 req/sec theoretical throughput, which would trigger 429s. Safe pattern: `p-limit(1)` on free tier, or `p-limit(5)` with exponential backoff on 429. Recommend `p-limit(1)` as default, `EMAIL_SEND_CONCURRENCY` env var for production tuning with backoff logic.

```typescript
// src/lib/cron/auth.ts — Source: https://vercel.com/docs/cron-jobs/manage-cron-jobs [VERIFIED]
import type { NextRequest } from 'next/server';

export function assertCronSecret(request: NextRequest): Response | null {
  const authHeader = request.headers.get('authorization');
  const cronSecret = process.env.CRON_SECRET;

  if (!cronSecret || authHeader !== `Bearer ${cronSecret}`) {
    return new Response('Unauthorized', { status: 401 });
  }
  return null; // OK
}
```

**CRITICAL FINDING — Hobby Plan Blocker:** `0 * * * *` (hourly) fails **deployment** on Hobby. [VERIFIED: vercel.com/docs/cron-jobs/usage-and-pricing]
> "Hobby accounts are limited to cron jobs that run once per day. Expressions like `0 * * * *` (hourly) will fail deployment with the error: *Hobby accounts are limited to daily cron jobs.*"

This is a deploy-time error, not a runtime error. The daily-reminder route cannot exist in `vercel.json` on a Hobby account. **Vercel Pro is required for this phase.**

**ALSO VERIFIED — maxDuration on Hobby:** Default is 300s (5 min). Maximum is also 300s on Hobby. Pro maximum is 800s. [VERIFIED: vercel.com/docs/functions/configuring-functions/duration]
CONTEXT D-04 states "Hobby default: 60s" — this is incorrect. Hobby default is **300s**. The `export const maxDuration = 300` on weekly-recap does NOT require Pro for the duration alone; but Pro IS required for the hourly cron frequency. Correct the CONTEXT assumption in the plan.

### Pattern 3: `unstable_cache` — TTL-based server caching
**What:** Wraps an async function, caches result keyed by function + keyParts array, revalidates after `revalidate` seconds.
**When to use:** Clerk first-name reads (1h TTL) and now-playing counts (60s TTL).

```typescript
// Source: https://nextjs.org/docs/app/api-reference/functions/unstable_cache [VERIFIED: official docs]
import { unstable_cache } from 'next/cache';
import { clerkClient } from '@clerk/nextjs/server';

// Ticker first-name — cache per user, refresh every 1 hour
export const getTickerFirstName = (userId: string) =>
  unstable_cache(
    async () => {
      const user = await clerkClient().users.getUser(userId);
      return user.firstName ?? 'Someone';  // firstName is null | string [VERIFIED: Clerk docs]
    },
    ['ticker-firstname', userId],  // keyParts must include userId for per-user isolation
    { revalidate: 3600 }
  )();

// Now-playing counts — cache for 60s, keyed by minute bucket
export const getNowPlayingCounts = unstable_cache(
  async () => {
    // SQL aggregate returning Map<song_id, count>
    const rows = await db.execute(sql`
      SELECT sv.song_id, COUNT(DISTINCT COALESCE(sp.user_id, sp.session_key)) AS listener_count
      FROM song_plays sp
      JOIN song_versions sv ON sv.id = sp.song_version_id
      LEFT JOIN users u ON u.id = sp.user_id
      WHERE sp.played_at >= now() - interval '30 minutes'
        AND (sp.user_id IS NULL OR u.social_activity_enabled = true)
      GROUP BY sv.song_id
      HAVING COUNT(DISTINCT COALESCE(sp.user_id, sp.session_key)) >= 3
    `);
    return new Map(rows.rows.map(r => [r.song_id as string, Number(r.listener_count)]));
  },
  ['now-playing-counts'],
  { revalidate: 60 }
);
```

**Gotcha:** `unstable_cache` is replaced by `use cache` directive in Next.js 16. The project is on Next.js `^15.5.14`. `unstable_cache` is the correct API. [VERIFIED: nextjs.org/docs/app/api-reference/functions/unstable_cache]

**Gotcha:** `keyParts` array must include all variables that affect cache identity that are not function arguments. For per-user Clerk first-name, use `['ticker-firstname', userId]` — not a closure over `userId` without including it in `keyParts`.

### Pattern 6: Streak-saver consume detection in `applyGamificationUpdate`
**What:** Detect "reset that grace did not cover" after `advanceStreak` returns.
**When to use:** Inside `applyGamificationUpdate` Step 5.5 (between Steps 5 and 6).

```typescript
// Source: src/lib/gamification/session-integration.ts + streak.ts [VERIFIED: codebase]
// advanceStreak Rule 6: gap >= 3 OR gap=2 with grace exhausted → streakCurrent = 1, streakAdvanced = true
// Detection: previousStreakCurrent > 1 && newState.streakCurrent === 1 && !graceApplied

const previousStreakCurrent = userRow.streakCurrent ?? 0;
const streakResult = advanceStreak(streakState, { tz, now });

let nextStreakSaverToken = userRow.streak_saver_token ?? 0;
let nextStreakSaverPending = userRow.streak_saver_pending ?? false;
let nextStreakCurrent = streakResult.newState.streakCurrent;
let nextLastStreakDate = streakResult.newState.lastStreakDate;

// Grant rule (D-12)
if (streakResult.milestoneHit === 7 && nextStreakSaverToken === 0) {
  nextStreakSaverToken = 1;
}

// Consume rule (D-12) — fires AFTER grant (if milestone=7 AND token was 1, consume wins)
const wasReset =
  !streakResult.graceApplied &&
  previousStreakCurrent > 1 &&
  streakResult.newState.streakCurrent === 1;

if (wasReset && nextStreakSaverToken === 1) {
  nextStreakCurrent = previousStreakCurrent + 1; // preserve + advance for today
  nextLastStreakDate = todayInTz;
  nextStreakSaverToken = 0;
  nextStreakSaverPending = true;
}
// ... write nextStreakCurrent to the UPDATE SET (replacing streakResult.newState.streakCurrent)
```

**Edge case:** If `milestoneHit === 7` fires AND consume would also fire in the same session (impossible by construction: you can't hit streak=7 milestone AND reset in the same `advanceStreak` call — milestone only fires on `streakAdvanced=true`, reset also sets `streakCurrent=1` not 7). The two branches are mutually exclusive. [VERIFIED: streak.ts logic]

### Anti-Patterns to Avoid
- **Using `resend.batch.send`:** Partial-failure reconciliation against `email_sent_log` is complex; 100-email chunk limit requires chunking logic. D-02 explicitly rejects this.
- **Adding `export const runtime = "nodejs"` to cron routes:** Phase 14 plan-00 documented this causes build failures in "use server" files. Do not add this export to route handlers.
- **Setting `export const maxDuration = 300` on daily-reminder on Hobby:** The route won't deploy on Hobby anyway due to cron frequency restriction. On Pro, 300s is the safe default without needing to set it explicitly (it's the default). Only weekly-recap benefits from an explicit `export const maxDuration = 300` as documentation intent.
- **Building Toast as a generic primitive before it has two consumers:** D-14 explicitly defers `src/components/ui/Toast.tsx` creation.
- **Caching `getRecentMasteryEvents` via `unstable_cache`:** The ticker's value proposition is freshness. No cache or short TTL (10–30s) acceptable; 1h would make it stale. The DB query is cheap (LIMIT 10, indexed on `created_at DESC`).

| Composite PK in drizzle | Manual ON CONFLICT in queries | `primaryKey({ columns: [...] })` in table definition | Drizzle enforces at schema level, generates correct SQL, already used at lines 229 + 358 of schema.ts |
| Timezone-aware "hour 19" filtering | Custom Intl.DateTimeFormat logic | Re-use `localDateFromTz` + `localHourFromTz` pattern from `streak.ts` | Already battle-tested in session-integration.ts; inject `now` for test determinism |
| Email deduplication | In-memory Set per cron run | `email_sent_log` table + INSERT…ON CONFLICT | SPEC constraint #9 explicitly bans in-memory dedup; DB is idempotent across retries + Vercel duplicate invocations |
| Client-side prefers-reduced-motion | CSS-only | `useReducedMotion()` hook (`matchMedia`) | Motion preference is behavioral, not just visual — auto-dismiss timer is a behavioral affordance |

**Key insight:** Email deliverability and idempotency are genuinely hard. Resend handles bounces, SPF/DKIM, unsubscribe lists, and retry semantics. The `email_sent_log` handles double-invocation idempotency (Vercel documents that cron events may occasionally fire twice).

## Common Pitfalls

### Pitfall 1: Hobby Plan Blocks Hourly Cron at Deploy Time
**What goes wrong:** Adding `{ "path": "/api/cron/daily-reminder", "schedule": "0 * * * *" }` to `vercel.json` on a Hobby account causes deployment to fail with error "Hobby accounts are limited to daily cron jobs."
**Why it happens:** Hobby minimum interval is once per day. [VERIFIED: vercel.com/docs/cron-jobs/usage-and-pricing]
**How to avoid:** Confirm Vercel Pro before writing `vercel.json`. If Hobby: use chunked dispatch (D-04 fallback) or remove daily-reminder from scope.
**Warning signs:** Deployment error mentioning "daily cron" restriction during `vercel deploy` or `vercel-build`.

### Pitfall 2: Resend Rate Limit Is 5 req/sec, Not 10
**What goes wrong:** `p-limit(5)` with ~150ms RTT generates ~33 req/sec theoretical throughput — 6.6× over the 5 req/sec limit. Results in 429 responses; emails silently not sent; `email_sent_log` rows written optimistically before 429 → email never actually sent, idempotency log blocks retry.
**Why it happens:** CONTEXT D-02 stated "10 req/sec" — this is incorrect. Official docs state 5 req/sec. [VERIFIED: resend.com/docs/api-reference/introduction]
**How to avoid:** Write `email_sent_log` AFTER confirming Resend returned success (not before). Default `EMAIL_SEND_CONCURRENCY=1`. Add 429 backoff: if `error` returned, check `error.statusCode === 429`, wait 200ms, retry once.
**Warning signs:** Cron response shows `emails_sent < users_evaluated` with no `skipped_already_sent` to account for the delta.

### Pitfall 3: `maxDuration` Misconception — Hobby Default Is 300s, Not 60s
**What goes wrong:** Planning around "Hobby cap = 60s" leads to over-engineering chunked dispatch for daily-reminder when the actual constraint is cron frequency (not duration).
**Why it happens:** CONTEXT D-04 states "Hobby caps at 60s" — outdated. Vercel updated their limits. [VERIFIED: vercel.com/docs/functions/configuring-functions/duration]
**How to avoid:** Understand the two distinct Hobby constraints: (1) frequency: once/day max; (2) duration: 300s max (same as Pro default). Both routes fit within 300s on Pro. Weekly-recap may exceed 300s at scale (5K opt-in users × 150ms × concurrency=1 = 750s). Set `export const maxDuration = 300` on weekly-recap as a hard kill switch, and use chunked dispatch with cursor pagination when user count > ~2000.
**Warning signs:** Weekly-recap cron timing out and Vercel logs showing "Function exceeded maximum duration."

### Pitfall 4: `unstable_cache` keyParts Must Include Per-User Variables
**What goes wrong:** `unstable_cache(fn, ['ticker-firstname'], { revalidate: 3600 })` without `userId` in keyParts → all users share the same cache entry → first user's name shown for everyone.
**Why it happens:** `keyParts` supplements the function signature; closures over external variables are not automatically included.
**How to avoid:** Always include `userId` in `keyParts`: `['ticker-firstname', userId]`. [VERIFIED: nextjs.org/docs/app/api-reference/functions/unstable_cache]
**Warning signs:** All ticker rows showing the same first name after a cache warm-up.

### Pitfall 5: `email_sent_log` Write Order — Write AFTER Resend Confirms
**What goes wrong:** INSERT `email_sent_log` BEFORE calling Resend → Resend call fails / 429 → log row exists → retry is skipped → email never sent.
**Why it happens:** "Optimistic" logging pattern treats the log as "intent" rather than "confirmation."
**How to avoid:** Per-row sequence: (1) check log — if exists, skip; (2) call Resend; (3) if `!error`, INSERT log row. If Resend fails, log row does not exist → retry can re-attempt.
**Warning signs:** `skipped_already_sent` count is high but email open rates are zero.

### Pitfall 6: Streak-Saver Consume on Grace-Applied Sessions
**What goes wrong:** `graceApplied=true` sessions: `streakResult.newState.streakCurrent` is unchanged (not 1), `streakAdvanced` is false. The consume detection `newState.streakCurrent === 1` would not fire — correct. But if code accidentally checks `!streakResult.graceApplied` incorrectly (using wrong boolean), grace sessions consume the token.
**Why it happens:** `graceApplied=true` means the streak survived via grace. The token is NOT consumed in this case — the consume should only fire on a full reset (gap >= 3, or gap=2 with grace exhausted).
**How to avoid:** Use the exact condition: `!streakResult.graceApplied && previousStreakCurrent > 1 && streakResult.newState.streakCurrent === 1`. [VERIFIED: streak.ts Rule 5 vs Rule 6]
**Warning signs:** Unit test: user with token=1 and a 2-day gap (grace available) should NOT consume token.

### Pitfall 7: Toast Double-Render on SSR + Hydration
**What goes wrong:** Server renders toast because `streak_saver_pending=true`. `clearStreakSaverPending` fires as server action. Client hydrates and re-renders. If the server action write completes between SSR and hydration, the server says `pending=true` but the hydrated state shows `pending=false` → React hydration mismatch warning.
**Why it happens:** Server action side-effects in the same render cycle can cause SSR/hydration divergence.
**How to avoid:** Mirror D-13 guidance: server action writes the flag THEN the component re-fetches state before committing the render. Pattern: mount toast as a client component that calls `clearStreakSaverPending` in `useEffect` (client-side, after mount). SSR renders the toast on first load regardless of pending flag value — client-side flag management avoids hydration mismatch.
**Warning signs:** React console warning "Hydration failed because the server rendered HTML didn't match the client."

### Pitfall 8: `activity_events` emit runs on EVERY session, not just star transitions
**What goes wrong:** INSERT without the star-transition guard fires on every `applyGamificationUpdate` call, bloating the table and causing `ON CONFLICT DO NOTHING` to silently swallow bugs.
**Why it happens:** Missing the `if (previousStars < 3 && newStars === 3)` guard.
**How to avoid:** The guard must wrap the INSERT. `previousStars` and `newStars` are already parameters in `GamificationInput` — use them. [VERIFIED: session-integration.ts line 153]
**Warning signs:** `activity_events` row count grows proportionally to all session saves rather than only 3-star transitions.

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | No | Cron routes use `CRON_SECRET` bearer token, not user auth |
| V3 Session Management | No | Cron routes are stateless; session managed by Clerk elsewhere |
| V4 Access Control | Yes | `assertCronSecret` guards cron routes; `social_activity_enabled` gates data visibility |
| V5 Input Validation | Yes | `kind` CHECK constraint in DB; `period_key` validated by format in route; `CRON_SECRET` validated server-side |
| V6 Cryptography | No | `CRON_SECRET` is a bearer token, not cryptographic. Use a high-entropy random string (≥32 chars). |

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Unauthenticated cron invocation | Spoofing | `assertCronSecret` checks `Authorization: Bearer ${CRON_SECRET}`; 401 on missing/mismatch |
| Double-send from duplicate Vercel cron event | Tampering / Denial of service | `email_sent_log` composite PK provides idempotency; second INSERT on same `(user_id, kind, period_key)` is no-op |
| Email enumeration from cron logs | Information Disclosure | Log dry-run at `console.info` level only; never log email addresses to stdout in production cron |
| `RESEND_API_KEY` exposure in logs | Information Disclosure | Helper validates key existence without logging the value; dry-run logs `userId` + `subject`, not the API key |
| Social opt-in bypass in now-playing query | Tampering | SQL WHERE clause enforces `social_activity_enabled = true` for auth users; anonymous plays counted separately via `COALESCE(user_id, session_key)` |
