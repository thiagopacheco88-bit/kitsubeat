## Phase Boundary

Layer functional virality + retention onto the Phase 14 visual foundation:
1. Anonymized **"X listening now"** chip on home `<SongCard>`s (last-30-min, ≥3 distinct opt-in-or-anon learners).
2. Anonymized **Recently Mastered ticker** on home (last 10 song-mastered events from opt-in users, Clerk first-name only, reduced-motion → static list).
3. **Daily streak-at-risk reminder email** at user-local 19:00 via Resend (only fires when streak > 0 AND not logged today).
4. **Sunday 18:00 UTC weekly recap email** via Resend (4 fixed sections: vocab learned, songs touched, streak status, next-up nudge).
5. **Free 7-day-milestone streak-saver token** (max 1 stockpiled, auto-applies silently with next-session toast).
6. **Single opt-IN master toggle** (`users.social_activity_enabled`, default off) gating all five behaviors.

This phase is **infrastructure + state-machine extension on a frozen visual foundation**. New deps: `resend`. New schema: 4 columns on `users` + 2 new tables (`activity_events`, `email_sent_log`). New routes: 2 cron endpoints. Visual surface: 1 chip on existing SongCard + 1 ticker section on home + 1 toggle row on /profile + 1 toast — all consume Phase 14 / 14.1 / 14.2 tokens; no new tokens or keyframes.

### Email + Cron Infrastructure (Requirements 4, 5, 8)

- **D-01 — Cron infra: Vercel Cron via `vercel.json`.** Project already deploys via Vercel (`vercel-build` in [package.json](../../../package.json#L12) runs `apply-migrations.ts && next build`). Two cron jobs fits Hobby-tier limit (2) exactly. New file `vercel.json` with `crons` array containing both routes. Reject GitHub Actions / Cron-Job.org / Upstash QStash — extra ops surface for zero marginal value when Vercel-native fits. Reject Inngest / Trigger.dev — overkill for 2 timed routes. Plan-phase verifies current Vercel plan; if Pro is required for the weekly-recap `maxDuration: 300` (see D-04), Plan-phase surfaces this as a deployment-cost item before code lands.

  **`vercel.json` shape:**
  ```json
  {
    "crons": [
      { "path": "/api/cron/daily-reminder", "schedule": "0 * * * *" },
      { "path": "/api/cron/weekly-recap",   "schedule": "0 18 * * 0" }
    ]
  }
  ```

- **D-02 — Email send: Resend SDK + serial loop with `p-limit` concurrency = 5.** `p-limit@^6.2.0` already a dep ([package.json:68](../../../package.json#L68)). At ~5K opt-in users × ~150ms RTT ÷ 5 concurrent = ~30s for weekly recap — fits Hobby 60s timeout with headroom; comfortably within Pro 300s. Per-row `email_sent_log` write between sends keeps idempotency simple (write row → call Resend → mark `sent_at`; on retry, presence of row short-circuits). Reject Resend `/emails/batch` endpoint — partial-failure reconciliation against `email_sent_log` adds bookkeeping, batch max 100/call needs chunking anyway. Reject background-queue services (Inngest, Vercel Queues) — overkill for 2 cron paths.

  **Concurrency tunable:** Plan-phase exposes `EMAIL_SEND_CONCURRENCY` env var defaulting to 5 — production tunes if Resend rate limits surface (Resend free tier: 10 req/sec; concurrency=5 stays under by 2x).

- **D-03 — Email templates: hand-written HTML strings in `src/lib/emails/`.** Shared helpers: `renderHeader()`, `renderFooter()`, `wrapLayout(body)`. Two templates: `dailyReminder.ts`, `weeklyRecap.ts`. Each exports a `render(props): { subject, html, text }` function. Plain-text fallback hand-written too (Resend recommends both; +5min/template, +deliverability). Reject `react-email` — adds dep + dev preview server; only 2 templates makes the toolchain heavy for the value (revisit at template count >5). Reject Resend hosted templates — vendor lock-in, dynamic vars only, no local preview without Resend account, breaks copy-review-in-PR workflow.

- **D-04 — Vercel function `maxDuration`: 60s daily, 300s weekly.** Daily reminder: `export const maxDuration = 60` (Hobby default). Daily fires hourly with only users in current hour-bucket — small batch (≤500 users at 5K total spread across 24 hour-buckets = ~210 avg). Weekly recap: `export const maxDuration = 300` — requires Vercel Pro (Hobby caps at 60s). Plan-phase verifies Vercel plan; if Hobby-only, fallback path: chunked dispatch with self-recursion (route processes N users, schedules a follow-up self-fetch with offset cursor; documented in vercel.json comment).

- **D-05 — `RESEND_API_KEY` dev-safety: log + return 200 with `{ dry_run: true }` payload when env unset.** Per SPEC §Req 8 + Constraint #6. Centralize in a `sendEmail(payload): Promise<{ sent: boolean, dry_run?: boolean }>` helper in `src/lib/emails/send.ts` so both cron routes share the dry-run branch identically. Helper stamps `dry_run: true` AND writes a structured log line (`console.info('[email-dry-run]', { kind, userId, subject })`). E2E test asserts dry-run path: route returns 200, `dry_run: true` in body, zero `email_sent_log` rows written.

- **D-06 — `CRON_SECRET` validation: shared middleware-style guard.** Both cron routes call `assertCronSecret(request)` first thing; helper reads `Authorization: Bearer ${CRON_SECRET}` header, returns 401 on missing/invalid. Same helper used in both routes prevents drift. Helper lives at `src/lib/cron/auth.ts`.

### Data Layer: activity_events + Now-Playing (Requirements 1, 2, 3)

- **D-07 — `activity_events` emission boundary: inside `applyGamificationUpdate` ([session-integration.ts:153](../../../src/lib/gamification/session-integration.ts#L153)), AFTER `deriveStars` resolves.** Detect transition `previousStars < 3 && newStars === 3` (the same delta the XP step-up bonus consumes — already in scope at session-integration.ts:222). Combined with `ON CONFLICT (user_id, song_id) DO NOTHING` for double-safety against retries / non-monotonic re-emission. Emits ONLY when transition fires; ON CONFLICT covers race-and-retry edge cases without bloating the happy-path semantic. Reject blind `ON CONFLICT DO NOTHING` always (adds an INSERT per session save even when stars don't change). Reject post-write trigger — disconnects emission point from the star-derivation that justifies it.

- **D-08 — `activity_events` schema:**
  ```sql
  CREATE TABLE activity_events (
    id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id text NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    event_type text NOT NULL CHECK (event_type = 'song_mastered'),
    song_id uuid NOT NULL REFERENCES songs(id) ON DELETE CASCADE,
    song_version_id uuid NOT NULL REFERENCES song_versions(id) ON DELETE CASCADE,
    created_at timestamptz NOT NULL DEFAULT now(),
    UNIQUE (user_id, song_id)
  );
  CREATE INDEX activity_events_created_at_idx ON activity_events (created_at DESC);
  CREATE INDEX activity_events_user_id_idx    ON activity_events (user_id);
  ```
  - **`user_id` is `text`** because [`users.id`](../../../src/lib/db/schema.ts#L425) is Clerk-derived text, not uuid (matches `song_plays.user_id` shape at schema.ts:621).
  - **`event_type CHECK = 'song_mastered'`** — single-value check now; expands cleanly to `IN (...)` when verse-mastery / level-up events land in a future phase (per SPEC §Out-of-scope, those are deferred).
  - **UNIQUE `(user_id, song_id)`** — not `(user_id, song_id, event_type)`. SPEC limits to song-mastered for now. When `event_type` expands, drop UNIQUE and replace with `UNIQUE (user_id, song_id, event_type)` in a follow-up migration.
  - **`song_version_id NOT NULL`** — carries which version was mastered (TV / full / cover); ticker links can resolve to the exact YouTube video the user mastered. Reject nullable — loses the version context a future ticker click might want.
  - **Indexes:** `(created_at DESC)` for ticker reads (`ORDER BY created_at DESC LIMIT 10`); `(user_id)` for per-user lookup if a future "your mastery feed" page lands.

- **D-09 — Ticker first-name read: `unstable_cache` keyed by `user_id`, TTL 1 hour.** `import { unstable_cache } from 'next/cache'`. `getTickerFirstName(userId)` returns Clerk first-name (via `clerkClient.users.getUser(userId).then(u => u.firstName ?? 'Someone')`), wrapped in `unstable_cache(fn, ['ticker-firstname', userId], { revalidate: 3600 })`. 10 ticker rows × per-render Clerk fetch is wasteful AND risks Clerk rate-limit on home traffic. Mirrored `users.first_name` column would need a Clerk webhook updater for active invalidation — defer; first-name changes are rare, 1h staleness acceptable. Reject mirrored column for now (revisit only if user-rename UX complaints arise).

  **Fallback:** When `firstName` is null/empty (Clerk allows users to omit first name), render "Someone" — anonymized, never a placeholder like "User_xyz".

- **D-10 — Now-playing query: single batched home aggregate, opt-in filter on auth users only, anon plays kept, `unstable_cache` 60s TTL.** Resolves SPEC REQ-1 + REQ-3 tension. SQL contract:
  ```sql
  SELECT sv.song_id, COUNT(DISTINCT COALESCE(sp.user_id, sp.session_key)) AS listener_count
  FROM song_plays sp
  JOIN song_versions sv ON sv.id = sp.song_version_id
  LEFT JOIN users u ON u.id = sp.user_id
  WHERE sp.played_at >= now() - interval '30 minutes'
    AND (sp.user_id IS NULL OR u.social_activity_enabled = true)
  GROUP BY sv.song_id
  HAVING COUNT(DISTINCT COALESCE(sp.user_id, sp.session_key)) >= 3
  ```
  - **Anonymous (NULL `user_id`) plays count toward the chip** — they have no opt-in row to consult; no privacy violation; chip stays meaningful at low-opt-in early stages.
  - **Authenticated plays gated on `social_activity_enabled = true`** — per SPEC REQ-3 Target (c).
  - **Caching:** wrap in `unstable_cache` keyed by hour-bucket (`Math.floor(Date.now() / 60000)`), TTL 60s per SPEC REQ-1 Target. Server-cached only — chip values may be stale by up to 60s; SPEC accepts.
  - Returns `Map<song_id, listener_count>` consumed by home `<SongCard>` rendering. SongCard renders chip when `listener_count >= 3`, suppressed otherwise.
  - Plan-phase decides: integrate into existing `getAllSongs` / `getFeaturedSongs` query path, or expose as separate `getNowPlayingCounts()` and merge in page.tsx. Recommendation: separate query, merge in page.tsx — keeps the home query plan stable and the now-playing read swappable / cacheable independently.

- **D-11 — Chip rendering: home SongCard ONLY, suppressed elsewhere.** Add a `nowPlayingCount?: number` prop to existing [SongCard](../../../src/app/songs/components/SongCard.tsx) (default `undefined`). Home page passes the prop from D-10's map; every other consumer of SongCard (`/songs`, `/path`, etc.) does not pass it → chip never renders. Per SPEC REQ-1 Acceptance: "chip absent on every other route." This avoids a polymorphism-via-context-flag and keeps the prop additive.

### Streak-Saver Integration + Toast (Requirement 6)

- **D-12 — State machine integration: integration-layer apply; `advanceStreak` stays pure and byte-equivalent.** The 14.1/12 streak state machine in [`streak.ts`](../../../src/lib/gamification/streak.ts) is well-tested ([`streak.test.ts`](../../../src/lib/gamification/__tests__/streak.test.ts)) and minimal-surface. Adding token state to it bloats a pure fn for a feature applicable only at 7-day milestone + reset events. Instead, `applyGamificationUpdate` reads `users.streak_saver_token` + `users.streak_saver_pending`, calls `advanceStreak`, then post-processes:
  - **Grant rule:** if `result.milestoneHit === 7 && currentToken === 0` → write `streak_saver_token = 1`. (No double-grant on subsequent 7-day passes after consume → re-grantable only after consume; SPEC §Req 6 Target.)
  - **Consume rule:** detect "reset that grace did not cover" via `(previousStreakCurrent > 1 && result.newState.streakCurrent === 1 && !result.graceApplied)`. If `currentToken === 1` → restore `streakCurrent = previousStreakCurrent + 1` (preserve + advance for today's session), set `lastStreakDate = today`, set `streak_saver_token = 0`, set `streak_saver_pending = true`.
  - `previousStreakCurrent` is already in scope at [session-integration.ts:237](../../../src/lib/gamification/session-integration.ts#L237) (the `userRow.streakCurrent ?? 0` read before `advanceStreak`).

  Reject pure-fn extension (couples token to a function whose name advertises "streak only"; bloats well-tested fn). Reject new separate `applyStreakSaver(streakState, token, gap)` — splits state across 2 fns, risks divergent definitions of "reset."

  **Plan-phase verification:** confirm the consume detection (`previousStreakCurrent > 1 && newState.streakCurrent === 1 && !graceApplied`) covers all reset paths in `advanceStreak`'s Rule 6 (gap >= 3, OR gap=2 with grace exhausted). Edge case: user at streak=0 with a token (impossible per grant rule, but assert in test). Edge case: token granted at exactly milestone, then consumed before the next session (sequence test).

- **D-13 — Toast "next session" detection: `users.streak_saver_pending boolean NOT NULL DEFAULT false`.** Added in same migration as `streak_saver_token`. Set true at consume-time (D-12). On next page load, the existing layout-level state fetch ([14.2 D-07](../14.2-redesign-home/14.2-CONTEXT.md) — `<LanternStreak>` consumer) already pulls user state for the streak chip; piggyback on that read for the pending flag. Server component reads → if `streak_saver_pending && session_render_count_for_user === 0`-equivalent (i.e., this render path), hand a `<StreakSaverToast streakSavedTo={streakCurrent} />` mount to the layout AND fire a `clearStreakSaverPending(userId)` server action in the same render cycle. Single source of truth in DB; no localStorage drift, no two-timestamp invariant.

  Reject `lastStreakSaverAppliedAt timestamptz` + `lastSavedToastSeenAt timestamptz` two-column diff — more state, more invariants. Reject localStorage flag — fragile across devices/browsers; loses toast on second device.

  **Plan-phase verification:** confirm `clearStreakSaverPending` write happens BEFORE toast render commits to client — otherwise SSR + hydration mismatch could render the toast twice (server says pending=true, client sees state cleared, hydration warning). Pattern: server action writes flag → re-fetch state in same async boundary → render. Mirror the existing theme-cookie + DB-write pattern in [setThemePreference](../../../src/app/actions/userPrefs.ts#L185).

- **D-14 — Toast UI: compose from existing UI primitives; reduced-motion fallback inherited from globals.css global override.** Plan-phase verifies whether [src/components/ui/](../../../src/components/ui/) has a toast primitive (Phase 14 shipped Button/Card/Badge/Modal/EmptyState/Skeleton; toast was not on the list). If absent, compose from `<Card>` + auto-dismiss `setTimeout(5000)` + close-button. Reduced-motion fallback (per Phase 14 D-13 + 14.2 D-11) — when `prefers-reduced-motion: reduce`, the `*` global keyframe override in [globals.css](../../../src/app/globals.css) suppresses the slide-in animation; toast renders as a static banner pinned to top of viewport with manual close only (no auto-dismiss timer; manual close only — auto-dismiss is itself a motion affordance for reduced-motion users).

  Plan-phase decides: rely on the global keyframe override (cheapest), OR add an explicit `useReducedMotion()` hook to gate the auto-dismiss timer (most correct). Recommendation: explicit `useReducedMotion()` hook for the timer logic (motion preference is not just animation suppression — it's a behavioral preference; auto-dismiss requires motion-equivalent attention).
