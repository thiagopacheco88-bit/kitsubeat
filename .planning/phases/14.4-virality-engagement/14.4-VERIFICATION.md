### Human Verification Required

#### 1. Daily Reminder Cron — Timezone Coverage

**Test:** Deploy with `CRON_SECRET` set. Wait for 19:00 UTC. Check if a test user with `streak_tz = "Europe/London"` (UTC+1) receives a daily reminder email.
**Expected:** User should receive email if the cron is hourly (SPEC), but with the `0 19 * * *` schedule, the cron fires at 19:00 UTC. The user's local hour is 20:00, not 19. The `EXTRACT(HOUR FROM now() AT TIME ZONE streak_tz) = 19` filter in the query will return no matching rows. So the user will never receive the email unless their streak_tz is UTC. This is a functional limitation introduced by the Hobby plan constraint change — verify whether this behavior is acceptable for the MVP or if an alternative (e.g., querying for any local hour between 19-23) should be considered.
**Why human:** Requires production deployment with real timezone data to observe. The schedule change was user-approved but the downstream consequence (most non-UTC users never receive the email) may not have been fully evaluated.

#### 2. Weekly Recap Vocab Count Semantics

**Test:** Seed a user with 10 `user_vocab_mastery` rows updated in the last 7 days (mixed: some with stage advancement, some reviews without stage change). Run the weekly recap cron manually with the secret.
**Expected:** SPEC says "count of user_vocab_mastery rows whose stage advanced." The actual query uses `lastReviewedAt >= 7 days ago` which counts all reviews, including those that didn't advance stage.
**Why human:** Cannot verify the semantic correctness of "stage advanced" vs "reviewed" without DB access and seeded data.

#### 3. ISO Week Key Correctness

**Test:** Set system date to 2024-12-30 (Monday of ISO week 2025-W01). Run `getISOWeekKey(new Date())` (accessible by reading the weekly-recap route source or calling it in a Node REPL). Verify it returns `"2025-W01"` not `"2024-W53"`.
**Expected:** The function returns the ISO 8601 week key matching what you would expect from a Monday-start week calendar. If the function uses `getUTCDay()` (0=Sunday), the calculation is Sunday-first and will produce different results than ISO 8601 (Monday-first).
**Why human:** A date calculation bug in the week key would cause duplicate recap emails to be sent in the same ISO week (idempotency guard uses wrong key). This is a correctness concern flagged by the code review (REVIEW.md WR-03).
