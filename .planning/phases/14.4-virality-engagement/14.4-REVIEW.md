# Phase 14.4: Code Review Report

**Reviewed:** 2026-05-08T21:08:34Z

**Files Reviewed:** 36

## Summary

Phase 14.4 adds social virality features: a "Recently Mastered" ticker, a "listening now" chip, streak-saver grant/consume, transactional emails (daily reminder + weekly recap), and a social opt-in profile toggle. The overall architecture is sound — the DB migration is atomic, idempotency guards are correctly placed, opt-in filtering is applied consistently, and the streak-saver pure-function design is clean and well-tested.

Five warnings were found: a fixed `hoursLeft` constant that ignores user timezone, a silent email-log skip during dry-run mode (the idempotency insert is guarded by `!isDryRun` but the same guard applies in both crons, making dry-run crons non-idempotent across re-runs), a `getISOWeekKey` implementation that uses a non-standard week number algorithm, an `activityEvents` insert that can silently fail when `songRows[0].versionId` is null/undefined, and an unchecked cast in the `updateUserPrefs` upsert. Four info-level items cover dead-render logic, a magic-number threshold, a missing `aria-live` on the ticker, and a repeated `useReducedMotion` hook definition.

## Warnings

### WR-01: `hoursLeft` is hardcoded to `5` — ignores user's actual remaining hours

**File:** `src/app/api/cron/daily-reminder/route.ts:65`
**Issue:** `hoursLeft` is set to the constant `5` regardless of when in the 19:xx window the cron fires or what the user's actual timezone offset is. Since the cron schedule in `vercel.json` is `0 19 * * *` (UTC), users whose `streak_tz` is UTC+5 see "5 hours left" at 00:00 local, which is actively misleading (they already missed midnight). Users in UTC-8 see the same "5 hours left" at 11:00 local, which is wildly wrong. The comment acknowledges this is simplified but there is no TODO or follow-up issue.
**Fix:**
```typescript
// Compute actual hours remaining until midnight in the user's timezone
function hoursUntilMidnight(tz: string | null): number {
  const now = new Date();
  const tzName = tz ?? "UTC";
  const formatter = new Intl.DateTimeFormat("en-US", {
    timeZone: tzName,
    hour: "numeric",
    hour12: false,
  });
  const localHour = parseInt(formatter.format(now), 10);
  return Math.max(1, 24 - localHour);
}

// Then replace:
const hoursLeft = hoursUntilMidnight(user.streak_tz);
```

### WR-02: Dry-run skips the idempotency log insert — cron is not idempotent in dry-run mode

**File:** `src/app/api/cron/daily-reminder/route.ts:82-89` and `src/app/api/cron/weekly-recap/route.ts:129-137`
**Issue:** Both cron handlers wrap the `email_sent_log` insert in `if (!isDryRun)`. This means that during local development (no `RESEND_API_KEY`), repeatedly invoking the cron will re-evaluate and re-"send" (in dry-run) all eligible users every time with no log entry persisted. If `isDryRun` is ever toggled to true in a production-like staging environment while `RESEND_API_KEY` is absent (which the current code uses as the sole gate), emails would not be sent but the idempotency record would also never be written, so the next real run would send emails to users who were already "processed" in staging. More concretely, if a developer runs the cron endpoint in staging to test user selection, they will not pollute production email logs — but the next production run will re-send to those same users.

This is a minor risk in practice (staging vs. prod have separate DBs) but the two concerns — dry-run detection and idempotency logging — should not be conflated.

**Fix:** Write the idempotency log in both modes, or make dry-run mode explicit via a separate header rather than tied to `RESEND_API_KEY`:
```typescript
// Always write the log (even in dry-run); include a dry_run flag in the record
// for observability. The composite PK still prevents double-sends on re-run.
await db
  .insert(emailSentLog)
  .values({ user_id: user.id, kind: "daily_reminder", period_key: todayKey })
  .onConflictDoNothing();
emailsSent++;
```

### WR-03: `getISOWeekKey` uses a non-standard week number — mismatches ISO 8601

**File:** `src/app/api/cron/weekly-recap/route.ts:26-33`
**Issue:** The implementation computes week number as `Math.ceil((dayOfYear + startOfYear.getUTCDay()) / 7)`. This is not ISO 8601 (which defines week 1 as the week containing the first Thursday of the year, with Monday as week start). The `period_key` format `YYYY-Www` implies ISO week semantics. Edge cases: in years where Jan 1 is a Sunday (e.g. 2023), `startOfYear.getUTCDay() = 0`, so `dayOfYear 1 + 0 = 1` → week 1 (correct by accident). But in years where Jan 1 is Saturday (e.g. 2022), days 1–2 are assigned to week 1 while ISO 8601 says they belong to the prior year's last week. This creates a scenario where two consecutive Sunday runs in late December / early January can write the same `period_key` for two distinct ISO weeks, allowing a second email to be skipped that should have been sent (or vice versa).
**Fix:**
```typescript
function getISOWeekKey(date: Date): string {
  // ISO 8601: week containing first Thursday; Monday = day 1
  const d = new Date(Date.UTC(date.getUTCFullYear(), date.getUTCMonth(), date.getUTCDate()));
  // Set to nearest Thursday (Thursday = day 4; adjust to Monday)
  d.setUTCDate(d.getUTCDate() + 4 - (d.getUTCDay() || 7));
  const yearStart = new Date(Date.UTC(d.getUTCFullYear(), 0, 1));
  const weekNum = Math.ceil(((d.getTime() - yearStart.getTime()) / 86400000 + 1) / 7);
  return `${d.getUTCFullYear()}-W${String(weekNum).padStart(2, "0")}`;
}
```

### WR-04: Silent `activityEvents` insert when `versionId` is null — event silently dropped

**File:** `src/lib/gamification/session-integration.ts:241-263`
**Issue:** The subquery for `versionId` uses a `SELECT` inside `sql\`\`` and returns `sql<string>`. If the song has no version with a `youtube_id` (all versions have `youtube_id = NULL`), the subquery returns `NULL`, which is cast to `string` by TypeScript's type assertion but is actually `null` at runtime. The subsequent `insert` would then supply `null` for `song_version_id`, which has a `NOT NULL` constraint in both the migration and schema. Drizzle will throw a DB-level error, which is caught nowhere — it propagates to the caller as an unhandled rejection inside a fire-and-forget path that wraps the step with no `try/catch`. This means a 3-star event for a song with no YouTube ID silently fails the entire `applyGamificationUpdate` call.
**Fix:**
```typescript
if (songRows[0] && songRows[0].versionId) {
  await db
    .insert(activityEvents)
    .values({
      user_id: userId,
      event_type: "song_mastered",
      song_id: songRows[0].id,
      song_version_id: songRows[0].versionId,
    })
    .onConflictDoNothing();
}
// else: no version with youtube_id — skip silently (no activity event emitted)
```

### WR-05: `updateUserPrefs` upsert always overwrites all columns — partial patch loses existing values

**File:** `src/app/actions/userPrefs.ts:103-119`
**Issue:** The upsert uses `db.insert(...).values({ id: userId, skip_learning: normalized.skip_learning ?? false, new_card_cap: normalized.new_card_cap ?? DEFAULT_NEW_CARD_CAP, soundEnabled: normalized.soundEnabled ?? true, ... })`. When only `socialActivityEnabled` is in the patch (the new social toggle), the `values` row seeds all other columns with their defaults. Because the `onConflictDoUpdate.set` only sets `normalized` fields, the other columns are not overwritten on conflict — that part is correct. However, on a fresh `INSERT` (first-time upsert for a user), all columns get the fallback defaults regardless of any previously stored state. This only matters if somehow a user row is deleted and re-inserted (unlikely), but the double-path (insert vs. conflict-update) is asymmetric: `skip_learning` in the insert defaults to `false` while the conflict update path only sets it if it was in the patch. This asymmetry is not a bug in normal operation, but it creates a subtle risk when the schema gains new columns that have non-default defaults — the insert path must be manually kept in sync.

More concretely: a user who only changes `socialActivityEnabled` will trigger an insert with `skip_learning: false` if their row doesn't exist yet, even if their stored preference was `true`. This is a correctness issue for new users whose row is seeded elsewhere first (e.g., `getUserPrefs` → `insert on conflict do nothing`) and then a partial upsert is attempted.
**Fix:** Separate the upsert logic: call `INSERT ... ON CONFLICT DO NOTHING` first (to seed defaults), then a plain `UPDATE` for the patch fields. This is how `getUserPrefs` already works:
```typescript
// Seed row if absent (preserves existing values on conflict)
await db.insert(users).values({ id: userId }).onConflictDoNothing({ target: users.id });
// Apply only the patched fields
if (Object.keys(normalized).length > 0) {
  await db.update(users)
    .set({ ...normalized, updated_at: new Date() })
    .where(eq(users.id, userId));
}
```

### IN-01: `StreakSaverToast` is always rendered but immediately returns null when not pending — dead render cycle

**File:** `src/app/page.tsx:114-120`
**Issue:** The server renders `<StreakSaverToast ... isPending={true} />` only when `userRow?.streakSaverPending` is truthy, but the component itself has an internal `isPending` prop and a `mounted` gate. The outer `isSignedIn && userRow?.streakSaverPending` guard means the component is only mounted when there is definitely a pending state — the internal `if (!mounted || !visible) return null` is a no-op until hydration. This is fine architecturally (Pitfall 7 pattern is correct). However, the `isPending` prop is hardcoded to `true` at the call site, making the prop redundant — if the parent only renders the component when pending is true, the child never needs to re-check. Consider removing the `isPending` prop and always showing on mount, or always passing the raw boolean for defensive clarity.
**Fix:** Either pass `isPending={userRow.streakSaverPending}` (boolean, not always `true`) and render unconditionally when `isSignedIn`, or document why the outer guard + inner prop are intentionally redundant.

### IN-04: `RecentlyMasteredTicker` has no `aria-live` region — screen reader users miss new events

**File:** `src/app/components/home/RecentlyMasteredTicker.tsx:73` and `src/app/components/home/RecentlyMasteredTicker.tsx:100`
**Issue:** The ticker section element has `aria-label="Recently mastered songs"` but no `aria-live` attribute. If the parent ever re-renders the ticker with new events (currently it's server-rendered, so this is not a problem today), screen readers will not announce additions. Additionally, the auto-scroll strip is not keyboard-navigable beyond tab-through of individual links — there is no scroll-left/right keyboard affordance. This is a minor accessibility gap for the current implementation since the data is static per page load.
**Fix:** Add `aria-live="polite"` to the `<section>` element for forward compatibility if client-side refresh is added in a later phase.
