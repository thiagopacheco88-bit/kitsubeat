## Prompt context + structure

### Q1: Context window: how much do we feed Ollama per stub verse?

| Option | Description | Selected |
|--------|-------------|----------|
| Whole-song raw lyrics + 2 verses before/after with translations | Per CONTEXT.md original spec. ~1.5-3K tokens per call — fits qwen2.5:14b context comfortably. | ✓ |
| Trimmed: 4 verses before/after only | Drop whole-song. Cheaper per call (~500-1K tokens), faster. Risk: loses song-wide thematic context. | |
| Whole-song + ALL existing translations (max context) | Send the entire lesson cache for the song. ~5-10K tokens. Maximum signal but slower. | |

**User's choice:** Whole-song raw lyrics + 2 verses before/after with translations (Recommended)

### Q2: Output format: how does Ollama return the verse JSON?

| Option | Description | Selected |
|--------|-------------|----------|
| JSON-mode strict via Ollama format param | Use Ollama's `format: 'json'` API param + JSON schema in prompt. Forces grammatically valid JSON output. | ✓ |
| Few-shot text + manual extract | Provide 2-3 example verse JSON, parse with regex/JSON.parse. More flexible, more parse failures. | |
| JSON-mode + 1 example verse from same song | JSON-mode strict + include one neighbour verse as in-prompt example. Best of both, slightly more tokens. | |

**User's choice:** JSON-mode strict via Ollama format param (Recommended)

### Q3: Token shape strictness: what fields are mandatory in the output?

| Option | Description | Selected |
|--------|-------------|----------|
| Strict: every field including kanji_breakdown when applicable | Match patch-sign-flow-verse-8.ts template exactly. Highest catalog quality. | ✓ |
| Loose minimum: surface/reading/romaji/meaning.en required, rest optional | Only block on missing core fields. Faster ship, more drift. | |
| Strict for tokens, loose for kanji_breakdown only | All token fields required, but kanji_breakdown optional (expensive to generate well). | |

**User's choice:** Strict: every field including kanji_breakdown when applicable (Recommended)

## Failure path: retry + inline review

### Q1: What's the retry sequence before escalating to inline Claude Code review?

| Option | Description | Selected |
|--------|-------------|----------|
| Single attempt per model → inline | Try winning model once. Fail = inline review immediately. Cleanest fail-forward. | ✓ |
| Try winning model → try alt model → inline | First fail = retry on alt model. Second fail = inline. ~2x latency for failed verses. | |
| Retry winning model with temp=0 fallback → inline | Default temp first, fail = retry at temp=0 (deterministic). Same model only. | |

**User's choice:** Single attempt per model → inline (Recommended)

### Q2: Inline review UX: when does Claude Code see the queue?

| Option | Description | Selected |
|--------|-------------|----------|
| Batch session at end — review all flagged verses in one chat | Run draft through all 6 songs first. Then one chat with full queue. Single attention burst. | ✓ |
| Per-song interleaved — draft + review + push, song by song | Process song 1 fully before song 2. Tighter feedback loop, splits attention. | |
| Threshold-gated: drafts ship immediately, only schema-hard-fails reviewed | Schema-valid drafts auto-merge with no review. Conflicts with SPEC's mandatory inline review. | |

**User's choice:** Batch session at end (Recommended)

### Q3: Beyond schema-fail, what else triggers 'needs_inline_review'?

| Option | Description | Selected |
|--------|-------------|----------|
| Schema fail OR meaning contains '?'/'unknown'/empty string | Tightest gate. Catches LLM cop-outs. Likely flag rate: 15-25% of 159. | ✓ |
| Schema fail only | If JSON parses + matches schema, ship. Trusts model on semantic quality. Flag rate: 5-10%. | |
| Schema fail OR translations.{en,pt-BR,es} starts with '(' (original stub signature) | Catches the worst regression mode. Flag rate: 10-15%. | |

**User's choice:** Schema fail OR meaning contains '?'/'unknown'/empty string (Recommended)
