# Phase 11.3: Fix Untranslated JP Verses — Specification

**Created:** 2026-04-26
**Ambiguity score:** 0.121 (gate: ≤ 0.20)
**Requirements:** 7 locked

## Goal

Replace stub-translated JP verses with proper tokenized translations (en + pt-BR + es) across the 6 worst-offender songs in the catalog — 159 broken verses total — and ship the cleaned lessons to Neon with a verifiable zero-stub gate.

## Background

A 2026-04-26 catalog audit found 970 stub-translated JP verses across 102 of 274 songs (37%). Stubs match this signature: `v.tokens.length === 1 && hasJapanese(v.tokens[0].surface) && v.translations.en.startsWith("(")`. Likely root cause: commit bec890c's lesson-prompt coverage rule (Phase 08.4) forced the LLM to emit verse entries for previously-skipped filler lines, and for some lines it cheaped out — emitting one "other" token with `meaning.en = "(untranslated lyric line)"` and verse-level `translations = { en: "(untranslated)", ... }`.

Existing infrastructure:
- [scripts/seed/apply-verse-patch.ts](../../../scripts/seed/apply-verse-patch.ts) is append-only (`after_original` mode); needs `replace_verse_number` mode added.
- [scripts/seed/auto-coverage-patch.ts](../../../scripts/seed/auto-coverage-patch.ts) is the existing batch-pipeline pattern — drafting infra mirrors it.
- [scripts/debug/patch-sign-flow-verse-8.ts](../../../scripts/debug/patch-sign-flow-verse-8.ts) is the manual single-verse template proving the token shape.
- [scripts/seed/05-insert-db.ts](../../../scripts/seed/05-insert-db.ts) gained `--slug=...` filter on 2026-04-26 (commit 7f1dc95).
- `.planning/verse-patches/` already contains ~10 append-mode patches from prior auto-coverage runs — new replace-mode patches must coexist in the same dir without disrupting re-runs.
- **Ollama is not installed locally** (not in PATH, not at standard Windows locations). Install must be part of this phase.

Scope-wise, this phase ships only the 6 worst offenders (159 verses):

| Slug                                       | Stub verses |
|--------------------------------------------|-------------|
| again-yui                                  | 38          |
| whats-up-people-maximum-the-hormone        | 29          |
| diver-nico-touches-the-walls               | 28          |
| mezamero-yasei-matchy-with-question        | 22          |
| name-of-love-cinema-staff                  | 21          |
| yellow-moon-akeboshi                       | 21          |
| **Total**                                  | **159**     |

The remaining 96 songs (811 verses) are deferred to a follow-up todo (`11.3.1` or backlog), to be opened after ship based on observed Ollama quality and inline-review attention burn.

## Requirements

1. **Ollama runtime installed and verified**: Local Ollama install with both candidate models pulled.
   - Current: Ollama not on PATH; no models pulled
   - Target: `ollama serve` reachable on `localhost:11434`; `qwen2.5:14b-instruct` and `llama3.1:8b` both downloaded and `ollama run` verified end-to-end
   - Acceptance: `ollama list` returns both model IDs; a smoke-test JP→en prompt against each returns valid JSON in the schema below

2. **Stub-detection audit script**: Detect the stub signature across all 3 locales in cached lessons.
   - Current: No audit script exists; manual count from ad-hoc grep
   - Target: `scripts/seed/audit-untranslated-verses.ts` scans `data/lessons-cache/*.json`, detects stub verses (signature: `tokens.length === 1 && hasJapanese(tokens[0].surface) && (translations.en|pt-BR|es).startsWith("(")`), and writes `.planning/translation-queue.tsv` with columns `slug \t verse_number \t surface \t locales_broken`
   - Acceptance: Running the script against current cache reports 970 stubs across 102 songs (matching prior audit); the 6 in-scope songs total exactly 159 stub-verse entries in the TSV

3. **Ollama draft pipeline with whole-song + neighbour context**: Draft replacement verse JSON in all 3 locales per stub.
   - Current: No drafter exists
   - Target: `scripts/seed/draft-untranslated-translations.ts` reads the queue, prompts Ollama per stub with (a) the full song's raw lyrics, (b) the 2 verses before and 2 verses after with their existing translations, (c) a schema-locked output spec matching the existing token shape (kanji/reading/romaji/grammar/grammar_color/meaning.{en,pt-BR,es}/jlpt_level per token + verse-level translations.{en,pt-BR,es}); writes `.planning/verse-patches/<slug>.json` entries with `replace_verse_number` mode
   - Acceptance: For each in-scope song, every stub verse produces either (a) a schema-valid replacement entry in the slug's patch file, OR (b) a queue entry flagged `needs_inline_review`. No silent skips.

4. **Inline Claude Code review for every Ollama fail**: Mandatory human-in-the-loop for low-confidence drafts.
   - Current: No review path exists
   - Target: Verses where Ollama output fails schema validation OR returns a token whose `meaning.en` contains "?", OR fails 2nd-pass retry against the alternate model, are queued for inline Claude Code review. Reviewed verses are written into the same patch file under `replace_verse_number` mode.
   - Acceptance: After review pass, the queue has zero entries flagged `needs_inline_review`; every stub verse in scope has a corresponding patch entry

5. **`apply-verse-patch.ts` extended with replace-mode**: Single applier handles both append and replace modes.
   - Current: Applier only supports `after_original` (append-only)
   - Target: Applier inspects each patch entry — `after_original` triggers existing append behaviour; `replace_verse_number` overwrites the matching `verse_number` in place (preserving sequential numbering after the patch). Both modes coexist in `.planning/verse-patches/<slug>.json`. Idempotency guard from current append-mode preserved for replace-mode (re-running the applier is a no-op once patch is applied).
   - Acceptance: Test patch with one append + one replace entry against a fixture lesson produces correct merged output; running the same patch twice produces identical output

6. **DB push per slug**: Cleaned lessons reach Neon via slug-batched insert.
   - Current: 6 in-scope songs hold stub verses in `song_versions.lesson` on Neon
   - Target: After patch apply, `npx tsx scripts/seed/05-insert-db.ts --slug=<slug>` runs once per in-scope slug
   - Acceptance: For each of the 6 slugs, `song_versions.lesson` JSONB on Neon contains the patched lesson (no stub verses)

7. **Zero-stub verification gate (cache + DB)**: Both checks must pass before phase is marked complete.
   - Current: No verification gate exists
   - Target: Audit script supports a `--verify` mode that checks (a) `data/lessons-cache/<slug>.json` for stub matches AND (b) Neon `song_versions.lesson` for the same slug for stub matches. Run against the 6 in-scope slugs.
   - Acceptance: `npx tsx scripts/seed/audit-untranslated-verses.ts --verify --slugs=<6-slugs>` returns 0 stubs from both cache and DB sources

## Boundaries

**In scope:**
- Ollama install + 2 candidate model pulls (qwen2.5:14b-instruct, llama3.1:8b)
- Audit script (`audit-untranslated-verses.ts`) detecting stubs across en + pt-BR + es
- Translation queue TSV generator scoped to the 6 in-scope songs
- Ollama draft pipeline with whole-song + 2-verse-window context
- Inline Claude Code review path for all Ollama fails
- `apply-verse-patch.ts` extension to support `replace_verse_number` mode
- Per-slug `05-insert-db` pushes for the 6 in-scope songs
- Verification gate covering cache + DB

**Out of scope:**
- The remaining 96 songs (811 verses) — deferred to `11.3.1` follow-up todo, opened after ship based on observed Ollama quality and inline-review burn
- Improving `scripts/lib/lesson-prompt.ts` — the bug is the LLM cheaping out on a subset of lines, not a broken prompt
- Re-generating entire lessons end-to-end — too expensive; spot-fix only the broken verses
- A formal translation-quality grading framework — if Ollama drafts feel weak, the inline review path absorbs it
- Picking the "best" Ollama model in the spec — that is a /gsd-discuss-phase decision after the install + smoke test
- Automating retry-on-2nd-model logic in the spec — the spec only locks "fallback to inline review on fail"; whether to try the alternate model first is a discuss-phase HOW decision

## Constraints

- **No paid API credits** (user constraint, persisted in memory): all drafting must use local Ollama or inline Claude Code; no external paid LLM API calls.
- **Token shape must match existing schema**: replacements must produce `{surface, reading, romaji, grammar, grammar_color, meaning.{en,pt-BR,es}, jlpt_level}` per token and `translations.{en,pt-BR,es}` per verse — anything else breaks the lesson renderer.
- **Patch file format coexistence**: New `replace_verse_number` entries must coexist with existing `after_original` entries in the same `.planning/verse-patches/<slug>.json` file without breaking re-runs of prior auto-coverage patches.
- **Idempotency**: Re-running the applier or the DB push must be a no-op (matches the existing append-mode contract from commit 43c0dac).
