<decisions>
## Implementation Decisions

### Ollama Model Strategy
- **D-01:** Pilot both `qwen2.5:14b-instruct` and `llama3.1:8b` on the same 10-verse sample (drawn from across the 6 in-scope songs). Compare schema-pass rate, JP-translation tone, and per-verse latency. Pick winner; lock for the remaining 149 verses. Pilot artifact: `.planning/phases/11.3-fix-untranslated-jp-verses/MODEL-PILOT.md` with side-by-side outputs + decision rationale.
- **D-02:** Compute backend: let Ollama auto-detect GPU vs CPU (no `OLLAMA_NUM_GPU` override). User did not specify hardware preference.

### Prompt + Output Structure
- **D-03:** Per-stub Ollama prompt includes: (a) the full song's raw lyrics (kept compact — drop romaji/translations, JP only), (b) the 2 verses immediately before and 2 verses immediately after the stub, with their existing en/pt-BR/es translations and full token shape, (c) a JSON schema describing the required output. Estimated 1.5–3K input tokens per call — fits qwen2.5:14b context comfortably.
- **D-04:** Use Ollama's `format: 'json'` API param to enforce JSON-valid output. Both candidate models support this.
- **D-05:** Token-shape strictness: every field required per token (`surface`, `reading`, `romaji`, `grammar`, `grammar_color`, `meaning.{en,pt-BR,es}`, `jlpt_level`). `kanji_breakdown` required when the token's surface contains kanji; absent for kana-only tokens. Verse-level `translations.{en,pt-BR,es}` and `literal_meaning.en` required. Reference template: [scripts/debug/patch-sign-flow-verse-8.ts](../../../scripts/debug/patch-sign-flow-verse-8.ts).

### Failure Path
- **D-06:** Retry shape: single Ollama attempt per stub. On fail, escalate to inline Claude Code review immediately. No alt-model retry, no temperature-fallback retry. Pilot stage proves the chosen model is sound; further automated retries add latency without changing the failure mode.
- **D-07:** Inline review surface: batch session at the end of the draft pass. Run Ollama against all 159 stubs across all 6 songs first; collect every `needs_inline_review` flagged verse into a single queue; open one Claude Code session against that queue for the inline review pass. Patch file written incrementally as each reviewed verse is approved.
- **D-08:** Flag triggers for `needs_inline_review`: (a) JSON parse failure, (b) schema validation failure (missing required field, wrong type), (c) any token's `meaning.en` containing `?`, the literal word `unknown`, or empty string, (d) verse-level `translations.{en,pt-BR,es}` starting with `(` (the original stub-detection signature — catches LLM regression to the same cop-out). Expected flag rate: 15–25% of 159 ≈ 25–40 verses for inline review.

### Rollout Sequencing
- **D-09:** Smoke test before scaling: pick the smallest in-scope song (yellow-moon-akeboshi or name-of-love-cinema-staff, both 21 stubs). Run the full pipeline (audit → draft → inline review queue → apply patch → DB push) on that one song. Manual Vercel play-through verification (open the song page on the deployed site, scroll all verses, confirm zero `(untranslated)` renders). Only proceed to the remaining 5 songs after smoke verification passes.
- **D-10:** Smoke verification mode: manual play-through on Vercel. Eyeballs every verse for `(untranslated)` render — catches both data-quality and render regressions. ~5 min per song.
- **D-11:** `apply-verse-patch.ts` execution order when both modes coexist in a slug's patch file: process all `replace_verse_number` entries first (modifying existing verses in place — does not shift verse numbers), then process all `after_original` entries (inserting new verses after originals — operates on post-replace state). Predictable, prevents append-then-replace shifting bugs.

### Claude's Discretion
- Pilot sample selection (which 10 verses from across the 6 songs). Suggested heuristic: 2 from each of the 5 songs that aren't the smoke-test song (so smoke-test song's data isn't pre-leaked into pilot).
- Ollama temperature, max_tokens, top_p — choose defaults that maximize JSON-validity; tune if pilot reveals issues.
- Per-verse / per-song progress logging format during the ~1.5–2.5 hour draft run.
- TSV column ordering and exact field names beyond the SPEC's requirement of `slug \t verse_number \t surface \t locales_broken`.

</decisions>
