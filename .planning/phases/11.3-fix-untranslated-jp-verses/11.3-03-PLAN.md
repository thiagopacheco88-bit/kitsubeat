<objective>
Extend the existing `scripts/seed/apply-verse-patch.ts` (currently append-only) to support a new `replace_verse_number` patch entry shape, so a single `.planning/verse-patches/<slug>.json` file can mix `after_original` (append) and `replace_verse_number` (in-place edit) entries — and the applier processes them in the locked D-11 order: ALL replaces first, THEN appends operating on the post-replace state. Cover the contract with a Vitest fixture that exercises both modes in one file plus the idempotency guarantee (running twice = no-op the second time). Also fix a critical import-safety regression: lines 77–95 of the current file contain top-level CLI code that calls `process.exit(1)` when no slug arg is supplied. Importing the module from a Vitest test (which provides no slug arg) currently kills the test runner. Wrap the CLI dispatch in a Node ESM entry-point guard so the module is import-safe.

Purpose: SPEC-REQ-5 ("apply-verse-patch.ts extended with replace-mode") is the seam between Plan 05 (drafter writes replace entries) and Plan 07/08 (rollout reads them). Without this extension, every drafted replacement would have to live in a separate file system, doubling complexity and breaking the "patches coexist in one slug.json" invariant called out in CONTEXT.md `code_context`. The entry-point guard is a hard prerequisite — without it, Task 2's Vitest fixture cannot import `applyPatch` without crashing.

Output: 1 modified script (with entry-point guard + replace-mode + applyPatch export) + 1 new Vitest test file. The 6 in-scope slugs already have `.planning/verse-patches/<slug>.json` files from prior auto-coverage runs; this plan does NOT touch those files.
