## Summary

The Phase 11.3 source delivery is structurally sound. The audit script is single-source-of-truth and reuses the same `isStub()` predicate across cache walk + cache verify + DB verify (good). The patcher's two-pass replace-then-append merge is correctly ordered per D-11, and the entry-point guard is canonically Node-ESM-shaped. The Vitest fixture exercises the high-level shape of all three modes (replace, append, mixed) and proves byte-equal idempotency for the simple case.

The principal weakness is that **the sidecar fix in commit 1a77cc6 added two behaviors (translation-aware idempotency + cache-side timing preservation) that no test exercises**. Both behaviors are load-bearing — without them, the smoke-test rollout in Plan 07 would have skipped 14/21 verses. The current 6-test suite would not regress if either behavior were silently reverted. This is not a bug today, but it is a real test-coverage gap that the reviewer's prompt explicitly flagged. See WR-01.

A correctness issue worth landing before any future re-run: the audit script's `--verify` gate **silently swallows JSON parse errors on cache files** and can therefore PASS the gate while a corrupted cache file goes unnoticed. See HI-01.

## High

### HI-01: `--verify` cache parse errors do not fail the gate

**File:** `scripts/seed/audit-untranslated-verses.ts:233-238` (parse-error branch) and `:295` (final gate condition)
**Category:** bug
**Issue:** The cache-side branch of `runVerify` writes `cachePerSlug.set(slug, -1)` on a JSON parse failure but does NOT add to `cacheTotal` (the `continue` short-circuits the `cacheTotal += n` line). The final gate is `if (cacheTotal + dbTotal > 0)` — so a slug whose cache file is corrupt produces stderr noise and a `-1` in the per-slug map, but **the gate still PASSes** if no other stubs are detected. SPEC-REQ-7 demands the gate "exits 1 if any stubs remain in either source" — but the more general intent is "phase complete only when both sources are demonstrably clean." A corrupt file is not demonstrably clean.

**Fix:** Track parse errors as a separate fail signal and include them in the gate.

```ts
// At the top of runVerify():
let cacheParseErrors = 0;

// In the catch block at L233-238:
} catch (err) {
  console.error(`[verify cache] ${slug}: ERROR parsing JSON — ${(err as Error).message}`);
  cachePerSlug.set(slug, -1);
  cacheParseErrors++;
  continue;
}

// Final gate (replace L295-302):
if (cacheTotal + dbTotal > 0 || cacheParseErrors > 0) {
  console.error(
    `[verify] FAIL — cache: ${cacheTotal} stubs (${cacheParseErrors} parse errors), db: ${dbTotal} stubs across ${verifySlugs.length} slug(s)`
  );
  return 1;
}
```

This also makes the failure mode for a corrupt cache symmetric with the existing DB-missing-row case (which currently returns 0 stubs and a `[SKIP]` log — also worth tightening, but lower priority since the rollout flow ensures the row exists).

## Medium

### ME-01: Sidecar fix (commit 1a77cc6) is not covered by any test

**File:** `scripts/seed/apply-verse-patch.test.ts` (whole file — gap is structural, not in any line)
**Category:** test-gap
**Issue:** Commit 1a77cc6 introduced two behaviors that the reviewer's prompt flags explicitly:

1. **Translation-aware idempotency** (`patchSigWithTr` at apply-verse-patch.ts:63-66): the replace-mode signature now includes `translations.en`. Without this, the 14 multi-token `(auto-coverage)` verses on yellow-moon-akeboshi would have been false-skipped as "already applied" because their token surfaces were unchanged.
2. **Cache-side timing preservation** (apply-verse-patch.ts:131-132): when the patch supplies `start_time_ms: 0` / `end_time_ms: 0`, the cached verse's timing is preserved. The Phase 11.3 drafter has no audio access and emits zeros.

Neither behavior is exercised by the existing 6 tests. In particular:
- `makeVerse(n, surface)` uses the surface as the English translation (`translations: { en: surface, ... }`) — so for every test, the surface change AND the translation change happen together. The test cannot distinguish whether the patcher is idempotent on surface alone or on (surface, translation).
- Test 2 (idempotency) writes a patch where the replace verse has `start_time_ms = 0, end_time_ms = 500` against an original with `start_time_ms = 3000`. The merge runs, but the test asserts only `verses.map(v => v.tokens[0].surface)` and the byte-equal re-apply — **not** the resulting `start_time_ms`. If `||` were silently changed to `=` (no fallback), Test 2 would still pass because the byte-equal check covers re-apply of the now-broken state.

The practical risk: a future refactor removes `patchSigWithTr` (or reverts to surface-only), CI passes, and the next batch of stub-translation patches false-skips.

**Fix:** Add two tests:

```ts
// Test: translation-aware idempotency — same tokens, different translations.en should NOT skip
it("treats stub-translation verses as not-yet-applied even when token surfaces match (sidecar 1a77cc6)", () => {
  // Original verse 2 has tokens [B] with translations.en = "B" (clean).
  // Stub case: tokens are the same but the cache has a stub translation.
  // Simulate by writing a lesson where verse 2's translations.en = "(untranslated)".
  writeLesson([
    makeVerse(1, "A"),
    { ...makeVerse(2, "B"), translations: { en: "(untranslated)", "pt-BR": "B", es: "B" } },
    makeVerse(3, "C"),
    makeVerse(4, "D"),
  ]);
  // Patch: replace verse 2 — same tokens, fixed translations.
  writePatch([
    {
      replace_verse_number: 2,
      verse: { ...makeVerse(0, "B"), translations: { en: "B (fixed)", "pt-BR": "B", es: "B" } },
    },
  ]);

  const result = applyPatch(SLUG);
  expect(result.skipped).toBe(0); // would be 1 under surface-only patchSig
  const verses = readLessonVerses();
  expect(verses[1].translations.en).toBe("B (fixed)");
});

// Test: cache-side timing preservation — patch with 0 timing keeps cache timing
it("preserves cache-side start/end timing when patch supplies 0 (sidecar 1a77cc6)", () => {
  // Cache verse 2 has start=2000, end=2500.
  writePatch([
    {
      replace_verse_number: 2,
      verse: { ...makeVerse(0, "REPLACED"), start_time_ms: 0, end_time_ms: 0 },
    },
  ]);

  applyPatch(SLUG);
  const verses = readLessonVerses();
  expect(verses[1].start_time_ms).toBe(2000); // preserved from cache, not overwritten with 0
  expect(verses[1].end_time_ms).toBe(2500);
});
```

Both tests run under the same fixture pattern — synthetic slug, beforeEach/afterEach unchanged.

### ME-02: Replace idempotency can false-skip on a song with a repeated chorus already-correct elsewhere

**File:** `scripts/seed/apply-verse-patch.ts:97-104`
**Category:** bug
**Issue:** The replace-mode idempotency check at L97-104 is `original.some((v) => patchSigWithTr(v) === replSig)` — i.e., "does ANY verse in the original lesson already match this patch's (surface, translations.en) signature?" The reviewer's prompt asks specifically: "are there pathological cases where two different verses have same surface-concat AND same translations.en?"

Yes. Example construction:
- Song has a chorus line `君と` with `translations.en = "with you"` repeated three times (verses 5, 12, 22).
- Verse 5 is a stub (`(untranslated)`). Verses 12 and 22 are clean.
- Drafter produces a patch: `replace_verse_number: 5, verse: { tokens: [君と], translations: { en: "with you", ... } }`.
- The check `original.some((v) => patchSigWithTr(v) === "君と␟with you")` returns TRUE — because verses 12 and 22 already match.
- The patch is filtered out of `replaceMap`. Verse 5 stays a stub. The patcher reports `skipped++` and silently does nothing.

For the actual Phase 11.3 corpus, this risk is low — the drafter generates fresh translations against neighbour-verse context, so byte-matching an existing correct verse is unlikely. But it is non-zero, and any operator running with `--verify` would catch it because the cache-side stub count would not drop to zero. So there is a downstream defense, but the patcher itself can silently no-op when it should not have.

**Fix:** Change the idempotency check to be slot-aware: scan whether the verse at the SAME `replace_verse_number` already matches, instead of scanning the whole lesson. The original comment at L80-93 acknowledges this is harder because mixed apply+append shifts slots — but the slot-aware check only needs to cover the FIRST apply (when verse_number values still align with `replace_verse_number`) plus the post-renumber state. A robust formulation:

```ts
for (const p of patch.patches) {
  if (!("replace_verse_number" in p)) continue;
  const replSig = patchSigWithTr(p.verse);
  // Check 1: does the verse currently AT this verse_number already match? (covers re-apply of pure replace patches and the first half of mixed patches.)
  const verseAtSlot = original.find((v) => v.verse_number === p.replace_verse_number);
  // Check 2: in mixed-mode re-apply, the renumber pass shifts the replaced row. Confirm by scanning forward from the slot for a match (the replaced row is downstream of any prior appends).
  const downstreamMatch = verseAtSlot
    ? original.slice(original.indexOf(verseAtSlot)).some((v) => patchSigWithTr(v) === replSig)
    : false;
  if ((verseAtSlot && patchSigWithTr(verseAtSlot) === replSig) || downstreamMatch) {
    skipped++;
  } else {
    replaceMap.set(p.replace_verse_number, p.verse);
  }
}
```

This narrows the false-skip window from "any verse anywhere" to "the slot or a downstream slot" — which by construction excludes upstream chorus repeats. If the cost of this surgery feels high relative to the actual risk (low for Phase 11.3's drafter), an alternate fix is to add a unique nonce field to the patch entry (e.g. `patch_id: uuid`) and use that as the idempotency key. Either way, the concern should be documented in the existing comment block at L80-93 (the comment claims signature collisions are "vanishingly unlikely" — for songs with repeated choruses that's not strictly true).

If the team's risk tolerance is "downstream `--verify` will catch any mis-skip", the minimum-viable fix is to **upgrade the comment at L80-93** to acknowledge the chorus case explicitly so the next person reading it isn't misled.

### ME-03: `||` fallback for timing makes "patch wants 0" indistinguishable from "patch unset"

**File:** `scripts/seed/apply-verse-patch.ts:131-132`
**Category:** quality (borderline bug for any future drafter that has audio)
**Issue:** Lines 131-132:
```ts
const start_time_ms = replacement.start_time_ms || v.start_time_ms;
const end_time_ms = replacement.end_time_ms || v.end_time_ms;
```

`||` treats `0` as "unset and fall through". The comment at L126-130 explicitly says: "A non-zero patch value still wins (covers the rare case a future patch deliberately sets timing)." So the design intent is "0 means unset; any non-zero means use the patch." That's defensible **today** because the Phase 11.3 drafter has no audio access and emits zero. But:

1. There is no legal `start_time_ms = 0` in clean data either — every cached verse has a non-zero timing — so the practical hazard is small.
2. A hypothetical future drafter that DOES have audio could legitimately want to set `start_time_ms = 0` for the very first verse of a song that starts at t=0. Under the current `||`, that 0 would fall through to the cache, which (if the cache row was stub-form) might also be 0. In that case the behavior is incidentally correct, but if the cache row was non-zero (e.g., a previous bad timing), the patch would silently fail to update.
3. The cleaner formulation matches the comment's intent verbatim: treat 0 as the sentinel for "patch unset", but make that explicit with a guard rather than rely on `||` semantics.

**Fix:**
```ts
const start_time_ms =
  replacement.start_time_ms !== 0 ? replacement.start_time_ms : v.start_time_ms;
const end_time_ms =
  replacement.end_time_ms !== 0 ? replacement.end_time_ms : v.end_time_ms;
```

Or, if the drafter can be persuaded to omit the field entirely instead of emitting 0:
```ts
const start_time_ms = replacement.start_time_ms ?? v.start_time_ms;
const end_time_ms = replacement.end_time_ms ?? v.end_time_ms;
```
Either is more honest about intent than `||`. Pair with the test in ME-01 to lock the behavior.

### LO-03: No try/catch around JSON.parse in `applyPatch`

**File:** `scripts/seed/apply-verse-patch.ts:74-75`
**Category:** quality
**Issue:** A malformed `data/lessons-cache/<slug>.json` or `.planning/verse-patches/<slug>.json` produces an unhandled `SyntaxError` rather than the controlled error path the file already uses for missing files (L71-72). The CLI dispatch catches nothing, so the user sees a stack trace instead of `[error] <slug>: invalid JSON in <path>`. Same pattern as the audit script's L155-158 (which DOES handle this case with a continue + warn).
**Fix:** Wrap each parse in a try/catch and rethrow with file context:
```ts
let lesson, patch;
try { lesson = JSON.parse(readFileSync(lessonPath, "utf-8")); }
catch (err) { throw new Error(`invalid JSON in ${lessonPath}: ${(err as Error).message}`); }
try { patch = JSON.parse(readFileSync(patchPath, "utf-8")) as Patch; }
catch (err) { throw new Error(`invalid JSON in ${patchPath}: ${(err as Error).message}`); }
```

### LO-04: Test-fixture types diverge silently from the live schema

**File:** `scripts/seed/apply-verse-patch.test.ts:37-53`
**Category:** test-gap
**Issue:** `TokenLike` and `VerseLike` are local-only and don't import from `scripts/types/lesson.ts`. PATTERNS.md explicitly notes the schema caveat (no `kanji_breakdown` at the verse-token level), and the test file's L59 comment says "PATTERNS.md beats CONTEXT.md D-05" — so the local types are deliberately the live shape.
