# Phase 18.2: Code Review Report

**Reviewed:** 2026-05-16

## Summary

Phase 18.2 adds five new Playwright E2E specs covering API health (D-05), auth-locale reachability (D-03), i18n nav matrix (D-01), nav sweep (D-02), and the onboarding/terms gate (D-04), plus a middleware API-route passthrough guard (step 4) and a new `test:e2e:qa` script.

The middleware change is structurally sound and correctly addresses the `intlMiddleware` rewriting `/api/*` to `/en/api/*` (which has no route match). The test specs are well-commented and show clear regression intent. No critical security or data-loss issues were found.

Four warnings and three info items are flagged below, covering: a middleware logic ordering gap, a flawed URL assertion in one spec, a missing cookie `secure` flag, a missing response-null guard, and minor test-quality concerns.

## Warnings

### WR-01: Middleware — Terms gate runs on every non-excluded authenticated request, including `_next/image` and other internal paths that match the catch-all but not the `isLegalOrOnboardingRoute` exclusion

**File:** `src/middleware.ts:72-93`

**Issue:** The `isLegalOrOnboardingRoute` exclusion list does not include `/_next/` or `/_vercel/` paths. The top-level `config.matcher` uses the canonical Clerk catch-all `/((?!.+\\.[\\w]+$|_next).*)` which already excludes `_next` paths via the negative lookahead, so in practice this is mitigated — but the exclusion pattern is not self-documenting about that dependency. More concretely, the current pattern also does not exclude `/((?!.+\\.[\\w]+$|_next).*)` from the terms gate, meaning any path that matches the outer matcher but not `isLegalOrOnboardingRoute` (e.g. `/trpc/...`) will call `auth()` in the terms gate path for every authenticated request. This is a latency concern but can also cause unexpected 401 redirection if `/trpc/` routes ever get added — they are not currently excluded.

**Fix:** Extend `isLegalOrOnboardingRoute` to cover `/trpc` and any other known non-page route families:
```typescript
const isLegalOrOnboardingRoute = createRouteMatcher([
  "/legal(.*)",
  "/onboarding(.*)",
  "/sign-in(.*)",
  "/sign-up(.*)",
  "/api(.*)",
  "/trpc(.*)",           // future-proofs against tRPC routes
]);
```
Low urgency since tRPC is not currently used, but worth tracking.

### WR-02: `auth-reachability-locale.spec.ts` — Final URL assertion is too strict and will false-positive on Clerk dev-browser redirect

**File:** `tests/e2e/auth-reachability-locale.spec.ts:55`

**Issue:** Line 55 asserts `toHaveURL('/sign-in', { timeout: 10_000 })` with an exact string match. In Clerk's dev mode, the sign-in page redirects to add `?__clerk_db_jwt=...` query params to the URL. The `toHaveURL` matcher with a plain string performs an exact match in Playwright by default, so the assertion will fail as soon as Clerk appends dev-mode query parameters. The comment on line 9 even describes this exact pattern ("Clerk dev-browser redirect interference") but the assertion does not account for it.

**Fix:** Use a regex or check just the pathname:
```typescript
// Option A — regex (matches with or without query params)
await expect(page).toHaveURL(/\/sign-in/, { timeout: 10_000 });

// Option B — assert pathname only (more precise)
const url = new URL(page.url());
expect(url.pathname).toBe('/sign-in');
```

### WR-03: Cookie setup in specs omits `secure: false` and `httpOnly: false` — may silently fail on some Playwright/browser versions

**File:** `tests/e2e/auth-reachability-locale.spec.ts:29-34`, `tests/e2e/i18n-nav-locale-matrix.spec.ts:53-58`

**Issue:** `context.addCookies` calls set `name`, `value`, `domain`, and `path`, but omit `secure` and `httpOnly`. In Playwright, the default for `secure` when omitted varies by browser context configuration. If the test context defaults to `secure: true` (which applies when `baseURL` uses HTTPS or when a future config change adds `https`), cookies set without `secure: false` will only be sent to HTTPS origins — and the local dev server at `http://localhost:7000` will silently ignore them, making the locale cookie invisible to the middleware. The tests currently pass on HTTP, but the omission is a latency bug waiting to activate on any HTTPS test environment.

**Fix:** Explicitly set the cookie flags to remove ambiguity:
```typescript
await context.addCookies([{
  name: 'kb_locale',
  value: locale,
  domain: 'localhost',
  path: '/',
  secure: false,
  httpOnly: false,
  sameSite: 'Lax',
}]);
```

### WR-04: `nav-sweep-all-locales.spec.ts` — `response` from `page.goto` is not checked for null before accessing `.status()`

**File:** `tests/e2e/nav-sweep-all-locales.spec.ts:44`

**Issue:** `const homeResponse = await page.goto(...)` can return `null` when navigation is blocked (e.g. by a service worker intercept or `waitUntil: 'domcontentloaded'` timing out without a real response). The assertion `homeResponse?.status() ?? 200` silently swallows navigation failures by substituting `200`, so a blocked navigation would pass the `< 500` check and let the test continue — extracting nav links from a potentially empty/error page. The `?? 200` fallback is misleading because a missing `homeResponse` represents a failure, not a success.

**Fix:** Fail explicitly on null response:
```typescript
const homeResponse = await page.goto(localeConfig.homeUrl, { waitUntil: 'domcontentloaded' });
expect(homeResponse, 'home page navigation must not be blocked').not.toBeNull();
expect(homeResponse!.status(), 'home page itself should load').toBeLessThan(500);
```
The same pattern exists in other specs (e2e tests D-01, D-04) but is less risky there because subsequent assertions (URL check, body text) would catch the underlying failure anyway. In `nav-sweep-all-locales` the rest of the test loops over nav links from the loaded DOM, so a silently empty page would make all remaining assertions vacuously pass.

## Info

### IN-01: `test:e2e:qa` script runs all specs with 4 workers — conflicts with per-spec `serial` mode declarations

**File:** `package.json:36`

**Issue:** `"test:e2e:qa": "playwright test --workers=4"` runs all specs, but three of the new specs (`auth-reachability-locale`, `i18n-nav-locale-matrix`, `nav-sweep-all-locales`) use `test.describe.configure({ mode: 'serial' })` precisely to avoid Clerk dev-browser redirect races under parallel load. The `serial` directive serializes tests *within a describe block* but the 4-worker setting still runs *different spec files* in parallel. If any two of these locale-aware specs load the same Clerk dev-browser cookie concurrently across workers, the `ERR_TOO_MANY_REDIRECTS` race they are designed to avoid can still occur at the file-parallelism level.

**Suggestion:** The existing `test:e2e` script (no `--workers` override) already uses Playwright's default (CPU count, capped by `fullyParallel: true`), so `test:e2e:qa` with `--workers=4` is not obviously safer. If the intent is to limit parallelism to avoid Clerk races, consider `--workers=1` for the locale specs or use a project filter that runs the locale specs serially: `playwright test --project=chromium --workers=1 api-health auth-reachability i18n-nav onboarding-terms nav-sweep`.

### IN-02: `onboarding-terms-gate.spec.ts` — Second test clears cookies but first test does not reset browser state

**File:** `tests/e2e/onboarding-terms-gate.spec.ts:41-55`

**Issue:** The second test (`/onboarding/age-gate is not redirected further`) explicitly calls `context.clearCookies()` to remove Clerk dev-browser cookies. The first test in the same describe block does not clear cookies. Since `test.describe` without `serial` mode runs in parallel by default (and these tests share the same describe block without `.configure({ mode: 'serial' })`), the first test may execute in a context that already has Clerk cookies from a previous test. The lack of `test.beforeEach(() => context.clearCookies())` creates asymmetric isolation.

**Suggestion:** Add a `test.beforeEach` to clear cookies, or add `test.describe.configure({ mode: 'serial' })` consistent with the other locale-aware specs in this phase:
```typescript
test.describe('onboarding-terms-gate — D-04', () => {
  test.describe.configure({ mode: 'serial' });
  test.beforeEach(async ({ context }) => { await context.clearCookies(); });
  // ...
```

### IN-03: `api-health.spec.ts` — `birthday-transitions` test uses a loose 4xx assertion with a comment suggesting the expected code is unknown

**File:** `tests/e2e/api-health.spec.ts:42-56`

**Issue:** The comment on line 46 says "NOTE: Assumed same auth pattern as daily-reminder and weekly-recap (verified in cron-auth.spec.ts). If this returns 403 or another 4xx, update the assertion." The test uses `toBeGreaterThanOrEqual(400)` + `toBeLessThan(500)` — an intentionally broad range. This is a conscious tradeoff documented by the author, but it means a `429 Too Many Requests` or `404 Not Found` (route missing entirely) would pass. A 404 would indicate the endpoint does not exist at all, which is worse than a 401. The dual-assertion approach is a good pattern, but the floor is too broad.

**Suggestion:** Tighten the lower bound to reject 404 specifically (which would indicate a missing route, not a security response):
```typescript
expect(res.status(), 'should be a 4xx auth rejection, not 404').not.toBe(404);
expect(res.status(), '...').toBeGreaterThanOrEqual(400);
expect(res.status(), '...').toBeLessThan(500);
```
Or, if the route is confirmed to match other cron endpoints, assert exactly 401.
