## Summary

This phase adds 4–5 targeted Playwright specs to catch the class of bug that hit production:
a locale cookie (`kb_locale=pt-BR`) causing next-intl to redirect `/sign-in` to `/pt-BR/sign-in`,
which returns 404 because Clerk's sign-in page is at root, not under `[locale]/`. The fix is
already in `src/middleware.ts` (the `isAuthRoute` check at step 3 skips intl middleware for
`/sign-in(.*)` and `/sign-up(.*)`). The specs must reproduce the scenario and lock it as a
regression guard.

The existing suite has 67 specs across chromium only (`projects: [{ name: 'chromium' }]`),
with `fullyParallel: true` already set in `playwright.config.ts`. The `workers` key is
**absent** from the config — Playwright defaults to using CPU count when `fullyParallel` is
true. The `test:qa` script requested in D-06 collides with an existing `test:qa` entry in
`package.json` that points to a seed/qa agent script — this must be renamed or the existing
entry preserved and a new name chosen.

Cookie injection via `context.addCookies` is already the established pattern in the codebase
(confirmed in `i18n-language-picker.spec.ts`). The `kb_locale` cookie config in
`src/i18n/routing.ts` uses `name: 'kb_locale'` with a 1-year maxAge — consistent with what
the specs must inject. The `onboarding-terms-gate.spec.ts` spec CAN reuse the
`authenticatedTest` fixture from `tests/support/auth-fixtures.ts`, which requires
`PLAYWRIGHT_AUTH=true KB_E2E_AUTH_BYPASS=<id>` env vars.

**Primary recommendation:** Use `context.addCookies` before `page.goto` for all locale
injection. Import from `@playwright/test` directly (not from `fixtures.ts` — the fixtures
add DB dependencies that locale tests don't need). Follow `cron-auth.spec.ts` pattern for
API health specs using the `request` fixture.

### Pattern 4: Nav Sweep — Status + No-404 Text Assert

```typescript
// Source: Derived from all-pages-revamp.spec.ts pattern (VERIFIED)
import { test, expect } from '@playwright/test';

test('header links reachable with pt-BR cookie', async ({ page, context }) => {
  await context.addCookies([{ name: 'kb_locale', value: 'pt-BR', domain: 'localhost', path: '/' }]);
  const response = await page.goto('/', { waitUntil: 'domcontentloaded' });
  expect(response?.status()).toBeLessThan(500);

  const links = page.getByRole('navigation').getByRole('link');
  const count = await links.count();
  for (let i = 0; i < count; i++) {
    const href = await links.nth(i).getAttribute('href');
    if (!href || href.startsWith('#') || href.startsWith('http')) continue;
    const r = await page.request.get(href);
    expect(r.status(), `${href} should not 500`).toBeLessThan(500);
  }
});
```

### Anti-Patterns to Avoid

- **Using `page.request.get` for pages that require SSR rendering:** `page.request.get` sends an HTTP GET without browser context — it won't catch JS-level 404s, only HTTP status codes. For page-level "page could not be found" text checks, use `page.goto` + `expect(page.locator('body')).not.toContainText('could not be found')`.
- **Clicking nav links in a loop without waiting:** After clicking a link, `page.waitForLoadState` or `page.waitForURL` should be used before asserting — bare clicks can race with navigation.
- **Setting `domain` to `'localhost'` vs `'127.0.0.1'`:** Playwright's `context.addCookies` requires `domain` to match the actual domain the browser uses. Since `baseURL` is `http://localhost:7000`, use `domain: 'localhost'`. [See Pitfall 1 below.]

## Common Pitfalls

### Pitfall 1: `context.addCookies` domain mismatch
**What goes wrong:** Cookie is set with `domain: '127.0.0.1'` but browser navigates to `localhost` (or vice versa). The cookie is not sent and locale is not detected. Test passes vacuously — no locale cookie, no redirect, but also no real coverage.
**Why it happens:** `baseURL` in playwright.config.ts is `http://localhost:7000` — hostname is `localhost`. Cookie domain must match.
**How to avoid:** Always use `domain: 'localhost'` in `addCookies` when baseURL is `http://localhost:7000`. [VERIFIED: baseURL in playwright.config.ts line 47]
**Warning signs:** Test passes even with a wrong locale; `context.cookies()` check after `goto` shows cookie missing.

### Pitfall 2: `test:qa` script name collision
**What goes wrong:** `package.json` already has `"test:qa": "tsx ... scripts/seed/06-qa-agent.ts"` (line 42). Adding another `test:qa` entry would silently overwrite it.
**Why it happens:** D-06 requests `npm run test:qa` pointing to `playwright test --workers=4`, but the name is taken.
**How to avoid:** Either rename the new script (e.g., `test:e2e:qa`) or rename the existing seed script (e.g., `test:qa:content`). The planner must choose and update both references consistently.
**Warning signs:** Running `npm run test:qa` runs the seed agent instead of Playwright, silently.

### Pitfall 3: `workers` key interaction with `fullyParallel: true`
**What goes wrong:** Adding `workers: 4` to playwright.config.ts changes behavior for ALL runs, not just `test:qa`. The dev workflow `npm run test:e2e` then always uses 4 workers.
**Why it happens:** D-06 says "set workers in playwright.config.ts" but also says "do NOT change default `test` script". These can be satisfied two ways: (a) set `workers: 4` in config and accept it applies to all Playwright runs, or (b) only pass `--workers=4` in the script and leave config unchanged.
**How to avoid:** Prefer option (b): leave `playwright.config.ts` `workers` unset (keep CPU-count default), and add `--workers=4` only to the new `test:e2e:qa` script. This keeps the config clean and honors D-06's intent without changing dev behavior.
**Warning signs:** CI runs slower than expected; `npm run test:e2e` uses fewer parallelism options than before.

### Pitfall 4: Terms gate test requires real Clerk auth
**What goes wrong:** The onboarding terms gate reads `session.sessionClaims?.publicMetadata.terms_version` from Clerk's JWT. In the E2E bypass mode, `auth()` in middleware returns the bypass user — BUT the JWT claims won't have `terms_version` unless the bypass is designed to return specific claims.
**Why it happens:** The bypass in `getCurrentUserId()` replaces the user ID, but the terms gate check is in `middleware.ts` using `session.sessionClaims` — a different Clerk auth path. The bypass may not populate JWT claims.
**How to avoid:** The planner must investigate whether the bypass propagates `sessionClaims` to middleware. If not, the `onboarding-terms-gate.spec.ts` spec may need to either (a) be marked `[kb-quarantine]` until a richer bypass exists, or (b) test only the non-authenticated path (anon users pass through) and the loop-prevention behavior.
**Warning signs:** Auth bypass user always passes through the terms gate (because `session.userId` is truthy but `sessionClaims` is undefined, so `termsVersion` is undefined and the gate should redirect — but if it doesn't, the bypass isn't wiring through middleware correctly).

### Pitfall 5: Nav link click from homepage visits redirect targets
**What goes wrong:** With a locale cookie set, clicking "Songs" may redirect to `/pt-BR/songs` (locale prefix added by intl middleware). If the test asserts `URL contains '/songs'` it passes even for the locale-prefixed path. The real assertion should be more specific.
**Why it happens:** `localePrefix: 'as-needed'` in routing config means `en` gets no prefix but `pt-BR` and `es` do. [VERIFIED: src/i18n/routing.ts]
**How to avoid:** For D-01/D-02 locale matrix tests: assert status < 500 and no 404 text, NOT an exact URL match. The goal is reachability, not preventing locale prefixes on non-auth routes.

### Pitfall 6: `all-pages-revamp.spec.ts` already tests `/sign-in` — avoid duplication
**What goes wrong:** The new `auth-reachability-locale.spec.ts` tests the same `/sign-in` route that `all-pages-revamp.spec.ts` line 18 already includes.
**Why it happens:** `staticRoutes` in `all-pages-revamp.spec.ts` includes `/sign-in` and asserts `response.status() < 500`. This is a direct HTTP GET without a locale cookie.
**How to avoid:** The new spec tests a DIFFERENT scenario: navigate to `/`, click the Sign in LINK in the nav, with a locale cookie pre-set, and assert the destination URL. This is fundamentally different (cookie-aware, click-driven, URL assertion) — not a duplicate. Make this distinction explicit in the new spec's describe block comment.

## Open Questions

1. **Does the auth bypass propagate `sessionClaims` to middleware?**
   - What we know: `playwright.config.ts` injects `KB_E2E_AUTH_BYPASS_ENABLED=true` and `KB_E2E_AUTH_BYPASS=test-user-1` into the Next.js server. `getCurrentUserId()` in `lib/user-prefs.ts` returns the bypass id. But the terms gate in `middleware.ts` reads `session.sessionClaims?.publicMetadata.terms_version` from `clerkMiddleware`'s `auth()` object.
   - What's unclear: Does the Clerk middleware's `auth()` also bypass, or does it only bypass at the `getCurrentUserId()` layer? If `session.userId` is null in middleware even with bypass, the terms gate skips (anonymous path) — which would make the terms-redirect test vacuously pass.
   - Recommendation: Before writing `onboarding-terms-gate.spec.ts`, verify by adding a `console.log(session.userId)` in middleware temporarily and running the auth bypass. If `session.userId` is always null in middleware bypass mode, the spec must test only the anonymous and loop-prevention cases.

2. **`test:qa` script name collision — which script to rename?**
   - What we know: `package.json` line 42 has `"test:qa": "tsx ... 06-qa-agent.ts"`. D-06 requests `npm run test:qa` for Playwright.
   - What's unclear: Whether renaming the seed script would break any CI references.
   - Recommendation: Name the new Playwright script `test:e2e:qa` (consistent with existing `test:e2e` naming). Leave seed script as `test:qa` to avoid breaking CI.
