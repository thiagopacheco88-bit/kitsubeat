## Summary

KitsuBeat has zero i18n infrastructure today — no next-intl, no translation files, no locale routing. This phase adds it from scratch using next-intl 4.12.0 (verified current on npm registry). The core architectural move is wrapping all existing app routes under a `src/app/[locale]/` dynamic segment using `localePrefix: 'as-needed'`, which keeps English at `/` (canonical URLs untouched) while adding `/pt-BR/` and `/es/` prefixes for the two new locales.

The most complex integration point is the existing `src/middleware.ts`, which already runs Clerk admin gating and a terms-version re-acceptance check. next-intl must be composed inside `clerkMiddleware()`, not replacing it. The verified pattern is: `clerkMiddleware(async (auth, req) => { ... existing checks ...; return intlMiddleware(req); })`. This preserves the existing auth logic while adding locale routing.

The song language filter and journal article localization are largely independent of the routing infrastructure — the filter wires the existing `songs.language` DB column (hardcoded to `'ja'` in 10 places in `queries.ts` that need parameterization), and the journal articles are new MDX files in locale subfolders with `articles.ts` extended to read them.

**Primary recommendation:** Install `next-intl@4.12.0`, scaffold `src/i18n/routing.ts`, `src/i18n/request.ts`, `src/i18n/navigation.ts`, move `src/app/layout.tsx` into `src/app/[locale]/layout.tsx`, chain middleware inside `clerkMiddleware()`, scaffold all 6 translation namespaces for EN/PT-BR/ES, then extract strings and translate journal articles as parallel work streams.

### Pattern 1: defineRouting with as-needed prefix

**What:** Central routing config. `localePrefix: 'as-needed'` means English has no prefix (canonical URLs preserved), PT-BR and ES get prefixes.

**When to use:** Always — this is the single source of truth for locales.

```typescript
// src/i18n/routing.ts
// Source: Context7 /amannn/next-intl
import { defineRouting } from 'next-intl/routing';

export const routing = defineRouting({
  locales: ['en', 'pt-BR', 'es'],
  defaultLocale: 'en',
  localePrefix: 'as-needed',
  localeCookie: {
    name: 'kb_locale',       // Match existing kb_* cookie naming convention
    maxAge: 60 * 60 * 24 * 365  // 1 year
  },
});
```

### Pattern 2: Chaining with existing clerkMiddleware

**What:** next-intl runs inside clerkMiddleware, not replacing it. Existing admin gate and terms-version gate are preserved.

**When to use:** Required — the existing middleware has critical auth checks that must stay.

**Critical insight:** The `intlMiddleware` must be called at the END of the clerkMiddleware callback as a return value, so Clerk runs its checks first. The existing middleware already reads `session.sessionClaims?.publicMetadata` for terms version — the same pattern works for locale.

```typescript
// src/middleware.ts — revised structure
import { clerkMiddleware, createRouteMatcher, clerkClient } from "@clerk/nextjs/server";
import createIntlMiddleware from 'next-intl/middleware';
import { NextResponse } from "next/server";
import { routing } from '@/i18n/routing';

const intlMiddleware = createIntlMiddleware(routing);

const isAdminRoute = createRouteMatcher(["/admin(.*)", "/api/admin(.*)"]);
const isLegalOrOnboardingRoute = createRouteMatcher([...]);

export default clerkMiddleware(async (auth, req) => {
  // 1. Admin gate — existing logic, unchanged
  if (isAdminRoute(req)) {
    // ... existing admin check ...
  }

  // 2. Terms version gate — existing logic, unchanged
  if (!isLegalOrOnboardingRoute(req)) {
    // ... existing terms check ...
  }

  // 3. Locale routing — NEW: runs last, handles all non-admin routes
  return intlMiddleware(req);
});

export const config = {
  matcher: [
    "/((?!.+\\.[\\w]+$|_next).*)",
    "/",
    "/(api|trpc)(.*)",
  ],
};
```

[VERIFIED: Clerk docs + Context7 next-intl composition pattern + existing middleware structure in codebase]

**Key pitfall:** The existing matcher `"/((?!.+\\.[\\w]+$|_next).*)"` already covers locale-prefixed paths. No matcher change needed. `intlMiddleware` internally handles `/pt-BR/*` and `/es/*` via the `localePrefix: 'as-needed'` config.

### Pattern 3: Locale-aware root layout

**What:** `src/app/[locale]/layout.tsx` receives locale as a param, validates it, sets it for static rendering, wraps in `NextIntlClientProvider`.

```typescript
// src/app/[locale]/layout.tsx
// Source: Context7 /amannn/next-intl — LocaleLayout setup
import { NextIntlClientProvider, hasLocale } from 'next-intl';
import { setRequestLocale } from 'next-intl/server';
import { notFound } from 'next/navigation';
import { routing } from '@/i18n/routing';

export function generateStaticParams() {
  return routing.locales.map((locale) => ({ locale }));
}

export default async function LocaleLayout({
  children,
  params,
}: {
  children: React.ReactNode;
  params: Promise<{ locale: string }>;
}) {
  const { locale } = await params;
  if (!hasLocale(routing.locales, locale)) notFound();

  // Required for static rendering — must be before any next-intl hooks
  setRequestLocale(locale);

  // ... existing Clerk auth, theme cookie reads, gamification state fetch ...

  return (
    <ClerkProvider>
      <html lang={locale} className={inter.variable} data-theme={initialTheme}>
        {/* ... existing head content ... */}
        <body>
          <NextIntlClientProvider>
            {children}
          </NextIntlClientProvider>
        </body>
      </html>
    </ClerkProvider>
  );
}
```

[VERIFIED: Context7 /amannn/next-intl — setRequestLocale, hasLocale, generateStaticParams patterns]

**Key pitfall:** `setRequestLocale(locale)` MUST be called before any `getTranslations()` or `useTranslations()` in Server Components. Without it, static rendering falls back to dynamic rendering.

### Pattern 5: Locale-aware navigation (LanguagePicker)

**What:** Switching locales from a client component uses next-intl's `useRouter` to replace the current pathname with the new locale.

```typescript
// src/components/ui/LanguagePicker.tsx  (client component)
'use client';
import { useRouter, usePathname } from '@/i18n/navigation';

export function LanguagePicker({ currentLocale }: { currentLocale: string }) {
  const router = useRouter();
  const pathname = usePathname();

  function switchLocale(newLocale: string) {
    router.replace(pathname, { locale: newLocale });
  }
  // Globe SVG button + dropdown renders here
}
```

**CRITICAL note on cookie:** `router.replace(pathname, { locale })` triggers the next-intl middleware on the next request, which automatically sets the `kb_locale` cookie (our custom `localeCookie.name`). No manual `document.cookie` write needed in the LanguagePicker — the middleware handles it. [VERIFIED: Context7 — localeCookie docs]

### Pattern 6: Clerk publicMetadata locale sync (Server Action)

**What:** When an authenticated user switches locale, a Server Action updates Clerk `publicMetadata.locale`.

```typescript
// src/app/actions/locale.ts  (Server Action)
'use server';
import { auth } from '@clerk/nextjs/server';
import { clerkClient } from '@clerk/nextjs/server';

export async function syncLocaleToClerk(locale: string) {
  const { userId } = await auth();
  if (!userId) return;  // Unauthed — cookie is sufficient
  const client = await clerkClient();
  await client.users.updateUser(userId, {
    publicMetadata: { locale },
  });
}
```

**LanguagePicker calls `syncLocaleToClerk` fire-and-forget after `router.replace`:**
- If Clerk sync fails → fail silently (cookie still drives routing)
- UI-SPEC confirmed: "fail silently — cookie drives routing, Clerk sync is a background enhancement"

### Anti-Patterns to Avoid

- **Moving admin routes under [locale]:** Admin routes (`/admin/*`) must stay at the app root, not inside `[locale]`. They do not need locale routing. Moving them would break the existing admin gate and require locale params on all admin pages.
- **Calling setRequestLocale without locale validation:** Always validate with `hasLocale()` before calling `setRequestLocale`. An invalid locale crashes the request.
- **Manual cookie writes in LanguagePicker:** next-intl middleware manages the locale cookie automatically. Do not write `document.cookie` manually — it creates two competing locale signals.
- **Replacing clerkMiddleware with intlMiddleware:** next-intl middleware must be called FROM INSIDE `clerkMiddleware()`, not alongside it. The existing terms-version and admin checks depend on `clerkMiddleware()` wrapping.
- **Running getTranslations before setRequestLocale:** In page-level Server Components (inside `[locale]`), always call `setRequestLocale(locale)` before any `getTranslations()` to enable static rendering.
- **Flat message files with deeply nested namespaces:** Keep top-level keys as namespace names (`common`, `songs`, etc.); avoid triple-nesting like `common.nav.links.songs` — use `common.nav.songs` instead.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Locale detection from Accept-Language | Custom header parsing middleware | next-intl middleware built-in | next-intl already handles priority: prefix → cookie → Accept-Language → defaultLocale |
| hreflang link generation | Manual link header construction | next-intl middleware auto-generates | next-intl emits correct `link: <url>; rel="alternate"; hreflang="..."` headers on every response automatically |
| Locale-aware Link/useRouter | Wrapper around Next.js Link with locale prefix injection | `createNavigation(routing)` from next-intl | Handles `localePrefix: 'as-needed'` transparently — no manual prefix logic |
| Translation loading/caching | Custom JSON loader | `getRequestConfig` + dynamic `import()` | React `cache()` is used internally; per-request memoization is built-in |
| RTL text direction detection | Language-to-direction map | next-intl `useTextDirection()` | Built-in (though not needed for PT-BR/ES — both are LTR) |

**Key insight:** next-intl handles the full i18n lifecycle (detection → routing → translation → SEO headers). The only custom code needed is: routing config, message loading config, navigation export, and UI components that consume `useTranslations`.

## Common Pitfalls

### Pitfall 1: [locale] folder conflicts with /admin and /api routes

**What goes wrong:** Moving ALL routes under `[locale]` would capture `/admin/lyrics` as `[locale]=admin` and `pathname=lyrics`, routing it to a translated layout that expects `hasLocale('admin')` to pass — which fails with `notFound()`.
**Why it happens:** Next.js [locale] is a catch-all dynamic segment.
**How to avoid:** Keep `/admin/*` and `/api/*` at the app root (outside `src/app/[locale]/`). The next-intl middleware's `localePrefix: 'as-needed'` only rewrites paths it recognizes as locale-prefixed (`/pt-BR/`, `/es/`). Admin routes are never prefixed.
**Warning signs:** 404s on admin routes after adding [locale] segment. Check `not-found.tsx` is present inside `[locale]` to catch bad locale segments.

### Pitfall 2: Locale cookie name collision with existing kb_* cookies

**What goes wrong:** next-intl's default cookie name is `NEXT_LOCALE`. If the project later reads locale from a cookie named differently in non-middleware code, cookie name mismatch causes split-brain locale state.
**Why it happens:** Default name ≠ project naming convention.
**How to avoid:** Set `localeCookie: { name: 'kb_locale' }` in `defineRouting`. This aligns with the project's existing `kb_theme`, `kb_consent`, `kb_terms_done` naming.
**Warning signs:** Locale switching works in middleware but locale-aware client components show wrong locale.

### Pitfall 3: setRequestLocale not called in page-level Server Components

**What goes wrong:** Pages render dynamically instead of statically, degrading performance. In dev mode this is silent; in production, ISR/static generation breaks.
**Why it happens:** next-intl needs explicit `setRequestLocale(locale)` in every page/layout to opt into static rendering.
**How to avoid:** Add `setRequestLocale(locale)` as the FIRST thing in every page Server Component after extracting `locale` from `params`.
**Warning signs:** `next build` output shows all locale pages as dynamic (λ) instead of static (○).

### Pitfall 4: getAllSongs language filter breaks home page carousels

**What goes wrong:** Other queries in `queries.ts` that hardcode `language = 'ja'` are correctly filtering to Japanese songs only. Accidentally removing those filters would show EN/PT/ES songs in carousels that are explicitly about Japanese content.
**Why it happens:** There are 10 occurrences of `language = 'ja'` in queries.ts — only the `getAllSongs` function at line 142 needs a filter param. The other 9 are correct as-is.
**How to avoid:** Only modify `getAllSongs`. Add `language` to its SELECT clause and add an optional WHERE param. Leave all other query functions untouched.
**Warning signs:** Home page carousels showing non-Japanese songs.

### Pitfall 5: Journal article slug collision across locales

**What goes wrong:** `getArticleSource(slug)` reads from `CONTENT_DIR` (EN root). If a PT-BR article at `src/content/journal/pt-BR/gurenge-demon-slayer-japanese-lesson.mdx` uses the same slug as the EN version, and `getArticleSource` is called with just the slug on the PT-BR route, it returns the EN file.
**Why it happens:** `articles.ts` currently has no locale awareness in `getArticleSource`.
**How to avoid:** Create `getArticleSourceByLocale(slug, locale)` that reads from the locale subdir. The journal `[slug]/page.tsx` inside `[locale]` receives both `slug` and `locale` params.
**Warning signs:** PT-BR article URLs render EN content.

### Pitfall 6: Vercel file tracing misses locale message JSON files

**What goes wrong:** `getRequestConfig` does dynamic `import()` of `messages/pt-BR/*.json`. Vercel's file tracer may not detect these dynamic imports, causing 500s in production.
**Why it happens:** Dynamic imports with template literals are harder for static analysis to trace.
**How to avoid:** Add to `next.config.ts` `outputFileTracingIncludes`:
```typescript
outputFileTracingIncludes: {
  "/**": ["./src/messages/**/*.json"],
  "/admin/journal": ["./src/content/journal/**/*.mdx"],
  // ... existing ...
}
```
**Warning signs:** Works in `next dev`, crashes in `next build` / Vercel prod.

### Pitfall 7: next-intl middleware runs BEFORE Clerk session is established on first load

**What goes wrong:** On the very first request to `/pt-BR/songs` with no cookie, next-intl redirects to set locale, Clerk session hasn't been fully established, and the terms-version gate misfires.
**Why it happens:** Middleware order matters. The terms gate checks `session.userId` — if `intlMiddleware` redirects before Clerk processes auth, the terms check fires on the redirect target instead of the original.
**How to avoid:** `intlMiddleware(req)` is called as the RETURN VALUE of `clerkMiddleware()` callback — Clerk runs first, then next-intl. This is the verified composition order (Pattern 2 above).
**Warning signs:** Authenticated users get redirected to `/onboarding/age-gate` spuriously on locale-switch.

### Pitfall 8: Locale prefix in canonical URL metadata

**What goes wrong:** Page-level `metadata.alternates.canonical` in `songs/page.tsx` is hardcoded to `${SITE_URL}/songs` (no locale prefix). After wrapping in `[locale]`, canonical for PT-BR should be `${SITE_URL}/pt-BR/songs`.
**Why it happens:** All existing pages have hardcoded canonical URLs.
**How to avoid:** Pass `locale` param to `generateMetadata`. Use next-intl's `getPathname({locale, href: '/songs'})` to generate locale-aware canonical URLs.
**Warning signs:** Google Search Console reports canonical mismatch for PT-BR/ES pages.

   - What we know: `clerkClient().users.updateUser(userId, { publicMetadata: { locale } })` call is established in codebase pattern
   - What's unclear: Does Clerk merge publicMetadata keys or replace the entire object? Existing middleware reads `terms_version` from publicMetadata — if locale sync wipes it, terms gate breaks.
