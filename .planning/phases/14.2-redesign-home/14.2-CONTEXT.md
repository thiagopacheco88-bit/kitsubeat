### Continue Learning Data Shape (Requirement 4)

- **D-01 — Filter: `completion_pct > 0`.** New `getContinueLearning(userId, limit = 3)` query in [`src/lib/db/queries.ts`](../../../src/lib/db/queries.ts) WHERE clause uses single-column `completion_pct > 0` filter on [`user_song_progress`](../../../src/lib/db/schema.ts). This is set whenever any exercise group is attempted (per `saveSessionResults` write path) — cleanest expression of "the user has engaged with this lesson." SPEC §Req 4 references `avg_track_pct > 0 OR any ex*_best_accuracy IS NOT NULL`, which is the same intent expressed across multiple columns. **Schema reality:** `avg_track_pct` is NOT a real column — schema has `completion_pct` (real, 0.0–1.0), `vocab_track_pct` / `grammar_track_pct` / `kanji_track_pct` (numeric 0–100), and `ex1_2_3_best_accuracy` through `ex7_best_accuracy` (real, nullable). Reject 3-column OR (verbose, no semantic gain over `completion_pct`). Reject `ex*_best_accuracy NOT NULL` (false positives — first-attempt failures with no track movement still surface).

- **D-02 — Progress bar fill source: `completion_pct * 100`, clamped 1%–100%.** ContinueCard's 3px `var(--color-accent)` progress bar reads `Math.max(1, Math.min(100, completion_pct * 100))`. Floor at 1% so a row with 0.005 still renders a visible bar (otherwise the bar reads as "no progress" and contradicts the card's mere presence). Reject SQL avg-of-3-tracks `(COALESCE(vocab_track_pct,0) + COALESCE(grammar_track_pct,0) + COALESCE(kanji_track_pct,0)) / 3.0` (right metric for the Star 3 unlock gate per Phase 11.6, wrong metric for "where am I in this lesson"). Reject single-track choice (arbitrary which track represents lesson-progress).

- **D-03 — Returned shape: `{slug, title, artist, anime, youtube_id, jlpt_level, completion_pct, updated_at}`. Sort `updated_at DESC`, default limit = 3.** Mirrors `getFeaturedSongs` shape so a future shared CardLink could consume both. `youtube_id` resolved via the same correlated subquery `getFeaturedSongs` uses (TV version preferred, ELSE first). `jlpt_level` carried for parity (ContinueCard does not currently render it, but the field is cheap and preempts a re-fetch if a future iteration adds the chip). Plan-phase: verify the JOIN against `song_versions` resolves to the song version the user actually progressed through (since `user_song_progress.song_version_id` is keyed by version, not song) — safest behavior is "show the song the user progressed through, link to its slug."

### Hero Data Path + Fallback (Requirement 3)

- **D-04 — New `getHeroSong(userId | null)` query encapsulates auth-aware resolution + fallback.** Returns `{ song: HeroSongRow, ctaLabel: 'Resume Lesson' | 'Try Free Lesson' | 'Start Learning', ctaHref: string, source: 'current_path' | 'fallback_featured' | 'unauth_featured' }`. Logic:
  - If `userId` is null → fetch top `getFeaturedSongs(1)`, ctaLabel = `'Try Free Lesson'`, source = `unauth_featured`.
  - If `userId` set → read `state.current_path_node_slug` from gamification state. If slug resolves to a renderable song row (active, has lesson, not delisted), ctaLabel = `'Resume Lesson'`, source = `current_path`. If slug is null OR the resolved row is missing/delisted, fall through to top `getFeaturedSongs(1)`, ctaLabel = `'Start Learning'`, source = `fallback_featured`, AND emit `console.warn` per D-06 (only when slug WAS set but didn't resolve — null slug is expected first-visit state, no warn).

  This mirrors 14.1 [`getStarterSongs()`](../../../src/lib/gamification/starter-songs.ts) D-01 filter+warn pattern. `page.tsx` becomes thin orchestration (`const hero = await getHeroSong(userId)`). Reject page.tsx-level fallback orchestration (duplicates fallback across auth/anon render branches; risk of divergence on console.warn signal). Reject extending `getUserGamificationState` (state is reused on `/path` and `/profile`; bloating it with a song row makes it heavier for callers that don't need it).

- **D-05 — verseCount source: `jsonb_array_length(sv.lesson->'verses')` subquery inside `getHeroSong`.** `song_versions.lesson` JSONB is the canonical lesson shape (already used everywhere in the lesson runtime). Default to 0 when `lesson IS NULL` (the meta line skips that segment gracefully — render as `{artist} · {anime}` without the verses suffix when count is 0). Reject a separate `verses` table count (no such table exists for served lessons; verses live in the JSONB). Reject dropping verseCount from the meta line (loses a SPEC-contracted signal). Plan-phase: confirm the JSONB shape is exactly `{ verses: [...] }` (verify against `src/lib/types/lesson.ts`); if the path differs, adjust the JSONB selector accordingly.

- **D-06 — console.warn signal style — match 14.1 D-01.** When `current_path_node_slug` IS set but doesn't resolve to a renderable song row: `[hero-song] {slug} (current_path_node_slug) missing or lessonless — falling back to top featured`. When `current_path_node_slug` IS NULL on an auth user: NO warn (expected state for users who haven't picked their starter; the catalog discovery path is intentional). When the unauth fallback is triggered: NO warn (this is the normal anonymous flow, not an error). Plan-phase: verify whether the codebase has a structured logger (Pino / Winston) or `console.warn` is convention — same Claude's-Discretion item as 14.1's `getStarterSongs` warn-log mechanism.

- **`getContinueLearning` SQL sketch (verify against drizzle in plan-phase):**
  ```sql
  SELECT s.slug, s.title, s.artist, s.anime, s.jlpt_level,
         (SELECT youtube_id FROM song_versions sv WHERE sv.song_id = s.id AND sv.youtube_id IS NOT NULL ORDER BY CASE sv.version_type WHEN 'tv' THEN 0 ELSE 1 END LIMIT 1) AS youtube_id,
         usp.completion_pct, usp.updated_at
  FROM user_song_progress usp
  JOIN song_versions sv ON sv.id = usp.song_version_id
  JOIN songs s ON s.id = sv.song_id
  WHERE usp.user_id = $1 AND usp.completion_pct > 0
    AND s.language = 'ja' AND s.quality_status = 'active'
  ORDER BY usp.updated_at DESC
  LIMIT $2
  ```
