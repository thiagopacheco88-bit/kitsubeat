## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| process.env.KB_E2E_AUTH_BYPASS -> getCurrentUserId | Source is the OS environment; trust depends entirely on the operator NOT setting it in production. The double-gate (NODE_ENV check + explicit ENABLED flag) is the mitigation. |
| playwright.config.ts webServer.env -> Next.js dev server | Test-only injection; Playwright runs the dev server as a child process. The env propagation only happens when PLAYWRIGHT_AUTH=true at the Playwright invocation. |
| getCurrentUserId bypass return value -> downstream queries | The returned id is a STRING used identically to a real Clerk user id. Drizzle queries bind it parameterized — no injection surface. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-14.2-01b-01 | Elevation of Privilege | Production deploy with KB_E2E_AUTH_BYPASS_ENABLED=true accidentally set | mitigate | Triple-gated: (a) NODE_ENV !== 'production' check is the strongest barrier (production deploys set NODE_ENV=production via Next.js runtime); (b) explicit per-CI-run env opt-in (NEVER set in any deploy pipeline); (c) console.warn on every call surfaces noise in any monitoring. .env.example does NOT document the vars (intentional — must be explicit per-CI-run). |
| T-14.2-01b-02 | Information Disclosure | Bypass user id leaks via DOM / logs | accept | The bypass id is a TEST user id (e.g., 'test-user-1'); not real PII. Logs intentionally warn on every call. |
| T-14.2-01b-03 | Tampering | Attacker sets KB_E2E_AUTH_BYPASS in their browser | mitigate | The env var is read SERVER-SIDE only (process.env in Node.js). Browser-side process.env is undefined. Client cannot influence the bypass. |
