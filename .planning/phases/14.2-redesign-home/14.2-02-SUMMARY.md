# Phase 14.2 Plan 02: getContinueLearning Integration Test + Implementation Summary

**One-liner:** `getContinueLearning(userId, limit=3)` TDD — 5-case integration test (RED) then 3-table JOIN query with read-time `deriveStars` derivation (GREEN).

## Function Signature

```typescript

  userId: string,

  slug: string;
```

## 5 Test Cases

1. **Test 1 (filter D-01):** Seeds completion_pct=0 and 0.33; asserts only 1 row returned (the >0 one).
2. **Test 2 (ordering D-02):** Seeds 2 rows 1 hour apart at pct=0.5; asserts newer row is first.
3. **Test 3 (limit D-03):** Seeds 5 rows; asserts default=3, explicit=5, explicit=1 all respected.
4. **Test 4 (shape D-03 + D-14):** Single seeded row; asserts exactly 9 keys: `anime, artist, completion_pct, jlpt_level, slug, stars, title, updated_at, youtube_id`.
5. **Test 5 (stars D-14):** Seeds rows A/B/C with ex1_2_3=0.85/0/0.85, ex4=0.85/0/null, ex6=0.85/0/null; asserts at least one stars=3 and one stars=0; validates tautological invariant via same `deriveStars()` call.

## Drizzle Quirk Discovered

The `completion_pct > 0` filter uses `sql` template literal (`sql\`${userSongProgress.completion_pct} > 0\``) rather than `gt(userSongProgress.completion_pct, 0)` — following the plan's guidance for real-typed comparisons with the Neon HTTP driver. The `desc` import was missing from drizzle-orm imports in queries.ts (existing code used raw `sql` strings for DESC ordering); added `desc` to support `desc(userSongProgress.updated_at)`.

## deriveStars Single Source of Truth Confirmed

`getContinueLearning` calls the SAME `deriveStars` helper from `src/lib/db/schema.ts` that `getAllSongs` uses (queries.ts line ~666) and that `SongCard.tsx` renders. No new mastery threshold formula was invented. The accuracy columns (`ex1_2_3_best_accuracy`, `ex4_best_accuracy`, `ex6_best_accuracy`, `grammar_best_accuracy`) are read directly from the joined `user_song_progress` row. The `has_grammar` EXISTS subquery mirrors the shape in `getAllSongs` (queries.ts line ~208). The raw accuracy columns are stripped from the returned shape in the post-query `.map()` — only `stars: 0|1|2|3` is exposed.
