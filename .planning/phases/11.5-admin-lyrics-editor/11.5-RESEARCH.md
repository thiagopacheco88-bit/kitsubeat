# Phase 11.5: Admin Lyrics Editor — Research

**Researched:** 2026-05-01
**Domain:** Admin tooling — auth gating, versioned JSONB editing, subprocess-driven AI fill, atomic publish under neon-http, kuromoji re-tokenization in Next.js server actions
**Confidence:** HIGH on stack decisions; MEDIUM on subprocess pattern (no precedent in repo); LOW on `claude --print` JSON contract (must be smoke-tested before plan execution)

## Summary

Phase 11.5 is a localhost-only admin tool that grafts onto an otherwise unauthenticated Next.js 15 + drizzle/neon-http codebase. Every locked decision in CONTEXT.md (D-01 .. D-22) was verified against current source: nothing in `src/middleware.ts`, no `@clerk/nextjs` installed, `scripts/lib/kuroshiro-tokenizer.ts` is plain ESM importable from server code, and the public song page reads `song_versions.lesson` jsonb directly — confirming D-15's two-write strategy is the only safe path forward. Drizzle migration `0015` is the next free slot. Existing migrations are hand-written `IF NOT EXISTS` ALTERs (Phase 11.4 precedent), not drizzle-kit-generated, so 0015 will follow the same convention.

**The single biggest risk is structural, not nominal:** the project uses `drizzle-orm/neon-http`, which has **no callback transaction support** — confirmed by both an in-source comment (`src/lib/db/queries.ts:804`) and direct inspection of `src/lib/db/index.ts`. D-15's "single transaction for insert + update + lesson rewrite" cannot use `db.transaction(async tx => ...)`. The Neon HTTP driver does support **non-interactive batched transactions** via `sql.transaction([...queries])` (an array of pre-built queries executed atomically in one HTTP round-trip), and that is the pattern the publish action MUST use. Section 7 below has the concrete shape.

**Primary recommendation:** Lock `@clerk/nextjs@^7.2.9` (stable, Next 15.5 compat verified), use `sql.transaction([...])` for the publish flow (NOT `db.transaction`), spawn `claude --print --output-format=json` from server actions via `node:child_process.spawn` with stdin-piped prompt, and parameterize the kuromoji dict path so the existing tokenizer can be reused unchanged from `src/app/admin/lyrics/.../actions.ts`. Smoke-test the `claude --print` JSON output as the very first executable task — if the CLI's headless mode auth-prompts or outputs ANSI noise, the AI-fill path collapses and we need a fallback.

## Claude CLI Headless Mode

**Status:** [VERIFIED via web search 2026-05-01] [LOW confidence on local install — CLI is NOT present on this researcher's PATH; smoke test must run on Thiago's machine before AI-fill plan executes]

### Confirmed flag syntax (current as of 2026-02 docs)

The Claude Code CLI's headless flag is `-p` or `--print`. The non-interactive call shape:

```bash
claude --print --output-format=json "your prompt here"
# OR pipe prompt via stdin:
echo "your prompt here" | claude --print --output-format=json
```

`--output-format` accepts `text` (default), `json`, or `stream-json`.

### JSON output contract

When `--output-format=json` is set, stdout is a single JSON object:

```json
{
  "type": "result",
  "subtype": "success",
  "result": "<the model's textual response>",
  "session_id": "...",
  "total_cost_usd": 0,
  "usage": {
    "input_tokens": N,
    "output_tokens": N,
    "cache_read_input_tokens": N
  }
}
```

The verse JSON the model emits will live inside the `.result` string — that string still needs to be JSON-parsed (mirror of how `03b-generate-content-sequential.ts` strips ```json fences before `JSON.parse`).

[CITED: code.claude.com/docs/en/headless — see Sources]

### Known issue (flag at plan time)

A reported bug (anthropics/claude-code#25629, Feb 2026) shows the CLI hanging after emitting the final `result` event in `stream-json` mode and never exiting cleanly. **Mitigation:** use `--output-format=json` (not `stream-json`) and set a hard timeout in the spawn wrapper (suggested: 180s). If the CLI exits with non-zero or never emits a parseable JSON, the wrapper throws and the editor surfaces the error inline (D-08 spinner → error toast).

[CITED: github.com/anthropics/claude-code/issues/25629]

### MANDATORY first executable task

Before any AI-fill code is written, run on Thiago's machine:

```bash
echo 'Reply with the JSON object {"ok": true} and absolutely nothing else.' | \
  claude --print --output-format=json --max-turns 1 2>&1
```

Verify:
1. Exit code 0
2. stdout is a parseable JSON object with `.type === "result"`, `.subtype === "success"`
3. `.result` contains parseable JSON `{"ok": true}` (model may wrap in code fences — strip first)
4. No interactive prompt appears (auth, MCP server consent, etc.)
5. Process exits within ~5 seconds (no hang)

If any of (1)-(5) fails, the AI-fill path **cannot ship as designed.** Plan must add a contingency task: "Fix Claude CLI headless mode" or "Fall back to manual lesson regeneration."

### Auth-prompt risk

Claude CLI authenticated via Max 20x plan stores credentials in `~/.claude/` (or `%USERPROFILE%\.claude\` on Windows). If the credential expires mid-session, the CLI may emit a re-auth URL on stderr. The spawn wrapper MUST capture stderr and surface "Claude CLI auth expired — run `claude login`" inline rather than hanging. ## Schema Migration 0015 Shape

**File:** `drizzle/0015_admin_lyrics_editor.sql`
**Convention:** Hand-written, single file, all `IF NOT EXISTS` guarded (mirrors `0013_dual_source_lyrics.sql` + `0014_vocab_image_url.sql`). NOT generated by `drizzle-kit generate` — Phase 11.4 noted that `db:generate` would pollute the file with `songs.popularity_rank` schema drift.

```sql
-- drizzle/0015_admin_lyrics_editor.sql
-- Phase 11.5: Admin Lyrics Editor — versioned lyrics, drafts, video swap audit,
-- pipeline + quality status columns.
--
-- Idempotent: safe to re-apply. All ALTERs use IF NOT EXISTS / IF EXISTS guards.

-- ============================================================================
-- 1. Enums
-- ============================================================================

DO $$ BEGIN
  CREATE TYPE "lyrics_version_source" AS ENUM ('auto','ai-assist','human','regen');
EXCEPTION WHEN duplicate_object THEN NULL; END $$;

DO $$ BEGIN
  CREATE TYPE "pipeline_status" AS ENUM ('idle','rerun_in_progress','rerun_failed');
EXCEPTION WHEN duplicate_object THEN NULL; END $$;

DO $$ BEGIN
  CREATE TYPE "quality_status" AS ENUM ('active','flagged_wrong_song','flagged_unfixable');
EXCEPTION WHEN duplicate_object THEN NULL; END $$;

-- ============================================================================
-- 2. lyrics_versions — indefinite-retention version history
-- ============================================================================

CREATE TABLE IF NOT EXISTS "lyrics_versions" (
  "id"                  uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  "song_version_id"     uuid NOT NULL REFERENCES "song_versions"("id") ON DELETE NO ACTION,
  "version_number"      integer NOT NULL,
  "source"              "lyrics_version_source" NOT NULL,
  "editor_id"           text NULL,                  -- Clerk user_id; null when source='auto'
  "verses"              jsonb NOT NULL,
  "parent_version_id"   uuid NULL REFERENCES "lyrics_versions"("id") ON DELETE NO ACTION,
  "created_at"          timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT "lyrics_versions_song_version_id_version_number_unique"
    UNIQUE ("song_version_id", "version_number")
);

CREATE INDEX IF NOT EXISTS "lyrics_versions_song_version_id_created_at_idx"
  ON "lyrics_versions" ("song_version_id", "created_at" DESC);

CREATE INDEX IF NOT EXISTS "lyrics_versions_song_version_id_source_idx"
  ON "lyrics_versions" ("song_version_id", "source");

COMMENT ON TABLE "lyrics_versions" IS

## Server Action + Subprocess Pattern (D-05 implementation)

**No precedent in this repo.** Pattern designed from `node:child_process.spawn` standard usage + Claude CLI verified `--print` flag.

### File: `src/lib/admin/claude-cli.ts`

```typescript
import { spawn } from "node:child_process";

export interface ClaudePrintOptions {
  /** Hard timeout in ms. Default 180_000 (3 min). */
  timeoutMs?: number;
  /** Optional AbortSignal (e.g. from Next.js request). */
  signal?: AbortSignal;
  /** CLI path. Defaults to "claude" — relies on PATH. */
  cliPath?: string;
}

export interface ClaudePrintResult {
  /** Parsed envelope JSON: { type, subtype, result, session_id, ... } */
  envelope: {
    type: string;
    subtype: string;
    result: string;
    session_id?: string;
    total_cost_usd?: number;
    usage?: { input_tokens: number; output_tokens: number };
  };
  /** stderr captured (for diagnosis on auth-prompt or other warnings). */
  stderr: string;
  /** Wall-clock duration in ms. */
  durationMs: number;
}

export class ClaudePrintError extends Error {
  constructor(
    message: string,
    public readonly code: "spawn_failed" | "non_zero_exit" | "timeout" | "invalid_json" | "auth_prompt",
    public readonly stderr: string,
    public readonly stdout: string,
  ) {
    super(message);
    this.name = "ClaudePrintError";
  }
}

/**
 * Spawn `claude --print --output-format=json` with the prompt piped via stdin.
 * Returns the parsed envelope. Throws ClaudePrintError on any failure path.
 */
export async function runClaudePrint(
  prompt: string,
  opts: ClaudePrintOptions = {},
): Promise<ClaudePrintResult> {
  const cli = opts.cliPath ?? "claude";
  const timeoutMs = opts.timeoutMs ?? 180_000;
  const startedAt = Date.now();

  return new Promise<ClaudePrintResult>((resolve, reject) => {
    const child = spawn(cli, ["--print", "--output-format=json"], {
      stdio: ["pipe", "pipe", "pipe"],
      // Inherit env so ~/.claude/ credentials are picked up
      env: process.env,
    });

    let stdout = "";
    let stderr = "";
    let settled = false;

    const timer = setTimeout(() => {
      if (settled) return;
      settled = true;
      child.kill("SIGKILL");
      reject(new ClaudePrintError(
        `claude --print exceeded ${timeoutMs}ms`, "timeout", stderr, stdout));
    }, timeoutMs);

    opts.signal?.addEventListener("abort", () => {
      if (settled) return;
      settled = true;
      child.kill("SIGTERM");
      clearTimeout(timer);
      reject(new ClaudePrintError("aborted", "spawn_failed", stderr, stdout));
    });

    child.stdout.on("data", (chunk: Buffer) => { stdout += chunk.toString("utf8"); });
    child.stderr.on("data", (chunk: Buffer) => { stderr += chunk.toString("utf8"); });

    child.on("error", (err) => {
      if (settled) return;
      settled = true;
      clearTimeout(timer);
      reject(new ClaudePrintError(
        `spawn failed: ${err.message}`, "spawn_failed", stderr, stdout));
    });

    child.on("close", (code) => {
      if (settled) return;
      settled = true;
      clearTimeout(timer);

      // Detect auth-prompt heuristically — exit 0 but stderr carries known phrases
      const authPromptHints = ["sign in", "log in", "claude login", "auth", "authenticate"];
      const looksLikeAuth = authPromptHints.some((h) =>
        stderr.toLowerCase().includes(h));

      if (code !== 0) {
        const codeKind = looksLikeAuth ? "auth_prompt" : "non_zero_exit";
        return reject(new ClaudePrintError(
          `claude --print exited ${code}`, codeKind, stderr, stdout));
      }

      try {
        const envelope = JSON.parse(stdout.trim());
        if (envelope.type !== "result" || envelope.subtype !== "success") {
          return reject(new ClaudePrintError(
            `unexpected envelope: type=${envelope.type} subtype=${envelope.subtype}`,
            "invalid_json", stderr, stdout));
        }
        resolve({ envelope, stderr, durationMs: Date.now() - startedAt });
      } catch (parseErr) {
        reject(new ClaudePrintError(
          `stdout not parseable JSON: ${(parseErr as Error).message}`,
          "invalid_json", stderr, stdout));
      }
    });

    // Pipe prompt to stdin
    child.stdin.end(prompt, "utf8");
  });
}

/**
 * Convenience: extract the model's textual response (envelope.result),
 * strip ```json fences if present, parse as JSON, validate against a Zod schema.
 */
import type { ZodSchema } from "zod";

export async function runClaudePrintParseJson<T>(
  prompt: string,
  schema: ZodSchema<T>,
  opts?: ClaudePrintOptions,
): Promise<T> {
  const { envelope } = await runClaudePrint(prompt, opts);
  let resultText = envelope.result.trim();
  if (resultText.startsWith("```")) {
    resultText = resultText.replace(/^```(?:json)?\n?/, "").replace(/\n?```$/, "");
  }
  const json: unknown = JSON.parse(resultText);
  return schema.parse(json);
}
```

## Two-Write Publish Transaction Pattern (D-15 implementation)

**Problem:** D-15 requires a single transaction wrapping (a) `INSERT INTO lyrics_versions`, (b) `UPDATE song_versions SET active_lyrics_version_id = ..., lesson = ...`, plus optional (c) any `vocabulary_items` upserts from re-tokenization. **Drizzle's `db.transaction(async tx => ...)` is unavailable** because the project uses `drizzle-orm/neon-http` (verified — `src/lib/db/index.ts:19`, plus the `// neon-http has no callback transactions` comment in `src/app/actions/review.ts:14-15`).

**Solution:** Use the Neon serverless driver's `sql.transaction([...queries])` API — it accepts an array of pre-built queries and runs them in a single non-interactive HTTP transaction. Drizzle integrates this via `db.batch([...statements])` for query objects, OR you can drop to raw `sql` and use the underlying Neon client directly.

### Pattern A: `db.batch([...])` (preferred — stays in Drizzle land)

```typescript
// src/lib/admin/publish-tx.ts
import { sql, eq } from "drizzle-orm";
import { db } from "@/lib/db";
import { lyricsVersions, songVersions } from "@/lib/db/schema";
import type { Verse } from "@/lib/types/lesson";

export interface PublishParams {
  songVersionId: string;
  editorId: string;
  baseVersionId: string;          // for stale check
  verses: Verse[];                // re-tokenized + vocab-relinked already
  source: "human" | "regen";
}

export interface PublishResult {
  newVersionId: string;
  newVersionNumber: number;
}

/**
 * Publish a new lyrics_versions row + update active pointer + rewrite
 * song_versions.lesson.verses, all in a single Neon non-interactive transaction.
 *
 * Returns 409-equivalent (throws StalePublishError) if base_version_id no longer
 * matches the current active_lyrics_version_id (D-18).
 */
export async function publishLyricsVersion(p: PublishParams): Promise<PublishResult> {
  // 1) Stale check + compute next version_number — cheap to do as a separate read
  //    because the actual write transaction below also re-checks via a guarded UPDATE.
  const [current] = await db.execute<{
    active_lyrics_version_id: string | null;
    next_n: number;
  }>(sql`
    SELECT
      sv.active_lyrics_version_id::text AS active_lyrics_version_id,
      COALESCE(MAX(lv.version_number), 0) + 1 AS next_n
    FROM song_versions sv
    LEFT JOIN lyrics_versions lv ON lv.song_version_id = sv.id
    WHERE sv.id = ${p.songVersionId}::uuid
    GROUP BY sv.active_lyrics_version_id
  `).then((r) => Array.isArray(r) ? r : (r.rows ?? []));

  if (!current) throw new Error("song_version not found");
  if (current.active_lyrics_version_id !== p.baseVersionId) {
    throw new StalePublishError(current.active_lyrics_version_id);
  }

  const newId = crypto.randomUUID();
  const versesJson = JSON.stringify(p.verses);

  // 2) Atomic batch — three statements in one HTTP round-trip.
  //    Drizzle's `db.batch` maps to `sql.transaction([...])` under neon-http.
  await db.batch([
    // (a) Insert new lyrics_versions row
    db.execute(sql`
      INSERT INTO lyrics_versions
        (id, song_version_id, version_number, source, editor_id, verses, parent_version_id, created_at)
      VALUES
        (${newId}::uuid, ${p.songVersionId}::uuid, ${current.next_n}, ${p.source},
         ${p.editorId}, ${versesJson}::jsonb, ${p.baseVersionId}::uuid, now())
    `),

    // (b) Update song_versions: active pointer + lesson blob
    //     GUARDED on active_lyrics_version_id = baseVersionId so a concurrent
    //     publish that slipped past step (1) still loses (race window).
    db.execute(sql`
      UPDATE song_versions
         SET active_lyrics_version_id = ${newId}::uuid,
             lesson = jsonb_set(
               COALESCE(lesson, '{}'::jsonb),
               '{verses}',
               ${versesJson}::jsonb
             ),
             updated_at = now()
       WHERE id = ${p.songVersionId}::uuid
         AND active_lyrics_version_id = ${p.baseVersionId}::uuid
    `),

    // (c) Clear the editor's draft for this song
    db.execute(sql`
      DELETE FROM lyrics_drafts
       WHERE song_version_id = ${p.songVersionId}::uuid
         AND editor_id = ${p.editorId}
    `),
  ]);

  return { newVersionId: newId, newVersionNumber: current.next_n };
}

export class StalePublishError extends Error {
  constructor(public readonly currentActiveId: string | null) {
    super("stale publish: base version no longer matches active");
    this.name = "StalePublishError";
  }
}
```

**On the post-publish side:** the action MUST also call `revalidateTag(\`song:${slug}\`)` (the existing `src/app/actions/cache.ts` helper) so the public song page picks up the new `lesson` blob.

### Pattern B: `vocabulary_items` upsert as part of the same batch

If re-tokenization (step inside the publish action, before the batch above) creates new `vocabulary_items` rows, append them to the same `db.batch([...])` array so the entire publish (vocab create + version insert + lesson update + draft clear) is atomic. Order matters: vocab inserts first, then `lyrics_versions` insert (which references the vocab via the verses jsonb), then `song_versions` update, then draft delete.

## Common Pitfalls / Gotchas / Landmines

### 1. neon-http has no callback transactions

**What goes wrong:** Writing `db.transaction(async (tx) => { ... })` for the publish flow fails at runtime — Neon HTTP driver doesn't expose interactive transactions.
**Why:** The driver is a stateless HTTP request layer. There's no connection to keep open between statements.
**How to avoid:** Use `db.batch([stmt1, stmt2, ...])` (Drizzle's neon-http transaction primitive). See §7.
**Detection:** in-source comment in `src/app/actions/review.ts:14-15` already documents this; any reviewer who skips that file will hit it during integration test.

### 2. kuromoji dict path resolves wrong from server-action context

**What goes wrong:** `scripts/lib/kuroshiro-tokenizer.ts:53-56` resolves the dict path relative to `import.meta.url`. When imported from `src/app/admin/lyrics/actions.ts`, `import.meta.url` points to the bundled server-action file, NOT to `scripts/lib/`. The dict path becomes wrong, kuroshiro fails to init.
**Why:** Next.js bundles server actions; relative paths break.
**How to avoid:** Parameterize `initKuroshiro(dictPath?: string)` and pass an absolute `path.resolve(process.cwd(), "node_modules/@sglkc/kuromoji/dict")` from the admin action. OR move the tokenizer to `src/lib/japanese/tokenizer.ts` AND parameterize.
**Detection:** integration test that runs the publish action against a test DB and asserts kuromoji-emitted tokens match expected.

### 3. `parent_version_id` self-FK type recursion

**What goes wrong:** Plain `.references(() => lyricsVersions.id)` with the table referring to itself produces TypeScript error `'lyricsVersions' is referenced directly or indirectly in its own initializer`.
**Why:** TypeScript can't resolve the circular type.
**How to avoid:** Annotate the callback: `.references((): AnyPgColumn => lyricsVersions.id)`. Import `AnyPgColumn` from `drizzle-orm/pg-core`.
**Detection:** TypeScript build fails immediately.

### 4. Subprocess deadlock on stdin

**What goes wrong:** Forgetting `child.stdin.end()` after writing prompt → child waits forever for EOF → never emits stdout → wrapper times out.
**Why:** stdio defaults; many examples skip the explicit `.end()`.
**How to avoid:** Use `child.stdin.end(prompt, "utf8")` (single call writes + closes). See §6 template.
**Detection:** unit test with mocked spawn that returns canned envelope after EOF.

### 5. Subprocess auth-prompt hangs

**What goes wrong:** Claude CLI's session expires; subprocess emits an interactive auth URL on stderr and waits for input → wrapper hangs until timeout.
**Why:** No way to detect "waiting on tty" from a piped subprocess; only the timeout catches it.
**How to avoid:** Heuristic stderr scanning for "sign in" / "auth" keywords (see `auth_prompt` branch in §6 template). Surface to user as "Claude CLI auth expired — run `claude login`".
**Detection:** manual — can't simulate easily. Document in sensei README.

### 6. `runtime = "edge"` accidental opt-in

**What goes wrong:** Server action file accidentally exports `export const runtime = "edge"` → `child_process` import errors at build time, kuromoji native bindings fail.
**Why:** Edge runtime doesn't include Node APIs.
**How to avoid:** Explicitly set `export const runtime = "nodejs"` at the top of `src/app/admin/lyrics/actions.ts` AND `src/app/api/admin/song/[id]/pipeline-status/route.ts`. Also set on `src/app/admin/lyrics/page.tsx` if needed.
**Detection:** build succeeds in dev, fails on `next build` if runtime is wrong.

### 7. `lesson.verses` JSONB write loses non-verses keys

**What goes wrong:** Naive `UPDATE song_versions SET lesson = ${newLessonJson}` overwrites the whole `lesson` object, blowing away `vocabulary`, `grammar_points`, `jlpt_level`, `difficulty_tier`.
**Why:** D-15 only versions `verses[]`, but the existing public page reads `vocabulary` and `grammar_points` from the same blob.
**How to avoid:** Use `jsonb_set(lesson, '{verses}', ${versesJson}::jsonb)` (see §7 publish template). Preserves siblings.
**Detection:** integration test asserts `lesson.vocabulary` and `lesson.grammar_points` are unchanged after publish.

### 8. ai-assist snapshot inflates row count fast

**What goes wrong:** D-20 writes a full `lyrics_versions` row on every AI fill click. With 10 admins × 50 songs × 30 verses × 5 retries = 75,000 rows; CONTEXT projects 25 MB total. Real-world drift (more retries) could 5x that.
**Why:** Maximum gap-analysis signal is the deliberate tradeoff (D-20 + SPEC #11).
**How to avoid:** None — it's locked. Document the storage growth in a comment on the schema; revisit when row count > 100k.
**Detection:** ad-hoc — track row count in a periodic admin dashboard query.

### 9. localStorage and server draft diverge under network failure

**What goes wrong:** Auto-save writes localStorage AND server. If server write fails (network hiccup), localStorage is ahead. Other tab/device gets stale server state. Page refresh per D-17 reads "server first, fall back to localStorage" — but localStorage is correct, server is stale → user keeps editing on stale state.
**Why:** Without conflict-resolution UI, "fall back to localStorage" can mask staleness.
**How to avoid:** On every successful save, set a `last_server_save_at` timestamp. On reload, compare `lyrics_drafts.updated_at` with `localStorage.last_server_save_at`. If localStorage is newer, replay localStorage → server (then load).
**Detection:** integration test with mocked failed server save followed by reload.

### 10. Concurrent draft from same admin in two tabs

**What goes wrong:** `lyrics_drafts` PK is `(song_version_id, editor_id)`. Two tabs from same admin = last-write-wins on the row. Earlier tab's edits overwritten silently.
**Why:** Per-editor draft semantics, not per-tab.
**How to avoid (option A — accept):** Document as "don't open the same song in two tabs." Same as D-17 implies.
**How to avoid (option B — detect):** Use `BroadcastChannel` to sync edits across tabs of the same origin. Adds complexity; CONTEXT calls this "consider".
**Detection:** manual.

### 11. Migration backfill picks wrong `verses` shape

**What goes wrong:** `INSERT INTO lyrics_versions ... SELECT sv.lesson->'verses'` — but some legacy `song_versions.lesson` rows have `null` verses or missing the `verses` key entirely. JSONB `->` returns SQL NULL, NOT NULL constraint violation.
**Why:** Catalog has variable-quality legacy data.
**How to avoid:** `COALESCE(sv.lesson->'verses', '[]'::jsonb)` (already in §5 draft).
**Detection:** integration test runs migration against a test DB with one legacy `lesson IS NULL` and one `lesson->>'verses' IS NULL` row.

### 12. Pipeline rerun status overwrites concurrent admin's flag

**What goes wrong:** Two admins each click swap on adjacent songs, pipeline 1 sets `pipeline_status = 'rerun_in_progress'`, pipeline 2 also tries to start on the same song (race) → both write status; admin sees confused state.
**Why:** No row-level lock; D-09 doesn't address.
**How to avoid:** Guarded UPDATE: `UPDATE song_versions SET pipeline_status = 'rerun_in_progress', pipeline_started_at = now() WHERE id = $1 AND pipeline_status = 'idle'`. If `rowCount === 0`, return 409 "rerun already in progress."
**Detection:** integration test fires two parallel `swapYoutubeVideo` calls.

### 13. `--steps=` checkbox propagates wrong default

**What goes wrong:** D-11 defaults to `[audio, whisper, lesson]`. If user unchecks "lesson" expecting "keep my human edits" but D-09 also writes a new `source='auto'` row at completion (per SPEC #19), the new auto version blasts through human edits anyway.
**Why:** Mismatch between "what steps run" and "what version is written."
**How to avoid:** If `--steps` does NOT include `lesson`, do NOT write a new `lyrics_versions` row at all — just update `youtube_id` + audio assets. Make this explicit in the orchestrator script.
**Detection:** integration test for `swap-video-pipeline.ts --steps=audio` asserts no new `lyrics_versions` row appears.

### 14. Clerk free tier MAU limit

**What goes wrong:** Clerk free plan caps at 10K MAU. Two admins are way under, but if Thiago ever opens the editor on demo machines, those count.
**Why:** Standard SaaS pricing trap.
**How to avoid:** Document in sensei README; not a v1 risk.
**Detection:** Clerk dashboard.

### 15. Vercel build break from middleware import

**What goes wrong:** `src/middleware.ts` imports `@clerk/nextjs/server`. Even though Vercel doesn't host `/admin/*`, the middleware file IS deployed and Vercel builds it. If `CLERK_PUBLISHABLE_KEY` / `CLERK_SECRET_KEY` env vars aren't set on Vercel, the middleware errors at request time on EVERY public route.
**Why:** Middleware runs for every request matching its `config.matcher`.
**How to avoid:** Set `config.matcher` to ONLY admin routes (NOT the Clerk-recommended catch-all). Set placeholder Clerk env vars on Vercel (publishable key is safe to expose — secret key can be a dummy string since middleware only matches admin routes that public Vercel users never hit). Verify with `next build` locally with empty Clerk vars.
**Detection:** deploy preview to Vercel and curl `/`.
