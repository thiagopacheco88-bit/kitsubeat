# Phase 11.5: Admin Lyrics Editor — Specification

**Created:** 2026-05-01
**Ambiguity score:** 0.081
**Requirements:** 23 locked

## Goal

Ship an admin-gated `/admin/lyrics` route where Thiago and his Japanese teacher can edit per-verse lyrics fields (furigana, romaji, translation, verse meaning, per-token kanji breakdown), manually adjust verse timing, insert/delete verses, swap the YouTube video (full pipeline rerun), flag songs as broken, and regenerate lessons — with every published edit producing a permanent versioned snapshot in a new `lyrics_versions` table that powers gap analysis between auto-pipeline and human-corrected output.

## Background

KitsuBeat is fully unauthenticated today (no Clerk, no middleware) — `PLACEHOLDER_USER_ID = "test-user-e2e"` in [src/lib/user-prefs.ts:1-2](kitsubeat/src/lib/user-prefs.ts#L1-L2). The `users` schema at [src/lib/db/schema.ts:284-291](kitsubeat/src/lib/db/schema.ts#L284-L291) is Clerk-ready (text PK) but Phase 10 has not shipped. An unauthenticated `/admin/timing/[songId]` route already exists for word-level WhisperX timing correction.

Lessons are stored as a single JSONB blob in `song_versions.lesson` ([src/lib/db/schema.ts:113](kitsubeat/src/lib/db/schema.ts#L113)) — there is no separate `verses` table. The `Verse` type at [src/lib/types/lesson.ts:64-79](kitsubeat/src/lib/types/lesson.ts#L64-L79) carries `tokens` (with per-token `surface`/`reading`/`romaji`), `translations` (multilingual map), `literal_meaning`, and `cultural_context`. Per-token `kanji_breakdown` lives on the joined `vocabulary_items` row from Phase 08.3.

Dual-source lyrics are already preserved immutably (`canonical_lyrics` + `whisper_lyrics`) alongside the active `synced_lrc`, and the `timing_verified` enum tracks `auto | manual` — strong precedent for the version-preservation pattern this phase formalizes for full lesson content.

The triggering problem: the auto-pipeline produces lyrics with errors (untranslated verses, wrong romaji, drifted timing, wrong song matched). Today's only fix path is editing JSONB by hand or re-running scripts. There is no audit trail of what auto produced vs what humans corrected, so Thiago cannot identify which pipeline step is the worst offender. This phase builds the editor that makes correction tractable AND captures the labeled data needed for pipeline gap analysis.

## Requirements

1. **Admin route auth gate**: `/admin/*` routes are protected by Clerk, accessible only to allowlisted emails.
   - Current: No auth library installed. `/admin/timing` exists and is publicly accessible.
   - Target: Clerk middleware installed, scoped to `/admin/*` only. Allowlist mechanism (env var or DB table) contains `thiagopacheco88@gmail.com` + sensei email. Existing `/admin/timing` route is also gated by the same middleware. Non-admin users navigating to any `/admin/*` URL are redirected to `/` (no 401/403 page that exposes route existence). User-facing flows (`/`, `/songs/*`, etc.) continue using `PLACEHOLDER_USER_ID` — full Phase 10 migration NOT included.
   - Acceptance: Logged-out user or logged-in non-allowlisted email navigating to `/admin/lyrics` and `/admin/timing` is redirected to `/` with no leaked information; allowlisted email can access both routes after auth.

2. **Admin lyrics editor route exists**: A new `/admin/lyrics` page renders the song search and editor shell.
   - Current: No `/admin/lyrics` route exists.
   - Target: `/admin/lyrics` renders a song search input at top + selected song's editor below. State of selected song persists in URL (`/admin/lyrics?songId=...&version=tv|full`) so admins can share/bookmark.
   - Acceptance: Navigating to `/admin/lyrics` (as admin) renders search + empty editor; navigating to `/admin/lyrics?songId=<id>&version=tv` directly loads that song into the editor.

3. **Song search**: Admin can find any song by title, artist, or anime.
   - Current: `/admin/timing` has a song list ([src/app/admin/timing/components/SongList.tsx](kitsubeat/src/app/admin/timing/components/SongList.tsx)) — list-only, no search.
   - Target: Search input filters all songs (including `flagged_wrong_song`/`flagged_unfixable`) by case-insensitive substring match across title/artist/anime/season_info. Results show song + version (TV/full) chips.
   - Acceptance: Typing "demon" returns Demon Slayer songs; typing an artist name returns all songs by that artist; flagged songs appear in admin search results (unlike the public catalog).

4. **YouTube player + verse list rendering**: Selected song renders embedded YouTube player and the full verse list with current published lyrics.
   - Current: Public song page at [src/app/songs/[slug]/page.tsx](kitsubeat/src/app/songs/[slug]/page.tsx) renders YouTube + verses for users; no editable equivalent.
   - Target: Editor renders the song's active YouTube embed (synced playback works) and a vertical list of all verses, each verse showing all editable fields. Player can scrub to any verse's `start_time_ms` for in-context review.
   - Acceptance: Selecting a song displays its current published verses in order; clicking a verse's "▶" button seeks YouTube to that verse's `start_time_ms`.

5. **Per-verse editable fields — furigana**: Each verse's tokens have an editable `reading` field (the kana representation displayed as furigana on the public player).
   - Current: `Token.reading` is set by the pipeline; no editing surface.
   - Target: Per token, an inline-editable kana text input. Tokens are rendered horizontally as in the public player, with the kana reading editable above each surface character.
   - Acceptance: Editing a token's reading updates the in-memory verse; verse renders with new reading after edit.

6. **Per-verse editable fields — romaji**: Each verse's tokens have an editable `romaji` field.
   - Current: `Token.romaji` is set by the pipeline; no editing surface.
   - Target: Per token, an inline-editable romaji input adjacent to the token.
   - Acceptance: Editing a token's romaji updates the in-memory verse without affecting other tokens.

7. **Per-verse editable fields — translation**: Each verse has editable per-language translations.
   - Current: `Verse.translations` is `Record<string, string>` set by the pipeline.
   - Target: Editor shows one input per language present in `translations` (typically `en` + `pt-BR` + others). Admin can edit any language independently. New languages can be added via a "+ language" picker.
   - Acceptance: Editing the `en` translation does not affect `pt-BR`; adding a new language inserts a key into `translations`.

8. **Per-verse editable fields — verse meaning**: Each verse has editable `literal_meaning` and `cultural_context` (the "breakdown" at the verse level).
   - Current: Both fields are `Localizable` (string or per-language map) set by the pipeline.
   - Target: Editor surfaces both as multiline text areas, per language.
   - Acceptance: Editing `literal_meaning` for `en` updates only that locale's value.

9. **Per-verse editable fields — per-token kanji breakdown**: Tokens that contain kanji surface their `kanji_breakdown` (linked from `vocabulary_items`) as editable.
   - Current: `KanjiBreakdown` is set by the Phase 08.3 enrichment script and lives on `vocabulary_items.kanji_breakdown`. No editor.
   - Target: Click a kanji-containing token to expand a breakdown editor showing per-character `meaning`, `on_yomi`, `kun_yomi`, `radical_hint`, plus a `compound_note` for multi-kanji words. Edits write back to the joined `vocabulary_items` row, NOT to the verse JSON (so all songs sharing the vocab benefit).
   - Acceptance: Editing the `radical_hint` for the kanji 鉄 in song A is reflected when 鉄 appears in song B; verse JSON is not modified.

10. **AI fill-the-rest button (per verse)**: A button on each verse fills the remaining fields using inline Claude Code based on the field(s) the human edited.
    - Current: No AI-assist surface in the codebase. Lessons are generated via `scripts/seed/03b-generate-content-sequential.ts` running inline Claude Code.
    - Target: Button is enabled per verse when at least one field has been edited. On click, calls inline Claude Code via the same path as lesson generation, passing the edited field as ground truth and asking the model to produce values for the unedited fields. Returned values populate the editor (not yet published — admin must review and publish).
    - Acceptance: Editing the romaji on verse 3, then clicking AI fill, populates a new translation/furigana/meaning suggestion in verse 3's other fields; verse 1 and 2 are untouched.

11. **AI-assist snapshot logged on every fill click**: Every AI fill click writes an `ai-assist` row to `lyrics_versions`, regardless of whether the human accepts or overrides the suggestion.
    - Current: No `lyrics_versions` table exists.
    - Target: Each click writes a row with `source = 'ai-assist'`, the AI's full proposed verses snapshot, the editor_id, and a timestamp. Used for gap analysis (compare AI suggestion vs final human version).
    - Acceptance: Clicking AI fill 3 times on a song without publishing produces 3 rows with `source = 'ai-assist'` in `lyrics_versions` for that song.

12. **Manual timing edit per verse**: Each verse's `start_time_ms` and `end_time_ms` are editable.
    - Current: Verse timing is set by `scripts/seed/restore-verse-order.ts` from synced_lrc; corrections happen via `/admin/timing` (word-level only, not verse-level boundary edits in the lyrics editor).
    - Target: Editor exposes ms input fields (or mm:ss.SSS picker) per verse. Validation warns on overlapping verses or non-monotonic timing but does NOT block publish.
    - Acceptance: Setting verse 5 `start_time_ms = 60000` and `end_time_ms = 65000` persists to draft; setting verse 5 to `start_time_ms = 30000` (overlapping verse 3) shows a warning but allows publish.

13. **Insert verse `+` buttons**: Admins can insert a new verse between any two existing verses, before the first, or after the last.
    - Current: Verses can only be added via re-running the pipeline.
    - Target: `+` button between every pair of verses, plus one above the first verse and one below the last. Clicking opens an inline form with empty fields + manual timing entry. New verse is added to draft with `verse_number` adjusted to slot in (subsequent verses renumbered on publish).
    - Acceptance: With 5 verses, clicking `+` between verse 2 and verse 3 produces a draft state with 6 verses; published state renumbers correctly so verses are 1–6 contiguously.

14. **Delete verse button**: Each verse has a delete button.
    - Current: No deletion surface.
    - Target: Trash icon on each verse. Clicking shows a confirm; on confirm, removes the verse from draft. Subsequent verse numbers are NOT auto-renumbered in draft (preserves edit context); renumbering happens on publish.
    - Acceptance: Deleting verse 3 of 5 produces a draft with verses [1, 2, 4, 5]; on publish, the row in `lyrics_versions` stores them as [1, 2, 3, 4].

15. **Save-per-verse (draft, not versioned)**: Each verse has a Save button that persists to a draft buffer + localStorage WITHOUT creating a `lyrics_versions` row.
    - Current: No draft mechanism.
    - Target: Save persists to a server-side `lyrics_drafts` table keyed on `(song_version_id, editor_id)` AND mirrors to `localStorage`. Page refresh restores draft. Other admins do NOT see this admin's draft (drafts are per-editor).
    - Acceptance: Editing verse 2, clicking Save, refreshing the page → verse 2 still shows the edit; opening the same song from a different browser still shows the edit (server-side persistence); a different admin opening the same song sees the published version, not this admin's draft.

16. **Publish (creates versioned row)**: A "Publish" button writes the full current draft as a new row in `lyrics_versions` with `source = 'human'` and replaces the active rendered lesson.
    - Current: No versioning. Lesson edits would overwrite `song_versions.lesson` directly.
    - Target: Publish creates a row `{song_version_id, version_number, source: 'human', editor_id, verses: <full snapshot>, created_at}`. Updates `song_versions.lesson` to point to / contain the new version's verses (active version). Clears the draft. Increments `version_number`.
    - Acceptance: Publishing produces a new `lyrics_versions` row with `source = 'human'` and the full verses snapshot; reloading the public song page shows the new lyrics; the previous version remains queryable by `version_number - 1`.

17. **Indefinite version retention**: All `lyrics_versions` rows are preserved permanently — never deleted, never overwritten.
    - Current: No version table.
    - Target: No deletion path exists in code. Initial seed creates a `source = 'auto'` row for every existing song version's current lesson on migration. Subsequent edits produce additional rows (`auto`, `ai-assist`, `human`, `regen`).
    - Acceptance: Publishing 5 different versions of song X over time produces 5 rows in `lyrics_versions` with monotonically increasing `version_number`; running the system for 6 months never deletes rows.

18. **Auto re-tokenize on publish**: When a verse's text/tokens are edited, publish re-runs kuromoji tokenization and re-links tokens to `vocabulary_items` by `(surface, reading)`.
    - Current: Token vocab linkage happens during initial pipeline run (`scripts/backfill-vocab-identity.ts`). No on-edit re-linking.
    - Target: On publish, for each verse marked as text-edited, run kuromoji over the new surface text, produce fresh tokens, and look up each token's `vocab_item_id` from `vocabulary_items` by `(surface, reading)`. Tokens that don't match an existing vocabulary_items row are flagged in the editor with a "new vocab created" or "needs review" indicator. The verse's tokens array is replaced with the re-tokenized output.
    - Acceptance: Editing verse 2 to replace 愛 with 恋 (reading こい), publishing → new tokens array contains 恋 with the existing `vocabulary_items.id` for 恋; if 恋 doesn't exist in vocabulary_items, a new row is created and the linkage flagged for review in the editor.

19. **YouTube video swap → full pipeline rerun**: A "Swap Video" button accepts a new YouTube URL and triggers the full content pipeline for that song version.
    - Current: `youtube_id` on `song_versions` is set during initial pipeline run; manual swap requires DB edit + script rerun.
    - Target: Button opens modal accepting a YouTube URL. On confirm, sets `song_versions.youtube_id`, sets song to `pipeline_status = 'rerun_in_progress'` (hidden from public catalog during rerun), enqueues the full pipeline (Whisper transcription + lyric extraction + AI lesson generation + lesson cache invalidation). On rerun completion, writes a new `lyrics_versions` row with `source = 'auto'`. Old `lyrics_versions` rows for the song are preserved.
    - Acceptance: Swapping the video on song X creates a new `lyrics_versions` row with `source = 'auto'` after rerun completes; old auto/human versions remain in the table; the song's old `youtube_id` is preserved in `song_video_history`; the public song page shows the new video and new lesson after completion.

20. **Pipeline rerun failure handling**: If the rerun fails, auto-retry once; on second failure, mark the song as `flagged_unfixable` with an auto-generated note.
    - Current: No rerun status tracking in DB.
    - Target: A `pipeline_status` column on `song_versions` with states `idle | rerun_in_progress | rerun_failed`. Rerun executor catches exceptions, retries once with same parameters. Second failure: sets `quality_status = 'flagged_unfixable'`, appends `quality_notes` with the failure step + error message + timestamp. Editor surfaces a "Retry rerun" button to the admin.
    - Acceptance: Mocking a Whisper failure produces 2 retry attempts then `quality_status = 'flagged_unfixable'` with a note matching pattern `Pipeline failed at <step>: <error> (<timestamp>)`.

21. **YouTube swap audit log**: Every video swap is logged to a new `song_video_history` table.
    - Current: No swap history.
    - Target: Table with `(id, song_version_id, old_youtube_id, new_youtube_id, changed_at, changed_by, reason)`. Reason is a free-text field captured in the swap modal.
    - Acceptance: Swapping a song's video produces a row in `song_video_history`; querying `song_video_history` by `song_version_id` returns all historical video URLs.

22. **Flag song quality**: Admin can mark a song as `flagged_wrong_song` (wrong content matched) or `flagged_unfixable` (no good alternative video exists), with free-text notes. Flagged songs are hidden from public catalog but visible in admin search.
    - Current: No quality status surface; songs are either published-and-visible or absent from the database.
    - Target: New `quality_status` enum on `songs`: `active | flagged_wrong_song | flagged_unfixable`, plus nullable `quality_notes` text. Public catalog query filters `quality_status = 'active'`. Admin lyrics editor search shows ALL songs regardless of flag. Player route returns 404 for flagged songs.
    - Acceptance: Setting song X to `flagged_wrong_song` removes it from `/songs` catalog; visiting `/songs/<x-slug>` returns 404; song still appears in `/admin/lyrics` search; admin can clear the flag back to `active`.

23. **Regenerate Lessons button**: Per-song button regenerates lesson content for verses changed since the last `regen` version, scoped to those verses only.
    - Current: Lessons regenerate via `scripts/seed/03b-generate-content-sequential.ts` running over the full song.
    - Target: Button shows a confirm modal listing the N verses with edits since the last `source = 'regen'` (or `auto`) version. On confirm, calls inline Claude Code per affected verse to regenerate the verse-level lesson content (vocab + grammar + meaning). Writes a new `lyrics_versions` row with `source = 'regen'`. Lessons cache for the song is invalidated.
    - Acceptance: Editing 2 of 8 verses, publishing, then clicking Regenerate Lessons → confirm modal shows "2 verses affected"; on confirm, inline Claude Code is invoked twice (once per edited verse); a new `lyrics_versions` row is created with `source = 'regen'`; the public song page reflects regenerated content for those 2 verses.

## Boundaries

**In scope:**

- `/admin/lyrics` route with Clerk middleware + email allowlist gate (also gates existing `/admin/timing`)
- Song search by title/artist/anime/season_info (case-insensitive substring), including flagged songs
- YouTube embed + verse list editor parity with the public player
- Per-verse editable fields: token-level furigana (`reading`), token-level romaji, verse-level translations (per language), verse-level `literal_meaning` + `cultural_context`, per-token `kanji_breakdown` (writes back to `vocabulary_items`)
- AI fill-the-rest button per verse using inline Claude Code path
- Manual timing edit per verse (warns on overlap, does not block)
- Insert verse `+` between verses, before first, after last (manual timing)
- Delete verse button per verse
- Save-per-verse to draft (server-side `lyrics_drafts` table + localStorage mirror, per-editor)
- Publish → creates new `lyrics_versions` row (`source = 'human'`)
- New `lyrics_versions` table (indefinite retention, never deleted)
- New `song_video_history` audit table
- New `pipeline_status` and `quality_status` columns on `song_versions`/`songs`
- Auto re-tokenize on publish (kuromoji + vocab re-linking + flag mismatches)
- YouTube swap → full pipeline rerun → new `auto` version + audit log entry
- Pipeline rerun status tracking + auto-retry-once + flag-on-failure
- Flag-as-broken (`flagged_wrong_song` / `flagged_unfixable` + notes)
- Regenerate Lessons (scoped to edited verses, inline Claude Code, new `regen` version)
- Stale-publish detection: if base_version_id != latest, block publish + show reload modal
- Per-edit AI-assist snapshots (every fill click writes an `ai-assist` row)
- Migration that backfills a `source = 'auto'` row for every existing song's current lesson

**Out of scope:**

- Full Phase 10 user authentication migration — public-facing flows continue using `PLACEHOLDER_USER_ID`. Reason: scope; this phase only needs an admin gate.
- Real-time collaborative editing (Google-Docs style) — concurrency handled via stale-publish detection, not live sync. Reason: two-user environment doesn't justify the complexity.
- Optimistic merge conflict resolver UI — last-publish-wins with reload-and-reapply is sufficient. Reason: same as above.
- Bulk operations (edit verses across multiple songs at once) — single-song workflow only. Reason: not yet a bottleneck.
- Mobile editing UX — desktop-only for v1. Reason: editing is desk work; mobile would compromise input UX.
- Public-facing version history viewer — versions captured in DB but no end-user surface. Reason: end users don't need it.
- One-click version rollback UI — admin can re-publish an old version manually if needed. Reason: simpler; rare operation.
- Side-by-side version diff viewer — diff data is captured (full snapshots) but visualization comes later. Reason: gap analysis needs the data first; UI can be added when patterns emerge.
- Auto-translation suggestions independent of AI fill — translation only filled when admin clicks AI fill. Reason: avoid surface-level features; one path for AI assistance.
- Performance SLA on Whisper / inline Claude Code rerun — best-effort; admin sees progress, no time guarantee. Reason: local + free pipeline can't promise latency.
- Migration of existing `/admin/timing` UI into the new lyrics editor — coexist as separate routes. Reason: out of scope; lyrics editor is a new workflow.

## Constraints

- **AI calls go exclusively through inline Claude Code** (the same path as `scripts/seed/03b-generate-content-sequential.ts`). NO paid Anthropic API calls. This is a hard project constraint per [memory: local-only tooling, no paid API credits](file://memory/feedback_local_only_tooling.md).
- **Pipeline rerun runs server-side and asynchronously**; the editor UI must poll status and not block. Admin can navigate away during rerun.
- **Drafts persist BOTH to server-side `lyrics_drafts` AND localStorage** so cross-device recovery works (sensei drafting on laptop, switching to desktop should not lose work) AND a server outage doesn't lose work mid-edit.
- **Auto-save to localStorage on min 5-second typing pause** — drafts are never just in-memory.
- **Browser support: latest 2 major versions** of Chrome / Edge / Firefox / Safari (parity with current KitsuBeat).
- **Storage budget: indefinite retention is acceptable** because per-version JSON snapshots are small (~1–5 KB) and song count is in the low hundreds in v1. Estimate: 500 songs × 10 versions average × 5KB = 25 MB total, well within Neon Postgres's free tier.
- **Admin route redirects to `/`, never returns 401/403**, so route existence isn't disclosed to non-admins.
- **All new tables created via Drizzle migrations** following existing pattern (see `migrations/0009-*` etc.). Migration must run via `vercel-build` script per project convention.
- **`/admin/timing` route behavior must not regress**: same auth gate added, but timing-editing functionality unchanged. Reason: avoid coupling new feature work to existing tool's behavior.
