**Gathered:** 2026-05-01

<domain>
## Phase Boundary

Admin-gated `/admin/lyrics` route where Thiago and his Japanese teacher edit per-verse lyrics fields (furigana, romaji, translation, verse meaning, per-token kanji breakdown), manually adjust verse timing, insert/delete verses, swap the YouTube video (full pipeline rerun), flag songs as broken, and regenerate lessons — with every published edit producing a permanent versioned snapshot in a new `lyrics_versions` table that powers gap analysis between auto-pipeline and human-corrected output.

- Auto-translation suggestions independent of AI fill
- Performance SLAs on Whisper / inline Claude Code rerun
- Migrating `/admin/timing` UI into the new editor (coexist as separate routes)

<decisions>
## Implementation Decisions

### Deployment surface

- **D-01 (LOCKED):** `/admin/lyrics` and `/admin/timing` are **localhost-only**. Thiago and sensei each run `npm run dev` on their own machines pointed at the shared Neon Postgres. The public catalog (`/`, `/songs/*`) continues to deploy to Vercel. Clerk middleware is installed but only the admin routes use it; public flows still use `PLACEHOLDER_USER_ID`.
  - **Why:** Unlocks the localhost-only AI/pipeline path required by the no-paid-API constraint. Vercel serverless can't host the multi-minute Whisper rerun, the `claude --print` subprocess, or kuromoji at production-grade reliability.
  - **Risk to flag in planning:** Sensei must clone the repo + run dev server. README/setup doc needed (separate task in plan, mirroring Phase 11.1 operator README).

### Admin gate

- **D-02:** **Clerk** is the auth library. Install scoped to `/admin/*` only. Public flows are NOT migrated to Clerk in this phase (Phase 10 deferred per SPEC).
- **D-03:** Allowlist = **env var `CLERK_ADMIN_EMAILS`** (comma-separated). Middleware reads it per request, splits, compares to `clerkAuth.user.primaryEmailAddress`. Adding a third admin = env var edit + dev-server restart. Hardcoded list in code is rejected (one less reason to redeploy public).
- **D-04:** Non-admin redirect = **`/`** with no 401/403 page (route existence not disclosed). Implementation in Next.js middleware (`src/middleware.ts`) matched by `/admin/:path*`.

### AI invocation path

- **D-05 (LOCKED):** AI fill + Regenerate Lessons invoke an LLM by **spawning `claude --print` (or equivalent headless flag) as a child_process from the Next.js server action**. The Claude CLI uses Thiago's Max 20x plan session token; no API credits are consumed. Localhost-only deployment is what makes this viable.
  - **Reconciles SPEC tension:** SPEC §Constraints says "same path as `scripts/seed/03b-generate-content-sequential.ts`" but that script imports `@anthropic-ai/sdk` and uses `ANTHROPIC_API_KEY` (paid). The constraint's intent was "use Claude, not OpenAI/Gemini" and "no paid credits" — the CLI subprocess satisfies both. The 03b script will likely be edited or replicated to use the CLI path too, but that's a planning decision.
  - **Subprocess prompt:** server action streams a JSON-formatted prompt to stdin, parses JSON from stdout, validates with Zod (LessonSchema or VerseFillSchema), surfaces results to editor.
- **D-06:** AI fill **prompt is a NEW per-verse prompt** at `scripts/lib/verse-fill-prompt.ts`. Takes one verse's edited field(s) + neighbour verses (±2) as anchors + the unedited fields to fill. Output schema: a single Verse subset, not a full lesson. Mirrors Phase 11.3's drafter+inline-review pattern.
- **D-07:** Regenerate Lessons = **same subprocess+prompt mechanism, looped per affected verse**. Iterates over the verses changed since the last `source = 'regen'` (or `auto`) version. Writes one `lyrics_versions` row at the end with `source = 'regen'`. Reuses validation, snapshot logging, error handling.
- **D-08:** Admin UX during AI fill = **inline blocking spinner** on the verse's button. Per-verse granularity (not whole-song) makes 10–90s waits tolerable. No background-job table, no SSE.

### Pipeline rerun (YouTube swap)

- **D-09 (LOCKED):** YouTube swap triggers **a single new orchestrator script `scripts/seed/swap-video-pipeline.ts`** that wraps the meaningful subset of the existing pipeline for one song. Server action spawns it via child_process with `--slug=X --new-youtube-id=Y --steps=audio,whisper,lesson` (steps is selectable, see D-11). Script writes status + current step to `song_versions.pipeline_status` + `song_versions.pipeline_step` columns as it progresses; editor polls.
- **D-10:** Status tracking = **DB column polling** at 3–5s interval via `/api/admin/song/:id/pipeline-status`. SPEC #20 already locks `pipeline_status` enum (`idle | rerun_in_progress | rerun_failed`); this phase adds two observability columns:
  - `pipeline_step text null` — current step name (`audio-download | demucs | whisperx | lesson-gen | tokenize | insert`)
  - `pipeline_started_at timestamptz null`
- **D-11:** Rerun scope = **admin selects which steps to re-run**. Swap modal includes a checkbox row: `[✓] re-download audio  [✓] Demucs+Whisper  [✓] lesson-gen  [ ] lyrics fetch`. Defaults to the three checked options. Lets admin recover from "wrong YouTube cut, same song" (audio+timing only) vs "wrong song matched" (everything).
  - **Tradeoff accepted:** more decisions per swap, but two-user system with mostly-Thiago operating the editor makes the granularity worth the click cost.
- **D-12:** Failure retry = **resume from failed step**. `pipeline_step` column already records where it died. On second failure, set `quality_status = 'flagged_unfixable'` with an auto-generated note matching SPEC #20's pattern. Editor surfaces a "Retry rerun" button.
- **D-13:** While `pipeline_status = 'rerun_in_progress'`, the song is **hidden from the public catalog**. Catalog query (currently in `src/lib/db/queries.ts` per project convention) filters `pipeline_status = 'idle'` AND `quality_status = 'active'`. Public song page returns 404 for non-idle pipeline status as well.

### Versioning + drafts schema

- **D-14 (LOCKED):** New `lyrics_versions` table:
  ```sql
  id uuid pk default gen_random_uuid()
  song_version_id uuid fk → song_versions.id (cascade delete? NO — preserve history)
  version_number int not null  -- monotonic per song_version_id
  source text check in ('auto','ai-assist','human','regen') not null
  editor_id text null  -- Clerk user id; null for source='auto' system rows
  verses jsonb not null  -- full Verse[] snapshot
  parent_version_id uuid null fk → lyrics_versions.id  -- which version this branched from
  created_at timestamptz not null default now()
  unique (song_version_id, version_number)
  index (song_version_id, created_at desc)
  ```
  - **`verses` only**, not whole lesson — verses are what this phase edits; grammar_rules / vocabulary list at the lesson level are derived/aggregated and don't need per-version snapshotting (vocabulary_items already has its own row identity).
  - Indefinite retention: no DELETE/CASCADE policy in schema or code. Re-runs and human edits APPEND.
- **D-15:** Active version pointer = **column on `song_versions`**: `active_lyrics_version_id uuid null fk → lyrics_versions.id`.
  - On publish: server transactionally inserts new `lyrics_versions` row, updates `song_versions.active_lyrics_version_id` AND `song_versions.lesson` (the latter keeps the existing public song page working — `lesson.verses` continues to be the runtime read source for backwards compat, but it must equal the active version's `verses`).
  - **Reason for two-write strategy:** the public song page reads `song_versions.lesson` (existing JSONB blob, used by the player). Phase 11.5 doesn't refactor that read path — it adds the version pointer + rewrites the blob in lockstep on publish. A future phase can switch the read path to JOIN `lyrics_versions` if needed.
- **D-16 (LOCKED):** New `lyrics_drafts` table:
  ```sql
  song_version_id uuid not null fk → song_versions.id
  editor_id text not null
  base_version_id uuid not null fk → lyrics_versions.id  -- branch point for stale detection
  verses jsonb not null
  dirty_verse_numbers int[] not null default '{}'
  updated_at timestamptz not null default now()
  primary key (song_version_id, editor_id)
  ```
  - Single row per (song, editor). Save-per-verse upserts the row (fast, avoids per-verse row writes).
  - `dirty_verse_numbers` = which verses have been edited since `base_version_id`. Used to scope Regenerate Lessons (D-07) and to drive the editor's "edited" badge UI.
- **D-17:** localStorage mirror key = `lyrics-draft:{song_version_id}:{editor_id}` storing the same shape. Auto-save debounces 5s typing pause → writes server `lyrics_drafts` AND localStorage. Page refresh: read server first, fall back to localStorage if server returns no row (handles the case where server-write failed but local edit happened).
- **D-18:** Stale-publish detection = **compare `base_version_id` against current `song_versions.active_lyrics_version_id`** at publish time. If different, server returns 409 Conflict + the new active's version_number. Editor shows reload modal (SPEC requirement). Optimistic concurrency, no locks.

### Re-tokenization on publish

- **D-19 (LOCKED):** On-publish kuromoji re-tokenization runs **inside the publish server action** via `runtime = 'nodejs'` (Next.js default for server actions). Imports the existing `scripts/lib/kuroshiro-tokenizer.ts` (or a refactored copy in `src/lib/`) and calls it with each `dirty_verse_numbers` verse's surface text.
  - For each new token, look up `vocab_item_id` from `vocabulary_items` by `(surface, reading)`. Misses → create new `vocabulary_items` row (mirror of how Phase 11.1 add-song pipeline handles unseen vocab) and flag the token in editor as `needs_review` for sensei follow-up.
  - **Why server action vs subprocess:** kuromoji init cost (~500ms) is acceptable in a long-lived Next.js dev server; subprocess-per-publish would double that. Localhost-only deployment removes the edge runtime concern.
  - **Refactor decision deferred to planner:** whether to leave `scripts/lib/kuroshiro-tokenizer.ts` where it is and import from there, or move it to `src/lib/japanese/tokenizer.ts`. The planner reads existing imports and decides.

### AI-assist snapshot logging

- **D-20:** Every AI fill click writes a `lyrics_versions` row with `source = 'ai-assist'` BEFORE the admin sees the suggestion (SPEC #11). The row's `verses` snapshot = the AI's full proposed verses (not the editor's current state). `parent_version_id` = current draft's `base_version_id`. `editor_id` = current admin. Used for gap analysis: compare ai-assist row against subsequent human row to see "what did the model suggest, what did the human override".

### Editor UI architecture

- **D-21:** State management = **single zustand store** (`useAdminLyricsStore`) holding the full draft (verses, dirty flags, base_version_id, save-status). Per-input components are uncontrolled with `onBlur` → store update. 5s typing-pause auto-save effect lives at the store level. Pattern matches Phase 8 / Phase 08.4 store conventions.
- **D-22:** Server-state queries (active version, drafts, pipeline status) use **TanStack Query** if already in deps, otherwise plain `fetch` + `useEffect` polling. (Planner verifies — project leans on Next.js server components + revalidate, so a heavy query lib may be overkill.)

- **Existing pipeline scripts** — orchestrated via the new `swap-video-pipeline.ts` rather than modified; their entry points stay untouched.

### Risks / things to watch

- **`claude` CLI headless flag drift** — `--print` is the current non-interactive flag at the time of writing; planner verifies at plan-time and locks the flag in the executor wrapper.
- **Migration number drift** — next free is `0015` as of 2026-05-01; planner checks `ls drizzle/*.sql | tail -1` before generating.
- **Sensei setup overhead** — localhost-only deployment means sensei needs Node, repo clone, .env.local, dev server, kuromoji dictionary. Plan should include a "sensei onboarding README" task or extend `docs/README-adding-songs.md`.
- **Kuromoji dictionary path resolution** — `scripts/lib/kuroshiro-tokenizer.ts` uses paths relative to the script location; if imported from a server action, dict path resolution may break. Verify at execution time and parameterize the dict dir.
- **Two-write publish atomicity** — D-15 updates BOTH `song_versions.active_lyrics_version_id` and `song_versions.lesson` in the same transaction with the new `lyrics_versions` insert. Must be a single transaction; otherwise the public page can read a stale `lesson` blob with a fresh active pointer.
- **`parent_version_id` integrity** — `lyrics_versions.parent_version_id` references the same table; Drizzle FK definition must allow self-reference. Standard but worth verifying.
- **Subprocess timeouts** — Next.js dev server doesn't kill long subprocesses, but production-mode Next.js server actions cap at 5min by default (configurable). For localhost-only this is moot, but if anyone ever runs production locally, they'll need to bump the timeout.
- **Concurrent draft on same song from same admin in two tabs** — `lyrics_drafts` PK is (song_version_id, editor_id). Same admin, two tabs = last-write-wins on the server row. localStorage is per-origin per-tab and may diverge. Planner should consider a `BroadcastChannel` mirror or accept last-write-wins as the documented behavior.

<specifics>
## Specific Ideas

- The whole reason `lyrics_versions` exists with the `parent_version_id` link + `source` enum is **gap analysis**: query "for each human row, find its parent ai-assist row, and diff" → tells Thiago whether the pipeline drifts on translation, romaji, timing, or kanji_breakdown. The schema must let that query be a 1-line CTE; if `parent_version_id` makes that hard, redesign.
- The editor needs to feel like the existing `/admin/timing` route — function-first, minimal styling, Thiago-friendly. Do NOT introduce a new design system in this phase.
- `claude --print` subprocess is the keystone. If the CLI's headless mode doesn't return clean JSON to stdout (or has interactive auth prompts in headless mode), the whole AI-fill path collapses. Plan should include a tiny smoke test as the first executable task: invoke `claude --print "Return {\"ok\": true} as JSON only"` and verify it parses.
- Sensei must be able to drive the editor without help from Thiago for individual song edits. Pipeline rerun + Regenerate Lessons can require Thiago's involvement initially (heavier ops).

</specifics>
