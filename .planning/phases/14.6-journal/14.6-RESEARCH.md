## Summary

Phase 14.6 adds a file-based MDX content pipeline to a Next.js 15 App Router application. The core technical challenge is choosing the right MDX approach for the Subutai "drop a file, it appears" workflow, wiring a full SEO layer (OG tags, JSON-LD, sitemap), and ensuring the Journal feels native to the session-14 design system rather than a bolted-on blog.

The recommended approach is **`next-mdx-remote/rsc` (v6.0.0) with `gray-matter` for frontmatter and `reading-time` for reading-time calculation**. This combination gives full Server Component support, no webpack configuration changes, and a clean file-drop workflow: a single `getAllArticles()` utility reads `src/content/journal/*.mdx` from the filesystem using Node's `fs` module and parses frontmatter with `gray-matter`. The individual article page uses `compileMDX` from `next-mdx-remote/rsc` to render content and extract frontmatter in one pass. `generateStaticParams` at build time enumerates slugs from the directory listing, making all articles statically generated with zero manual registration.

The SEO layer plugs directly into Next.js's `generateMetadata()` export (App Router native), which handles `<title>`, `<meta>`, `og:*`, and `canonical` without any third-party SEO package. JSON-LD is injected via `<script type="application/ld+json">` in the page component body following the official Next.js pattern. Sitemap is handled by a native `src/app/sitemap.ts` file returning `MetadataRoute.Sitemap`, which Next.js auto-serves at `/sitemap.xml`.

**Primary recommendation:** Use `next-mdx-remote/rsc` + `gray-matter` + `reading-time`. No next.config.ts changes needed. No CMS, no database — pure filesystem. Subutai drops `.mdx` into `src/content/journal/`; the build picks it up automatically.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| MDX file parsing + frontmatter extraction | Build-time Server (Node) | — | fs.readdir + gray-matter run at build on the server; no client involvement |
| Article content rendering | Server Component (RSC) | — | `compileMDX` from `next-mdx-remote/rsc` is async, server-only |
| Article index (card grid) | Server Component (RSC) | — | getAllArticles() reads filesystem at build time |
| SEO metadata (title, OG, canonical) | Server Component (generateMetadata) | — | App Router native; runs server-side before HTML emission |
| JSON-LD (schema.org/Article) | Server Component (page body) | — | Injected via `<script>` tag in RSC, not client JS |
| Sitemap | Build-time Server (sitemap.ts) | — | Next.js MetadataRoute.Sitemap, served at /sitemap.xml |
| Category badge UI | Browser / Client | — | Pure display, Tailwind, no state |
| Cover image display | Browser / Client | Server (next/image optimization) | next/image handles responsive optimization server-side |
| Reading time display | Build-time (pre-computed) | — | Computed once in getAllArticles(), stored in frontmatter or derived |

### Pattern 1: Content Collection Utility (`src/lib/journal/articles.ts`)

**What:** Single utility that owns all filesystem access. Returns typed frontmatter objects. Called from index page (list), article page (single), and sitemap.

**When to use:** Whenever a Server Component needs article data.

```typescript
// Source: Next.js official MDX guide (https://nextjs.org/docs/app/guides/mdx)
// + next-mdx-remote README (https://github.com/hashicorp/next-mdx-remote)
import fs from 'node:fs';
import path from 'node:path';
import matter from 'gray-matter';
import readingTime from 'reading-time';

const CONTENT_DIR = path.join(process.cwd(), 'src/content/journal');

export type ArticleCategory = 'lore' | 'language' | 'translation';

export interface ArticleFrontmatter {
  title: string;
  slug: string;
  date: string;           // ISO date string e.g. "2026-05-10"
  coverImage: string;
  category: ArticleCategory;
  summary: string;
  tags?: string[];
  author?: string;
  readingTime?: string;   // pre-computed or overridden in frontmatter
}

export interface ArticleMeta extends ArticleFrontmatter {
  readingTimeComputed: string; // always populated, fallback if not in frontmatter
}

export function getAllArticles(): ArticleMeta[] {
  const files = fs.readdirSync(CONTENT_DIR).filter((f) => f.endsWith('.mdx'));
  return files
    .map((filename) => {
      const raw = fs.readFileSync(path.join(CONTENT_DIR, filename), 'utf8');
      const { data, content } = matter(raw);
      const rt = readingTime(content);
      return {
        ...(data as ArticleFrontmatter),
        readingTimeComputed: data.readingTime ?? rt.text,
      };
    })
    .sort((a, b) => new Date(b.date).getTime() - new Date(a.date).getTime());
}

export function getArticleSource(slug: string): string | null {
  const filepath = path.join(CONTENT_DIR, `${slug}.mdx`);
  if (!fs.existsSync(filepath)) return null;
  return fs.readFileSync(filepath, 'utf8');
}
```

### Pattern 2: Article Page with compileMDX + generateMetadata + JSON-LD

**What:** The `[slug]` page combines static generation, SEO metadata, and MDX rendering.

**When to use:** Every article page.

```typescript
// Source: next-mdx-remote/rsc README + Next.js generateMetadata docs
// https://github.com/hashicorp/next-mdx-remote
// https://github.com/vercel/next.js/blob/canary/docs/01-app/02-guides/json-ld.mdx
import { notFound } from 'next/navigation';
import { compileMDX } from 'next-mdx-remote/rsc';
import { getAllArticles, getArticleSource, type ArticleFrontmatter } from '@/lib/journal/articles';
import type { Metadata } from 'next';

export async function generateStaticParams() {
  return getAllArticles().map((a) => ({ slug: a.slug }));
}

export async function generateMetadata({
  params,
}: {
  params: Promise<{ slug: string }>;
}): Promise<Metadata> {
  const { slug } = await params;
  const source = getArticleSource(slug);
  if (!source) return { title: 'Not Found | KitsuBeat Journal' };
  const { frontmatter } = await compileMDX<ArticleFrontmatter>({
    source,
    options: { parseFrontmatter: true },
  });
  const canonicalUrl = `https://kitsubeat.vercel.app/journal/${slug}`;
  return {
    title: `${frontmatter.title} | KitsuBeat Journal`,
    description: frontmatter.summary,
    alternates: { canonical: canonicalUrl },
    openGraph: {
      title: frontmatter.title,
      description: frontmatter.summary,
      url: canonicalUrl,
      images: [{ url: frontmatter.coverImage }],
      type: 'article',
      publishedTime: frontmatter.date,
    },
  };
}

export default async function ArticlePage({
  params,
}: {
  params: Promise<{ slug: string }>;
}) {
  const { slug } = await params;
  const source = getArticleSource(slug);
  if (!source) notFound();

  const { content, frontmatter } = await compileMDX<ArticleFrontmatter>({
    source,
    options: { parseFrontmatter: true },
  });

  const jsonLd = {
    '@context': 'https://schema.org',
    '@type': 'Article',
    headline: frontmatter.title,
    description: frontmatter.summary,
    datePublished: frontmatter.date,
    image: frontmatter.coverImage,
    author: {
      '@type': 'Organization',
      name: frontmatter.author ?? 'KitsuBeat',
    },
    publisher: {
      '@type': 'Organization',
      name: 'KitsuBeat',
      url: 'https://kitsubeat.vercel.app',
    },
  };

  return (
    <article>
      {/* JSON-LD: XSS-safe; replace /</g mitigates script injection */}
      <script
        type="application/ld+json"
        dangerouslySetInnerHTML={{
          __html: JSON.stringify(jsonLd).replace(/</g, '<'),
        }}
      />
      {/* Hero + content below */}
      {content}
    </article>
  );
}
```

### Pattern 3: Sitemap with Journal Routes

**What:** A single `src/app/sitemap.ts` file that Next.js auto-serves at `/sitemap.xml`. Includes static routes plus all journal articles.

```typescript
// Source: Next.js sitemap docs
// https://github.com/vercel/next.js/blob/canary/docs/01-app/03-api-reference/03-file-conventions/01-metadata/sitemap.mdx
import type { MetadataRoute } from 'next';
import { getAllArticles } from '@/lib/journal/articles';

const BASE_URL = 'https://kitsubeat.vercel.app';

export default function sitemap(): MetadataRoute.Sitemap {
  const articles = getAllArticles();
  const articleEntries = articles.map((a) => ({
    url: `${BASE_URL}/journal/${a.slug}`,
    lastModified: new Date(a.date),
    changeFrequency: 'monthly' as const,
    priority: 0.7,
  }));

  return [
    { url: BASE_URL, lastModified: new Date(), changeFrequency: 'daily', priority: 1 },
    { url: `${BASE_URL}/journal`, lastModified: new Date(), changeFrequency: 'weekly', priority: 0.8 },
    ...articleEntries,
  ];
}
```

Note: this file coexists with the existing root layout. It must be placed at `src/app/sitemap.ts` (not inside a subdirectory) to be served at the root `/sitemap.xml`.

### Pattern 4: MDX Frontmatter Format (for Subutai)

**What:** The exact format Subutai must write at the top of every `.mdx` file.

```mdx
---
title: "The Legend Behind Magikarp and Gyarados"
slug: "magikarp-gyarados-legend"
date: "2026-05-15"
coverImage: "/images/journal/magikarp-hero.jpg"
category: "lore"
summary: "How an ancient Chinese legend about a carp climbing a waterfall became the story of the most iconic Pokémon transformation."
tags: ["pokemon", "japanese-culture", "koi", "mythology"]
author: "KitsuBeat"
readingTime: "6 min read"
---

Article body in MDX here...
```

The `slug` field **must match** the filename without extension (e.g., `magikarp-gyarados-legend.mdx`). The content utility assumes this invariant.

### Anti-Patterns to Avoid

- **Using `@next/mdx` with files in `src/content/`:** `@next/mdx` treats `.mdx` files as Next.js pages; content must live inside `src/app/`. The Subutai file-drop workflow requires content to be decoupled from routes. Use `next-mdx-remote/rsc` instead.
- **Calling `compileMDX` in `getAllArticles()`:** compiles full MDX for every article just to build the index. Gray-matter's frontmatter-only parse is 10-20x cheaper for the listing page. Reserve `compileMDX` for the single-article render.
- **Dynamic imports of MDX files as modules:** requires `require()` or dynamic `import()` per file, does not auto-discover new files. The `fs.readdirSync` approach auto-discovers.
- **Using the old `serialize` + `<MDXRemote>` pattern from `next-mdx-remote` (Pages Router API):** that's the pre-RSC API. For App Router, always import from `next-mdx-remote/rsc`, not `next-mdx-remote`.
- **Bare `<img>` for cover images:** the existing codebase uses bare `<img>` in several places (AnimeCard, SongCard, HeroFeatured) with `object-cover`. This is acceptable per established project pattern. `next/image` adds complexity without clear benefit for a content section where cover images are external URLs. Follow the existing `<img>` pattern.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Frontmatter parsing | Custom YAML/regex parser | `gray-matter` | YAML edge cases (multiline, special chars, dates) are non-trivial; gray-matter has 10+ years of battle-testing |
| Reading time | Custom word-count | `reading-time` | Handles CJK character counting, MDX/HTML stripping, punctuation correctly |
| MDX rendering | Custom marked/unified pipeline | `next-mdx-remote/rsc` | Security (XSS), plugin ecosystem, RSC async compatibility |
| Sitemap | Custom XML generation | Next.js `MetadataRoute.Sitemap` | Built in; auto-escapes URLs; no package needed |
| JSON-LD injection | Third-party SEO library | Inline `<script>` pattern from Next.js docs | No dependency needed; Next.js docs show this as the standard pattern |
| OG tags | `next-seo` package | `generateMetadata()` from App Router | `next-seo` is the Pages Router era pattern; `generateMetadata` is App Router native |

**Key insight:** Next.js 15 App Router handles nearly the entire SEO layer natively via `generateMetadata`. No SEO package (react-helmet, next-seo, next-sitemap) is needed. The only npm additions are the MDX pipeline: `next-mdx-remote`, `gray-matter`, `reading-time`.

## Common Pitfalls

### Pitfall 1: `compileMDX` double-call in `generateMetadata` + page render
**What goes wrong:** Both `generateMetadata` and the default page export call `getArticleSource(slug)` + `compileMDX`. The source is read from disk twice and compiled twice on each request (dev) or at build time (production).
**Why it happens:** Next.js calls `generateMetadata` and the page function separately.
**How to avoid:** In production this is build-time cost so it's acceptable. In dev, use `React.cache()` to wrap `compileMDX` or `getArticleSource` so the result is memoized within a single render pass. Alternatively, fetch the source once with `React.cache` and pass it to both.
**Warning signs:** Unusually slow dev page loads on article pages; double filesystem reads in logging.

### Pitfall 2: `params` is a Promise in Next.js 15
**What goes wrong:** Writing `params.slug` instead of `const { slug } = await params` causes a TypeScript error and runtime failure.
**Why it happens:** Next.js 15 changed `params` to be async (Promise) to enable streaming. The existing `songs/[slug]/page.tsx` already uses `await params` — follow that pattern exactly.
**How to avoid:** Always `const { slug } = await params;` in both `generateMetadata` and the page function.
**Warning signs:** `TypeError: Cannot read properties of undefined (reading 'slug')`.

### Pitfall 3: Hardcoded `BASE_URL` in sitemap and canonical
**What goes wrong:** `https://kitsubeat.vercel.app` is hardcoded but the app may be previewed on different Vercel preview URLs. Canonical URLs pointing to the wrong domain hurt SEO on the production domain.
**Why it happens:** No `NEXT_PUBLIC_SITE_URL` env var currently exists in the project.
**How to avoid:** Add `NEXT_PUBLIC_SITE_URL=https://kitsubeat.vercel.app` to `.env.local` and the Vercel project environment variables. Use `process.env.NEXT_PUBLIC_SITE_URL ?? 'https://kitsubeat.vercel.app'` as the fallback. Add this to Vercel environment variables as part of the wave that ships sitemap/canonical.
**Warning signs:** Canonical tag pointing to a Vercel preview URL (*.vercel.app) instead of production domain.

### Pitfall 4: `fs` used in a Client Component
**What goes wrong:** If `articles.ts` is imported into a Client Component (e.g., a component with `"use client"`), the build fails with "Module not found: Can't resolve 'fs'".
**Why it happens:** `fs` is a Node.js module; it does not exist in the browser bundle.
**How to avoid:** Keep `src/lib/journal/articles.ts` as a server-only module. All callers must be Server Components. Add `import 'server-only'` as the first line of `articles.ts` for a hard compile-time error if accidentally imported client-side.
**Warning signs:** Build error mentioning `fs` or `path` modules not found.

### Pitfall 5: `gray-matter` + `next-mdx-remote` version compatibility
**What goes wrong:** next-mdx-remote v6 uses `parseFrontmatter: true` option which uses `vfile-matter` internally. Using both gray-matter AND `parseFrontmatter: true` in `compileMDX` means frontmatter is parsed twice in the article page — harmless but wasteful.
**Why it happens:** The article collection utility uses gray-matter for the index; the article page uses `compileMDX({ options: { parseFrontmatter: true } })` for content + frontmatter together.
**How to avoid:** In the article page, let `compileMDX` handle frontmatter so only one parse happens. The index page uses gray-matter for the lightweight frontmatter-only read. Do not call `compileMDX` in `getAllArticles()`.
**Warning signs:** None — it just wastes a few milliseconds at build time if done wrong.

### Pitfall 6: `generateStaticParams` with zero articles
**What goes wrong:** If `src/content/journal/` is empty (no `.mdx` files), `getAllArticles()` returns `[]`, `generateStaticParams` returns `[]`, and Next.js may warn about an empty static params array. The `/journal` index page renders an empty grid.
**Why it happens:** The directory exists but has no files.
**How to avoid:** Ship at least one article (the Magikarp/Gyarados article is planned as article #1). Add a `no articles yet` empty state to the `/journal` index page for graceful handling.
**Warning signs:** Empty page on `/journal`; Next.js build warning about no static params.

## Existing Patterns to Reuse

The project already has well-established patterns for this type of page. The journal must follow them:

1. **Cover-art-as-background cards with vignette**: `AnimeCard.tsx` and `HeroFeatured.tsx` both implement this exact pattern — `<img>` with `position: absolute; inset: 0; object-cover`, plus a `linear-gradient` vignette overlay with `pointerEvents: none`. Copy this verbatim.

2. **Bottom text on dark overlay**: Same files — white text with `textShadow: '0 2px 4px rgba(0,0,0,0.65)'` for readability. Use inline styles to bypass `kitsubeat-tokens/no-raw-tokens` lint rule (established precedent in PathNode.tsx, HeroFeatured.tsx).

3. **CardLink primitive**: Use `<CardLink variant="flat" size="sm">` from `src/components/ui/Card.tsx` for the article index cards. Sets `group` class for hover scale effect on inner `<img>`.

4. **generateMetadata async params pattern**: `songs/[slug]/page.tsx` uses `const { slug } = await params` — copy exactly.

5. **Suspense + skeleton**: `songs/[slug]/page.tsx` wraps the heavy loader in `<Suspense fallback={...}>`. The journal article page can do the same if compileMDX becomes slow on large articles, though for static generation it is a build-time cost.

6. **Design tokens**: All colors via `var(--color-*)`, radii via `var(--radius-*)`. Inline `style={}` for `color: "white"` and gradient stops (not Tailwind classes) — this is the established bypass for the lint rule.

### Known Threat Patterns for MDX/Content Stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| XSS via JSON-LD injection | Tampering | `JSON.stringify(jsonLd).replace(/</g, '<')` — official Next.js pattern [VERIFIED: Next.js JSON-LD docs] |
| MDX arbitrary JSX execution | Tampering | `next-mdx-remote/rsc` with `blockJS: false` (default in RSC mode blocks raw JS execution) — content from Subutai only, not user-submitted |
| Open redirect via coverImage URL | Spoofing | coverImage used as `<img src>`, not as a redirect — no risk |
| Slug path traversal (e.g. `../../etc/passwd`) | Information Disclosure | `path.join(CONTENT_DIR, `${slug}.mdx`)` — slug comes from `generateStaticParams` which reads from the controlled `src/content/journal/` directory at build time; not from user input at runtime. At runtime, `getArticleSource(slug)` where slug is a URL param — validate that slug matches `[a-z0-9-]+` pattern before filesystem access |

**Critical note on slug validation:** At runtime in `getArticleSource(slug)`, the slug comes from the URL. Add a slug sanitization guard: `if (!/^[a-z0-9-]+$/.test(slug)) return null;` before the `path.join` call. This prevents any path traversal attempt.
