## Summary

The journal pipeline is well-structured: the slug guard in `articles.ts` correctly blocks path traversal, the Next.js 15 async-params pattern is applied correctly in `[slug]/page.tsx`, and the JSON-LD XSS mitigation (`replace(/</g, '\\u003c')`) is in place. Tests cover the key paths including the traversal guard.

There is one critical issue: `coverImage.startsWith('/')` is called without a null guard in two places in `[slug]/page.tsx`, and this will throw a `TypeError` at runtime if any MDX file ships without a `coverImage` field — crashing both `generateMetadata` and the page render. There are four warnings covering a silent reading-time fallback, a timezone date-display bug, unsafe sort behavior on malformed dates, and a copy-paste duplication of category constants that will silently diverge.

## Critical Issues

### CR-01: `coverImage.startsWith()` called without null guard — runtime crash on missing field

**File:** `src/app/journal/[slug]/page.tsx:47` and `:89`

**Issue:** `frontmatter.coverImage.startsWith('/')` is called twice without checking whether `coverImage` is defined. The `ArticleFrontmatter` type marks `coverImage` as required, but `compileMDX` returns frontmatter typed as `ArticleFrontmatter` via a generic — there is no runtime schema validation. Any MDX file that ships with a missing or misnamed `coverImage` field will produce `undefined` here, throwing `TypeError: Cannot read properties of undefined (reading 'startsWith')`. This crashes both `generateMetadata` (returning an empty Metadata object and breaking OG images silently) and the page render (unhandled Next.js 500).

**Fix:**
```typescript
// In generateMetadata (line ~47)
const ogImage = frontmatter.coverImage
  ? frontmatter.coverImage.startsWith('/')
    ? `${BASE_URL}${frontmatter.coverImage}`
    : frontmatter.coverImage
  : undefined;

return {
  // ...
  openGraph: {
    // ...
    images: ogImage ? [{ url: ogImage }] : [],
    // ...
  },
};

// In ArticlePage (line ~89)
const jsonLdImage = frontmatter.coverImage
  ? frontmatter.coverImage.startsWith('/')
    ? `${BASE_URL}${frontmatter.coverImage}`
    : frontmatter.coverImage
  : BASE_URL; // fall back to site root or a default OG image
```

## Warnings

### WR-01: Article page silently shows wrong reading time for content-computed articles

**File:** `src/app/journal/[slug]/page.tsx:79`

**Issue:** `readingTimeComputed` is set to `frontmatter.readingTime ?? '5 min read'`. When an article has no `readingTime` frontmatter field the fallback is the hardcoded string `'5 min read'`, regardless of actual content length. `getAllArticles()` correctly calls the `reading-time` library to compute this; the article page does not. An article could be 1 min or 15 mins long and will always show "5 min read" in the hero.

**Fix:** Import and call `readingTime` on the raw MDX content (available as the `source` variable that is already in scope):
```typescript
import readingTime from 'reading-time';
import matter from 'gray-matter';

// After getting source (line 66), before building articleMeta:
const { content: rawContent } = matter(source);
const articleMeta: ArticleMeta = {
  ...frontmatter,
  readingTimeComputed: frontmatter.readingTime ?? readingTime(rawContent).text,
};
```
`gray-matter` and `reading-time` are already in `package.json` dependencies.

### WR-02: Date displayed one day early in timezones behind UTC

**File:** `src/app/journal/components/ArticleHero.tsx:64`

**Issue:** `new Date(article.date)` where `article.date` is a bare ISO date string such as `"2026-05-15"`. The ECMAScript spec (and MDN) specify that bare date-only strings (no time component, no `Z`) are parsed as UTC midnight. When `toLocaleDateString` is then called on that value by a user in UTC-1 through UTC-12, the resulting local time is the previous calendar day, so "15 May 2026" renders as "14 May 2026". This is a known, silent bug.

**Fix:** Append `T00:00:00` to force local-time parsing, or use explicit UTC formatting:
```typescript
// Option A — force local midnight (avoids the UTC-shift):
new Date(`${article.date}T00:00:00`).toLocaleDateString('en-GB', {
  year: 'numeric', month: 'long', day: 'numeric',
})

// Option B — format as UTC explicitly (keeps intent clear):
new Intl.DateTimeFormat('en-GB', {
  year: 'numeric', month: 'long', day: 'numeric', timeZone: 'UTC',
}).format(new Date(article.date))
```

### WR-03: NaN comparator in sort — undefined behavior on malformed or missing dates

**File:** `src/lib/journal/articles.ts:40`

**Issue:** `new Date(b.date).getTime() - new Date(a.date).getTime()`. If any MDX file has a missing or unparseable `date` field (e.g., `undefined`, `"TBD"`, or a typo), `getTime()` returns `NaN` and the comparator returns `NaN`. JavaScript's `Array.sort` with a `NaN` comparator has implementation-defined behavior — V8 currently treats it as 0 (stable, leaves order unchanged) but this is not specified and results in silently garbled sort output rather than a clear error.

**Fix:** Guard against `NaN` in the comparator:
```typescript
.sort((a, b) => {
  const ta = new Date(a.date).getTime();
  const tb = new Date(b.date).getTime();
  // Push articles with invalid dates to the end
  if (isNaN(ta) && isNaN(tb)) return 0;
  if (isNaN(ta)) return 1;
  if (isNaN(tb)) return -1;
  return tb - ta;
})
```

### WR-04: `CATEGORY_LABELS` and `CATEGORY_COLORS` duplicated across two components

**File:** `src/app/journal/components/JournalCard.tsx:4-15` and `src/app/journal/components/ArticleHero.tsx:4-15`

**Issue:** The two `Record<string, string>` constants are copy-pasted verbatim in both components. If a new category is added to `ArticleCategory` in `articles.ts`, both files must be updated independently — a missed update will silently render a different color or fall back to the grey default in one surface but not the other. This is a maintenance trap, not just style.

**Fix:** Extract to a shared module consumed by both components:
```typescript
// src/app/journal/utils/categoryDisplay.ts
import type { ArticleCategory } from '@/lib/journal/articles';

export const CATEGORY_LABELS: Record<ArticleCategory, string> = {
  lore: 'Lore',
  language: 'Language',
  translation: 'Translation',
};

export const CATEGORY_COLORS: Record<ArticleCategory, string> = {
  lore: 'rgba(220,38,38,0.85)',
  language: 'rgba(37,99,235,0.85)',
  translation: 'rgba(22,163,74,0.85)',
};
```
Using `Record<ArticleCategory, string>` (keyed on the union type) makes TypeScript emit a compile error whenever `ArticleCategory` gains a new member that is not covered.

## Info

### IN-01: `getAllArticles()` does not validate required frontmatter fields at runtime

**File:** `src/lib/journal/articles.ts:35-38`

**Issue:** `data` is cast directly as `ArticleFrontmatter` via `...(data as ArticleFrontmatter)`. Required fields (`title`, `slug`, `date`, `coverImage`, `category`, `summary`) are not checked. An MDX file with a missing field will produce `undefined` values that flow silently into the UI — `article.title` renders as nothing, `article.slug` produces broken links, and (as noted in CR-01) `article.coverImage.startsWith` crashes downstream. The `readingTimeComputed` field is also not cross-validated.

**Suggestion:** Add a lightweight guard before returning each article, or use `zod` (already in `package.json`) to parse the frontmatter and filter/log invalid entries rather than crashing:
```typescript
import { z } from 'zod';

const FrontmatterSchema = z.object({
  title: z.string(),
  slug: z.string().regex(/^[a-z0-9-]+$/),
  date: z.string().regex(/^\d{4}-\d{2}-\d{2}$/),
  coverImage: z.string(),
  category: z.enum(['lore', 'language', 'translation']),
  summary: z.string(),
  tags: z.array(z.string()).optional(),
  author: z.string().optional(),
  readingTime: z.string().optional(),
});

// In getAllArticles map():
const parsed = FrontmatterSchema.safeParse(data);
if (!parsed.success) {
  console.warn(`[journal] Invalid frontmatter in ${filename}:`, parsed.error.flatten());
  return null;
}
// filter(Boolean) after map
```
