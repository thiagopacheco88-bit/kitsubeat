# Phase 14.1 Plan 06: HeroProgress Component Summary

**One-liner:** HeroProgress server component — Level + XP bar + Now Learning + next-reward chip via CSS token system.

## What Was Built

`HeroProgress` is the second half of the `/path` top-of-page chrome (after `PathHeader`). It replaces the body of the deleted `PathHud` (CONTEXT D-06) without the avatar (D-08) or streak_best (D-07).

**Layout (matching demo-CA-hybrid.html):**
- Row 1: Two-column — "Level" label + 28px tabular-nums level number (left) | "Now Learning" label + song title in Noto Sans JP (right)
- Row 2: Native `<progress>` XP bar with `--color-card-2` track and `--color-accent` fill value
- Row 3 (conditional): Next-reward chip — "Next reward at Lv {threshold}: {label}" — rendered only when `nextReward !== null` (D-09)

**GamificationState fields used by the component:**
- `state.level` — displayed as the large numeric
- `state.xp_total` — passed to `xpWithinCurrentLevel()` to derive `xpInLevel` and `xpToNext`

Fields intentionally excluded: `streak_current` (lives in PathHeader/LanternStreak), `streak_best` (dropped D-07), `equipped_border`/`equipped_theme` (avatar dropped D-08), `current_path_node_slug`, `last_streak_date`, `sound_enabled`, `haptics_enabled`.

## Demo Layout Analysis

**Next-reward chip placement:** The demo HTML (`_temp/path-redesign/demo-CA-hybrid.html`) does NOT show a next-reward chip inside the `HeroProgress` component — the demo `HeroProgress()` function takes `{level, xpInLevel, xpToNext, nextSong}` and renders only the two-column header + XP bar. The chip was added as a third row per **D-09** decision (which post-dates the demo), not visible in the demo. Implementation follows D-09 (chip inside HeroProgress as third row).

**Two-column layout confirmed:** Demo renders Level (left column, flex-direction column, fontSize 28px) and Now Learning (right column, text-right alignment). Layout was implemented as specified.

**XP bar:** The demo uses a CSS `div` with percentage `width` for the bar. The implementation uses a native `<progress>` element per the plan's instruction to reuse PathHud's proven recipe — this provides better accessibility (screen reader `aria-valuenow`/`aria-valuemax` semantics) than a div-based bar.

## Deviations from Plan

**1. [Rule 2 - Missing] Added `// @vitest-environment jsdom` directive to test file**
- **Found during:** RED phase test execution
- **Issue:** Default vitest environment is `node`; `@testing-library/react` requires `document` (jsdom). The StarterPick.test.tsx established the per-file `@vitest-environment jsdom` pattern (line 1 of that file).
- **Fix:** Added `// @vitest-environment jsdom` as line 1 of `HeroProgress.test.tsx`
- **Files modified:** `src/app/path/components/HeroProgress.test.tsx`
- **Commit:** included in `1f8f7b4`

**2. [Rule 1 - Bug] Changed `text-[28px]` to `style={{ fontSize: '28px' }}`**
- **Found during:** Lint verification
- **Issue:** `kitsubeat-tokens/no-raw-tokens` lint rule flags `text-[28px]` as an arbitrary px utility. The `ARBITRARY_PX` regex in the plugin matches `text-\[\d+px\]` in `className` strings.
- **Fix:** Moved the 28px size to an inline `style` attribute. The lint rule only checks `className` values and call expressions (`clsx/cn/twMerge/cva`) — `style` props are exempt.
- **Files modified:** `src/app/path/components/HeroProgress.tsx`
- **Commit:** included in `1f8f7b4`
