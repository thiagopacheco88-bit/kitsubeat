# Phase 11.6 Plan 10: Dual-Card /Review Queue + Shared Daily Cap Summary

**One-liner:** Extended /review queue-builder and recordReviewAnswer to surface both romaji_meaning and kanji_kana cards with shared daily new-card cap (SPEC R17).

## What Was Built

### recordReviewAnswer signature change

Added optional `cardKind` parameter (Zod-validated, defaults to `"romaji_meaning"` for backward compat):

```typescript
export async function recordReviewAnswer(input: {
  // ...existing fields...
  cardKind?: "romaji_meaning" | "kanji_kana"; // NEW
}) {
  const cardKind = CardKindSchema.parse(input.cardKind ?? "romaji_meaning"); // Zod validated
  // SPEC R17: review_new_today increments ONCE per isNew=true regardless of cardKind
  // ...existing budget gate...
  return recordVocabAnswer({ ..., cardKind }); // NEW passthrough
}
```

### Test transition

`tests/integration/review-queue-dual-cards.test.ts` was created as RED in Task 1, then updated to GREEN in Task 2 (ts-expect-error directives and unsafe casts removed after implementation landed). 4 tests cover:

1. Queue emits both card_kinds for same vocab (getDueReviewQueue → buildReviewQueue)
2. Daily cap shared across kinds (review_new_today = 5, not 10, after 5 calls alternating kinds)
3. recordReviewAnswer routes cardKind to recordVocabAnswer (mastery row has correct card_kind)
4. kanji_kana DueCardInput forces vocab_typed exerciseType in buildReviewQueue

Tests are skipped without TEST_DATABASE_URL (integration DB gate). TypeScript clean — tsc --noEmit exits 0.

### Daily-cap shared semantics confirmed

SPEC R17: `review_new_today` is incremented exactly once per `isNew=true` call to `recordReviewAnswer`, regardless of `cardKind`. The budget check in `consumeNewCardBudget` runs before `recordVocabAnswer` is called — introducing both card kinds for the same vocab burns 2 daily slots as designed.
