## Implementation Decisions

### Schema & Data Layer

- **D-01: `user_vocab_mastery` migration via DELETE + ALTER (migration 0017 — number drifted)**
  - DELETE all existing rows in same transaction; ALTER TABLE adds `card_kind` enum NOT NULL (values: `romaji_meaning`, `kanji_kana`); drop existing single-column PK on (user_id, vocab_item_id); add new composite PK (user_id, vocab_item_id, card_kind).
  - **Migration number:** SPEC originally referenced "0016" and CONTEXT originally said "0015"; both are now taken (0015 = `0015_admin_lyrics_editor.sql` from Phase 11.5; 0016 = `0016_user_theme_preference.sql` from Phase 14). Actual number lands at the next free slot at execution time — currently **0017** but planner reconfirms by listing `drizzle/`.
  - Drizzle generates the SQL from schema diff; manual edit ensures the DELETE runs first to avoid PK collision during ALTER.
  - Existing FK constraints (vocab_item_id → vocabulary_items, user_id → users) preserved.
  - **Why**: Cleaner audit trail than DROP+CREATE; preserves indexes and FK definitions; matches drizzle's incremental migration model.

- **D-02: `user_verse_domination` as an explicit table**
  - Schema: `(user_id text, song_version_id uuid, verse_number int, dominated_at timestamp default now())` with composite PK on the three identity columns.
  - Row inserted by `recordVocabAnswer` action at the moment the tipping correct answer lands (the answer that makes "every applicable item in this verse correct ≥1 time" true).
  - Lyrics view reads this table via a single keyed query per page load.
  - **Why**: The animation trigger needs to know exactly which verse just tipped; an explicit row write at that moment beats a derived recomputation. Derived would require N joins per page render.

- **D-03: Denormalize per-track progress into `user_song_progress`**
  - Add four columns: `vocab_track_pct numeric(5,2)`, `grammar_track_pct numeric(5,2)`, `kanji_track_pct numeric(5,2)`, `advanced_drills_unlocked_at timestamp` (null until all three ≥80).
  - `recordVocabAnswer` recomputes the three pct values inside the same transaction after writing the FSRS card; if all three cross the 80 threshold and `advanced_drills_unlocked_at` is null, set it to `now()`.
  - Three-ring UI reads from `user_song_progress` directly — no per-track correlated subqueries on the song page.
  - **Why**: Three rings render on every song page visit (high read volume); writes happen only during exercises. Pattern matches existing `user_song_progress` usage from Plan 10-07.

- **D-04: All-kana song detection — query, not column**
  - At ExerciseTab render time, run a one-shot query `SELECT count(*) FROM vocabulary_items vi WHERE vi.id IN (SELECT vocab_item_id FROM song_vocab WHERE song_version_id = ?) AND vi.surface ~ '[一-龯]'` (kanji unicode block).
  - If count = 0 → hide Kanji card, kanji ring auto-passes, kanji_kana FSRS cards never created for this song.
  - No new schema column — recomputed each render. Fast at the small song-vocab scale (~15-30 items per song).
  - **Why**: Adding a denormalized `has_kanji` flag couples song setup to vocab content; live query is cheap and stays in sync if vocab is edited.

### Image Source & Hosting (post-2026-05-02 pivot — supersedes prior D-05..D-11 ComfyUI cluster)

> **SPEC pivot 2026-05-02:** The original ComfyUI direction (D-05..D-11) is **superseded**. Plan 11.6-02 (commits ff30935 + 1e32e42) is to be reverted. New direction: extend the existing Phase 11.4 seed-19 Unsplash CC0 pipeline to cover the full imageable catalog via the free Unsplash API. See SPEC.md R8/R9 and Discussion Log Round 4 for the source decision.

- **D-05: Image source = Unsplash API auto-search (free demo tier, overnight unattended)**
  - New seed script (working name `scripts/seed/19c-fetch-vocab-images.ts`; planner reconfirms integer slot) issues `GET https://api.unsplash.com/search/photos?query={meaning_en}+{pos_hint}&orientation=squarish&per_page=1` per imageable row, picks the top result's `urls.regular` (1080px, sufficient for LearnCard 220px + FeedbackPanel 120px), and writes the URL into `vocabulary_items.image_url`.
  - Auth: `UNSPLASH_ACCESS_KEY` env var sourced from a free Unsplash Developer app registration (no credit card, no payment). `.env.example` documents the var.
  - Idempotent: `WHERE image_url IS NULL AND part_of_speech IN (...)` (per D-06) — re-runs skip populated rows.
  - Dedup: in-process Map keyed by `meaning_en` so multiple Japanese vocab sharing an English meaning reuse the same image (saves API budget and gives consistent visual associations).
  - **Why**: Aligns with the "no paid API credits" project preference (Unsplash API is free); preserves the inherited Phase 11.4 CC0 licensing assumption; eliminates GPU/local-model dependency entirely; output URLs match the existing 11.4 `URL_PATTERN` regex with no schema or rendering changes.

- **D-06: Image search query = `${meaning_en} (${pos_hint})` — reuses seed-19's existing builder**
  - Per-row query template (matches `scripts/seed/19-curate-vocab-images.ts:85-92`): `"action"` hint for verbs, `"object"` for nouns/adjectives.
  - Example: 飲む (drink, verb) → query `"drink (action)"`; 美しい (beautiful, i_adjective) → `"beautiful (object)"`.
  - **Why**: This builder is already proven by hand-curators on the 50-row set; disambiguates verb senses from noun senses ("drink" the action vs the beverage); avoids sending Japanese tokens to an English-tuned search index.

- **D-07: POS allowlist = noun + verb + i_adjective + na_adjective (imageable POS)**
  - SQL filter: `WHERE part_of_speech IN ('noun', 'verb', 'i_adjective', 'na_adjective') AND image_url IS NULL`.
  - Non-imageable POS (particles, conjunctions, copula, expressions, adverbs, interjections) stay `image_url IS NULL` by design.
  - **Why**: Adjectives are concrete enough to image ("big", "beautiful", "quiet"); adverbs and interjections are mostly abstract and would produce garbage Unsplash matches that pollute the visual experience; particles and conjunctions trivially have no image.

- **D-08: Imageless fallback = silent hide (Phase 11.4 pattern, reused verbatim)**
  - LearnCard and FeedbackPanel render `<img src={image_url} loading="lazy" onError=hide-self />` only when `image_url` is truthy (the existing 11.4 contract).
  - For non-imageable POS, the `<img>` element never renders; card layout collapses to text-only naturally.
  - No new code paths, no POS-typed placeholder icons, no romaji-mega variant — strictly inherit the 11.4 rendering contract.
  - **Why**: Zero new rendering surface to test; the 11.4 silent-hide pattern already handles the truthiness branch and broken-URL branch identically; non-imageable POS being text-only is a feature, not a defect (particles never had a sensible visual representation).

- **D-09: Rate-limit strategy = demo tier overnight + sleep-on-429**
  - Demo tier: 50 requests/hour. Catalog estimate: ~1,000-1,100 imageable rows after D-07 filter; expected runtime ~22-28 hours unattended.
  - On HTTP 429, sleep until the `X-Ratelimit-Reset` header timestamp, then resume.
  - Per-row commit (no transaction wrapper) — matches `scripts/seed/19b-load-vocab-images.ts` precedent so partial progress survives Ctrl-C / crash / power loss.
  - Submit for production tier (5,000/hr, ~30 min runtime) is **not** required up front — operator can apply during the overnight run if they want a faster second pass for any failed rows.
  - **Why**: Zero approval friction (just register an Unsplash app); aligns with the project's "ship without gating on third-party approvals" pattern from prior phases; per-row commit means a 22-hour run that crashes at hour 18 keeps 18 hours of progress.

- **D-10: SPEC R8 acceptance check restricted to imageable POS**
  - Original SPEC acceptance: `SELECT count(*) FROM vocabulary_items WHERE image_url IS NULL` returns 0. **Updated:** restrict to imageable POS — `SELECT count(*) FROM vocabulary_items WHERE part_of_speech IN ('noun','verb','i_adjective','na_adjective') AND image_url IS NULL` returns 0.
  - Non-imageable rows staying NULL is the contract, not a bug.
  - SPEC.md R8 acceptance line will be patched in the next SPEC revision (or noted in the planner's amendment log) to reflect this.
  - **Why**: Counting all rows would never reach 0 because particles/conjunctions/etc. have no image; the planner needs an honest acceptance check that mirrors the actual scope.

- **D-11: Plan 11.6-02 revert = full clean (script + workflow + .gitignore + npm script + env vars)**
  - Delete: `scripts/seed/20-comfyui-batch-images.ts`
  - Delete: `scripts/seed/comfyui-workflows/` (entire directory, including `mnemonic-flat.json`)
  - Remove: `public/vocab-images/` line from `.gitignore`
  - Remove: `gen-image` script entry from `package.json`
  - Remove: `COMFYUI_URL` and `COMFYUI_OUTPUT_DIR` lines from `.env.example`

  - **Why**: Leaves zero ComfyUI traces in tracked config; `npm run gen-image` would otherwise reference a deleted file; `.env.example` documentation drift is a real onboarding hazard.

### Three-Ring UI

- **D-12: Three-ring layout = side-by-side, ~64px each, labeled**
  - Component renders three SVG circles in a horizontal flex row above the Advanced Drills card.
  - Each ring: 64px diameter, 8px stroke, gray track + gold fill where fill arc length = `progress_pct/100 × full_circle`.
  - Labels: "Vocab" / "Grammar" / "Kanji" rendered in `text-xs text-muted-foreground` directly under each ring.
  - States: ring < 80% → gray fill; ring ≥ 80% → gold fill + faint glow; all three ≥ 80% → Advanced Drills button colorizes from gray to active gold.
  - **Why**: Side-by-side rings are instantly legible; concentric rings get visually noisy near the 80% threshold; bars feel utilitarian. Locks the user's mental model literally ("you need all three").

- **D-13: Advanced Drills button affordance**
  - Locked state: muted gray background, gray text, disabled cursor; tooltip on hover lists missing %s ("Vocab: 78%, need 80%").
  - Unlocked state: gold gradient background, white text, active cursor.
  - Transition: 300ms color ease when the third ring closes.
  - **Why**: Tooltip-on-hover keeps the locked-state explainable without taking persistent screen space; the gold-on-unlock matches the verse star color convention (D-14) for consistency.

### Scheduler Algorithm

- **D-17: Pre-compute full session sequence at session start**
  - `buildSessionSequence({trackKind, songVersionId, lengthMode, userPrefs}) → Question[]` runs once when `Session.start()` is invoked.
  - Constraints applied in order: (1) compute eligible pool (per-track items in song, due reviews, capped new), (2) run lag-test placement solver to satisfy intro→test gap ≥3, (3) sort within constraint-allowed buckets by JLPT, (4) interleave new + review by D-19.
  - Output array persisted to `useExerciseSession.items` (existing zustand slice); session resume from refresh re-reads the array unchanged.
  - **Why**: Stable order; deterministic (Vitest can assert intro→test gap on the array directly); resume-friendly; constraint solver is small (≤30 items per session).

- **D-18: Lag-test strict, JLPT best-effort**
  - Lag constraint (intro→test gap ≥3) is an invariant. The constraint solver places intros/tests first respecting gap ≥3; any reordering happens within the constraint envelope.
  - JLPT order is applied as a sort within each constraint bucket. If satisfying lag forces an N4 word before an N5 word, that's accepted as a best-effort tradeoff.
  - **Why**: Lag-test enforces a learning-correctness invariant ("don't quiz on what you just saw"). JLPT is a UX preference. Constraints leave enough slack to mostly satisfy JLPT.

- **D-19: Adaptive interleave — due reviews first, fill with capped new**
  - Order of operations in `buildSessionSequence`:
    1. Pull all due-for-review items in this track (queried against `user_vocab_mastery WHERE due <= now() AND card_kind = <track_card_kind>`)
    2. Pull new candidates capped by Phase 8.4's `users.new_card_cap` (default 10, premium-raisable)
    3. Compose: total = due_reviews + new (clamped to D-20 length)
    4. Shuffle within lag/JLPT constraints
  - When due_reviews alone exceed the length cap, no new intros happen — session is pure review (this is the right behavior; user is deep into FSRS with this track).
  - **Why**: Anki/FSRS philosophy — overdue cards matter more than new. Phase 11's /review queue already implements "all due + capped new"; this stays consistent.

- **D-20: Session length = Short 10 / Long 25, uniform across tracks**
  - Short mode: target 10 questions per session.
  - Long mode: target 25 questions per session.
  - Edge case: when the eligible pool (due + capped new) is smaller than the target, session emits all available items and ends. The Long toggle is a cap, not a target.
  - **Why**: Consistency lets users develop expectation ("Short is always 10"); aligns with Phase 9 kana's 20-question fixed cadence; small grammar pools don't pad with noise.
