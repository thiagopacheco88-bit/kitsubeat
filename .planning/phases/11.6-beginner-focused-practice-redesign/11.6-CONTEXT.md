## Implementation Decisions

### Schema & Data Layer

- **D-01: `user_vocab_mastery` migration via DELETE + ALTER (migration 0015)**
  - DELETE all existing rows in same transaction; ALTER TABLE adds `card_kind` enum NOT NULL (values: `romaji_meaning`, `kanji_kana`); drop existing single-column PK on (user_id, vocab_item_id); add new composite PK (user_id, vocab_item_id, card_kind).
  - Drizzle generates 0015 from schema diff; manual edit ensures the DELETE runs first to avoid PK collision during ALTER.
  - Existing FK constraints (vocab_item_id → vocabulary_items, user_id → users) preserved.
  - **Why**: Cleaner audit trail than DROP+CREATE; preserves indexes and FK definitions; matches drizzle's incremental migration model.

- **D-02: `user_verse_domination` as an explicit table**
  - Schema: `(user_id text, song_version_id uuid, verse_number int, dominated_at timestamp default now())` with composite PK on the three identity columns.
  - Row inserted by `recordVocabAnswer` action at the moment the tipping correct answer lands (the answer that makes "every applicable item in this verse correct ≥1 time" true).
  - Lyrics view reads this table via a single keyed query per page load.
  - **Why**: The animation trigger needs to know exactly which verse just tipped; an explicit row write at that moment beats a derived recomputation. Derived would require N joins per page render.

- **D-03: Denormalize per-track progress into `user_song_progress`**
  - Add four columns: `vocab_track_pct numeric(5,2)`, `grammar_track_pct numeric(5,2)`, `kanji_track_pct numeric(5,2)`, `advanced_drills_unlocked_at timestamp` (null until all three ≥80).
  - `recordVocabAnswer` recomputes the three pct values inside the same transaction after writing the FSRS card; if all three cross the 80 threshold and `advanced_drills_unlocked_at` is null, set it to `now()`.
  - Three-ring UI reads from `user_song_progress` directly — no per-track correlated subqueries on the song page.
  - **Why**: Three rings render on every song page visit (high read volume); writes happen only during exercises. Pattern matches existing `user_song_progress` usage from Plan 10-07.

- **D-04: All-kana song detection — query, not column**
  - At ExerciseTab render time, run a one-shot query `SELECT count(*) FROM vocabulary_items vi WHERE vi.id IN (SELECT vocab_item_id FROM song_vocab WHERE song_version_id = ?) AND vi.surface ~ '[一-龯]'` (kanji unicode block).
  - If count = 0 → hide Kanji card, kanji ring auto-passes, kanji_kana FSRS cards never created for this song.
  - No new schema column — recomputed each render. Fast at the small song-vocab scale (~15-30 items per song).
  - **Why**: Adding a denormalized `has_kanji` flag couples song setup to vocab content; live query is cheap and stays in sync if vocab is edited.

### ComfyUI Batch & Image Style

- **D-05: Model = SDXL-Lightning (4-step)**
  - Checkpoint: `sdxl_lightning_4step.safetensors` (~6.5GB).
  - VRAM target: 6-8GB usable (mid-range GPU).
  - Steps: 4. CFG: 1.0. Sampler: Euler. Resolution: 1024×1024 (downsampled to 512×512 PNG for storage).
  - **GPU detection**: User's GPU spec unknown at decision time. Batch script must probe VRAM at startup (e.g. `nvidia-smi` query) and:
    1. If ≥8GB → run SDXL-Lightning batch
    2. If 4-7GB → fall back to SD 1.5 Turbo (`sd_turbo.safetensors`, ~4GB checkpoint, 1-step, ~1-2s/image)
    3. If <4GB or no NVIDIA GPU detected → fail with actionable error message ("Local image gen needs ≥4GB VRAM. Skip batch with `--use-pollinations` to fall back to free public API.")
  - **Why**: Sweet spot for mnemonic illustration quality vs batch runtime (~90 min for 1,409 images on mid GPU). Probe-or-fallback prevents OOM mid-batch.

- **D-06: Visual style = flat 2D illustration**
  - Locked style modifiers in the prompt template: `"flat illustration, vector style, white background, no text, simple composition, clean lines, soft pastel colors"`.
  - Negative prompt: `"text, words, letters, photorealistic, anime, manga, dark background, complex composition"`.
  - **Why**: Flat illustration is recognizable at LearnCard 220px and FeedbackPanel 120px; consistent across noun/verb/abstract; works on white background matching the existing app palette; avoids AI-uncanny-valley faces.

- **D-07: Prompt template = `meaning + part_of_speech`**
  - Template: `"flat illustration of: {meaning_en} ({part_of_speech}), white background, no text, simple composition, clean lines, soft pastel colors"`.
  - Example for 飲む (drink, verb): `"flat illustration of: drink (verb), white background, no text, simple composition, clean lines, soft pastel colors"`.
  - **Why**: POS distinguishes "drink" the action from "drink" the noun. JLPT level isn't visual context. Including the Japanese surface causes text-in-image artifacts.

- **D-08: Image storage = `public/vocab-images/<vocab_uuid>.png` (gitignored)**
  - Filename pattern uses the vocab_item_id UUID for stable URL referencing from `vocabulary_items.image_url`.
  - Add `public/vocab-images/` to `.gitignore`. The batch script is the source of truth (re-runnable).
  - URL pattern in DB: `/vocab-images/<vocab_item_id>.png` (matches existing 11.4 column type `text`).
  - **Why**: Free, no infra dependency, ~140MB total disk impact (~100KB × 1,409). Vercel deploys static assets so the URLs survive deploys after a one-time push of the directory contents to the deployment storage. Falls within R7 (image storage) and R8 (idempotent batch script).

- **D-09: Batch script numbering = `scripts/seed/14-comfyui-batch-images.ts`**
  - Phase 11.4 used 19/19b for the Unsplash curate+load pair (per their D-11). The next-free integer in the seed/ directory at this phase boundary should be re-checked at planning time, but `14-` is a likely candidate slot if the 19/19b naming proves to be the cap. Planner reconfirms the integer.
  - Idempotent flow: query rows where `image_url IS NULL`, drive ComfyUI, write PNG, update row. Re-runs skip populated rows.
  - **Why**: Match existing `scripts/seed/` numeric naming; idempotence is required by SPEC R8 acceptance.

- **D-10: ComfyUI invocation strategy = subprocess to local API**
  - User runs ComfyUI in API mode locally (`python main.py --listen 127.0.0.1`).
  - Batch script POSTs workflow JSON to `http://127.0.0.1:8188/prompt`, polls `/history/<prompt_id>` for completion, reads the output PNG from ComfyUI's output directory, copies to `public/vocab-images/<uuid>.png`.
  - Workflow JSON checked into `scripts/seed/comfyui-workflows/mnemonic-flat.json` so the prompt+model+sampler config is reproducible.
  - **Why**: ComfyUI's API mode is the standard programmatic interface; subprocess avoids embedding a Python runtime in the Node script.

### Regeneration & Operator Workflow

- **D-11: Bad-image regeneration = manual swap + `--regenerate <uuid>` flag**
  - When a generated image is wrong (abstract concept produced something nonsensical), operator deletes the bad PNG file from `public/vocab-images/` and either:
    1. Re-runs the full batch script (which picks up the missing file as needing re-gen), OR
    2. Runs `npm run gen-image -- --regenerate <vocab_item_id>` for one-shot retry.
  - No admin UI for re-rolling. Phase 11.5 Admin Lyrics Editor is not extended.
  - **Why**: Re-runnable script is already SPEC R8's source of truth; a `--regenerate <uuid>` flag is one extra branch in the script. UI scope creep into 11.5 not justified for an operator-only workflow.

### Three-Ring UI

- **D-12: Three-ring layout = side-by-side, ~64px each, labeled**
  - Component renders three SVG circles in a horizontal flex row above the Advanced Drills card.
  - Each ring: 64px diameter, 8px stroke, gray track + gold fill where fill arc length = `progress_pct/100 × full_circle`.
  - Labels: "Vocab" / "Grammar" / "Kanji" rendered in `text-xs text-muted-foreground` directly under each ring.
  - States: ring < 80% → gray fill; ring ≥ 80% → gold fill + faint glow; all three ≥ 80% → Advanced Drills button colorizes from gray to active gold.
  - **Why**: Side-by-side rings are instantly legible; concentric rings get visually noisy near the 80% threshold; bars feel utilitarian. Locks the user's mental model literally ("you need all three").

- **D-13: Advanced Drills button affordance**
  - Locked state: muted gray background, gray text, disabled cursor; tooltip on hover lists missing %s ("Vocab: 78%, need 80%").
  - Unlocked state: gold gradient background, white text, active cursor.
  - Transition: 300ms color ease when the third ring closes.
  - **Why**: Tooltip-on-hover keeps the locked-state explainable without taking persistent screen space; the gold-on-unlock matches the verse star color convention (D-14) for consistency.

### Verse Domination Visuals

- **D-14: Verse star icon = custom inline SVG, gold-fill, 4px-right margin**
  - SVG inline component, 5-point star, gold fill (`#FBBF24` matches Tailwind `amber-400`).
  - Renders at the start of the verse line, left of the verse number, with 4px right margin.
  - Pattern matches BonusBadgeIcon shape from Plan 10-07 (33-line inline SVG sparkle).
  - Conditional: present when `dominated_at IS NOT NULL` for `(user, verse)`, absent otherwise.
  - **Why**: Custom SVG is themable (gold-on-dark / gold-on-light), tiny (~200B), consistent across browsers (emoji ⭐ renders ugly on Windows). Matches existing icon convention.

- **D-15: Domination animation = combination (confetti + glow pulse + text overlay)**
  - Total duration: ~1.5s.
  - `canvas-confetti` particle burst (already in deps from Plan 08-04) emits from the FeedbackPanel center, ~50 particles, gold + amber color palette.
  - Verse text in lyrics view briefly pulses with a CSS keyframe `@keyframes verse-dominated-pulse` — gold tint via `text-shadow` for 800ms, single iteration.
  - Brief text overlay "Verse dominated!" renders at the top of the FeedbackPanel for 1.2s, fades out.
  - Trigger: `recordVocabAnswer` server response includes `versesDominatedNow: number[]`. Client state in `useExerciseSession` reads this on every answer; if non-empty, the FeedbackPanel triggers the three animation effects.
  - **Why**: User explicitly asked for "an animation showing the verse learned" — combination matches the "addictive, entertainment-first" KitsuBeat philosophy. Star pop-in alone (option d) is too small a payoff for the milestone.

- **D-16: Counter = header text + catalog "% dominated" line**
  - Song page header: `⭐ 7/12 verses` rendered next to the song-title row in muted-gold (`text-amber-500`); SVG star precedes the count.
  - Song catalog SongCard: a new line under the existing stars+bonus-badge row reading `42% dominated` in `text-xs text-muted-foreground`.
  - Both pull from `user_song_progress` (D-03 plus a new `verses_dominated_count` derived column or computed from `user_verse_domination` count).
  - **Why**: Header text is sufficient — bar is redundant with per-verse stars in the lyrics view; sticky pill is overkill for static metric. Catalog line creates pre-click signal of progress.

### Scheduler Algorithm

- **D-17: Pre-compute full session sequence at session start**
  - `buildSessionSequence({trackKind, songVersionId, lengthMode, userPrefs}) → Question[]` runs once when `Session.start()` is invoked.
  - Constraints applied in order: (1) compute eligible pool (per-track items in song, due reviews, capped new), (2) run lag-test placement solver to satisfy intro→test gap ≥3, (3) sort within constraint-allowed buckets by JLPT, (4) interleave new + review by D-19.
  - Output array persisted to `useExerciseSession.items` (existing zustand slice); session resume from refresh re-reads the array unchanged.
  - **Why**: Stable order; deterministic (Vitest can assert intro→test gap on the array directly); resume-friendly; constraint solver is small (≤30 items per session).

- **D-18: Lag-test strict, JLPT best-effort**
  - Lag constraint (intro→test gap ≥3) is an invariant. The constraint solver places intros/tests first respecting gap ≥3; any reordering happens within the constraint envelope.
  - JLPT order is applied as a sort within each constraint bucket. If satisfying lag forces an N4 word before an N5 word, that's accepted as a best-effort tradeoff.
  - **Why**: Lag-test enforces a learning-correctness invariant ("don't quiz on what you just saw"). JLPT is a UX preference. Constraints leave enough slack to mostly satisfy JLPT.

- **D-19: Adaptive interleave — due reviews first, fill with capped new**
  - Order of operations in `buildSessionSequence`:
    1. Pull all due-for-review items in this track (queried against `user_vocab_mastery WHERE due <= now() AND card_kind = <track_card_kind>`)
    2. Pull new candidates capped by Phase 8.4's `users.new_card_cap` (default 10, premium-raisable)
    3. Compose: total = due_reviews + new (clamped to D-20 length)
    4. Shuffle within lag/JLPT constraints
  - When due_reviews alone exceed the length cap, no new intros happen — session is pure review (this is the right behavior; user is deep into FSRS with this track).
  - **Why**: Anki/FSRS philosophy — overdue cards matter more than new. Phase 11's /review queue already implements "all due + capped new"; this stays consistent.

- **D-20: Session length = Short 10 / Long 25, uniform across tracks**
  - Short mode: target 10 questions per session.
  - Long mode: target 25 questions per session.
  - Edge case: when the eligible pool (due + capped new) is smaller than the target, session emits all available items and ends. The Long toggle is a cap, not a target.
  - **Why**: Consistency lets users develop expectation ("Short is always 10"); aligns with Phase 9 kana's 20-question fixed cadence; small grammar pools don't pad with noise.

- **GPU detection probe in ComfyUI batch (D-05)** — User does not know their GPU spec at decision time. The probe-or-fallback path (`nvidia-smi` query → SDXL-Lightning vs SD 1.5 Turbo vs error) is non-negotiable for D-05 to be safe. - **80% per song unlock is a beginner mental model** — User explicitly chose 80%/answered-correctly-once over stricter FSRS-state-based gates. The unlock should feel reachable in 1-2 sessions per track per song, not days of grinding.
