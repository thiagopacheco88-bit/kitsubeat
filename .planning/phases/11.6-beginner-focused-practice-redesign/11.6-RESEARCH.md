### Locked Decisions

#### Schema & Data Layer
- **D-01: `user_vocab_mastery` migration via DELETE + ALTER (migration 0015)** — DELETE all existing rows in same transaction; ALTER TABLE adds `card_kind` enum NOT NULL (values: `romaji_meaning`, `kanji_kana`); drop existing single-column PK on (user_id, vocab_item_id); add new composite PK (user_id, vocab_item_id, card_kind). Drizzle generates 0015 from schema diff; manual edit ensures the DELETE runs first to avoid PK collision during ALTER. Existing FK constraints (vocab_item_id → vocabulary_items, user_id → users) preserved. **NOTE (research-flagged):** D-01 says "0015" but `drizzle/0015_admin_lyrics_editor.sql` is already applied. Phase 11.6's migration must be **0016**. Planner must reconfirm at write time.
- **D-02: `user_verse_domination` as an explicit table** — Schema: `(user_id text, song_version_id uuid, verse_number int, dominated_at timestamp default now())` with composite PK on the three identity columns. Row inserted by `recordVocabAnswer` action at the moment the tipping correct answer lands. Lyrics view reads via single keyed query per page load.
- **D-03: Denormalize per-track progress into `user_song_progress`** — Add four columns: `vocab_track_pct numeric(5,2)`, `grammar_track_pct numeric(5,2)`, `kanji_track_pct numeric(5,2)`, `advanced_drills_unlocked_at timestamp` (null until all three ≥80). `recordVocabAnswer` recomputes the three pct values inside the same write path after the FSRS card.
- **D-04: All-kana song detection — query, not column** — At ExerciseTab render time, run a one-shot SELECT count(*) over song_vocab JOIN vocabulary_items WHERE surface ~ '[一-龯]' (kanji unicode block). If count = 0 → hide Kanji card, kanji ring auto-passes. No new schema column.

#### ComfyUI Batch & Image Style
- **D-05: Model = SDXL-Lightning (4-step)** — Checkpoint: `sdxl_lightning_4step.safetensors` (~6.5GB). VRAM target: 6-8GB usable. Steps: 4. CFG: 1.0. Sampler: Euler. Resolution: 1024×1024 (downsampled to 512×512 PNG). GPU detection probe at startup: ≥8GB → SDXL-Lightning; 4-7GB → fallback to SD 1.5 Turbo (`sd_turbo.safetensors`, ~4GB checkpoint, 1-step); <4GB or no NVIDIA GPU → fail with actionable error message.
- **D-06: Visual style = flat 2D illustration** — Locked style modifiers: `"flat illustration, vector style, white background, no text, simple composition, clean lines, soft pastel colors"`. Negative: `"text, words, letters, photorealistic, anime, manga, dark background, complex composition"`.
- **D-07: Prompt template = `meaning + part_of_speech`** — Template: `"flat illustration of: {meaning_en} ({part_of_speech}), white background, no text, simple composition, clean lines, soft pastel colors"`.
- **D-08: Image storage = `public/vocab-images/<vocab_uuid>.png` (gitignored)** — Filename pattern uses the vocab_item_id UUID. URL pattern in DB: `/vocab-images/<vocab_item_id>.png`. Add to `.gitignore`.
- **D-09: Batch script numbering = `scripts/seed/14-comfyui-batch-images.ts`** — CONTEXT flags numbering must be re-checked at planning time. **Research-confirmed: 14 is taken** (`14-seed-reward-slots.ts`, `14-semantic-merge-grammar-rules.ts`); next free integer is **20**. Planner must reconfirm.
- **D-10: ComfyUI invocation strategy = subprocess to local API** — User runs ComfyUI in API mode locally (`python main.py --listen 127.0.0.1`). Batch script POSTs to `http://127.0.0.1:8188/prompt`, polls `/history/<prompt_id>` for completion, reads output PNG, copies to `public/vocab-images/<uuid>.png`. Workflow JSON checked into `scripts/seed/comfyui-workflows/mnemonic-flat.json`.

#### Regeneration & Operator Workflow
- **D-11: Bad-image regeneration = manual swap + `--regenerate <uuid>` flag** — No admin UI for re-rolling. Operator deletes the bad PNG and re-runs the script.

#### Three-Ring UI
- **D-12: Three-ring layout = side-by-side, ~64px each, labeled** — 64px diameter, 8px stroke, gray track + gold fill. Labels in `text-xs text-muted-foreground`. States: <80% gray; ≥80% gold + faint glow; all three ≥80% Advanced Drills button colorizes from gray to active gold.
- **D-13: Advanced Drills button affordance** — Locked: muted gray + tooltip listing missing %. Unlocked: gold gradient. 300ms color ease transition.

#### Verse Domination Visuals
- **D-14: Verse star icon = custom inline SVG, gold-fill (`#FBBF24` = Tailwind `amber-400`), 4px-right margin** — Pattern matches BonusBadgeIcon shape from Plan 10-07. Conditional on `dominated_at IS NOT NULL`.
- **D-15: Domination animation = combination (confetti + glow pulse + text overlay), ~1.5s total** — `canvas-confetti` particle burst (~50 particles, gold + amber palette) + verse text glow pulse via `@keyframes verse-dominated-pulse` (`text-shadow` 800ms, single iteration) + "Verse dominated!" text overlay 1.2s fade. Trigger: `recordVocabAnswer` returns `versesDominatedNow: number[]`.
- **D-16: Counter = header text + catalog "% dominated" line** — Song page header: `⭐ 7/12 verses` in `text-amber-500`. Song catalog SongCard: new line `42% dominated` in `text-xs text-muted-foreground`.

#### Scheduler Algorithm
- **D-17: Pre-compute full session sequence at session start** — `buildSessionSequence({trackKind, songVersionId, lengthMode, userPrefs}) → Question[]` runs once when `Session.start()` is invoked. Constraints applied in order: (1) eligible pool, (2) lag-test placement solver, (3) sort within constraint-allowed buckets by JLPT, (4) interleave new + review.
- **D-18: Lag-test strict, JLPT best-effort** — Lag (intro→test gap ≥3) is invariant. JLPT order is a soft sort within the constraint envelope.
- **D-19: Adaptive interleave — due reviews first, fill with capped new** — Pull all due-for-review items; cap new by `users.new_card_cap` (default 10); compose `due_reviews + new` (clamped to D-20 length); shuffle within lag/JLPT constraints.
- **D-20: Session length = Short 10 / Long 25, uniform across tracks** — Edge case: pool < target → emit all available items.

const COMFYUI_URL = "http://127.0.0.1:8188";

async function generateImage(
  workflowJson: object,
  positivePrompt: string,
  negativePrompt: string,
  outputPath: string

import { execSync } from "child_process";

function probeVramMb(): number | null {
  try {
    // CSV output is more reliable than -q -x XML across nvidia-smi versions.
    // Pick the first GPU's total memory in MiB.
    const stdout = execSync(
      "nvidia-smi --query-gpu=memory.total --format=csv,noheader,nounits",

    return null;

      "or curate manually."

### Pattern 3: Lag-Test Constraint Solver (D-17, D-18, D-19)

**What:** Given a session pool of `{intros: vocab[], reviews: vocab[]}`, produce an ordered Question[] where every intro→test gap ≥3 (strict) and JLPT order is approximately preserved (best-effort).

**When to use:** `buildSessionSequence` runs once at session start.

**Algorithm: Greedy with backtracking** (recommended for pool sizes ≤30):

```typescript
// Source: derived from D-17/D-18/D-19 constraint definitions [DERIVED]
interface SessionItem {
  vocabItemId: string;
  jlptLevel: "N5" | "N4" | "N3" | "N2" | "N1" | null;
  isNew: boolean;          // true → emit LearnCard then test
  introIndex?: number;     // position of LearnCard once placed
  testIndex?: number;      // position of first test once placed
}

const JLPT_RANK: Record<string, number> = { N5: 1, N4: 2, N3: 3, N2: 4, N1: 5 };
const jlptKey = (lvl: string | null): number => lvl ? JLPT_RANK[lvl] : 99;

export function buildSessionSequence(pool: {
  intros: SessionItem[];
  reviews: SessionItem[];
  lengthCap: number;
  minIntroToTestGap: number; // 3 per D-18
}): Question[] {
  // 1. Sort each bucket by JLPT (soft preference)
  const intros = [...pool.intros].sort((a, b) => jlptKey(a.jlptLevel) - jlptKey(b.jlptLevel));
  const reviews = [...pool.reviews].sort((a, b) => jlptKey(a.jlptLevel) - jlptKey(b.jlptLevel));

  // 2. Greedy interleave: place reviews first (D-19 priority), insert intro+test pairs
  //    when the gap budget allows. Backtrack one step if a placement violates lag.
  const sequence: Array<{ kind: "intro" | "test" | "review"; item: SessionItem }> = [];
  const introQueue = [...intros];
  const reviewQueue = [...reviews];
  const pendingTests: Array<{ item: SessionItem; introIdx: number }> = [];

  while (sequence.length < pool.lengthCap && (introQueue.length > 0 || reviewQueue.length > 0 || pendingTests.length > 0)) {
    // Prefer to place a test if its lag is satisfied
    const readyTest = pendingTests.find(p => sequence.length - p.introIdx >= pool.minIntroToTestGap);
    if (readyTest) {
      pendingTests.splice(pendingTests.indexOf(readyTest), 1);
      sequence.push({ kind: "test", item: readyTest.item });
      continue;
    }
    // Else place a review (lag-immune — already learned)
    if (reviewQueue.length > 0) {
      sequence.push({ kind: "review", item: reviewQueue.shift()! });
      continue;
    }
    // Else introduce a new card (creates a pendingTest)
    if (introQueue.length > 0) {
      const item = introQueue.shift()!;
      const introIdx = sequence.length;
      sequence.push({ kind: "intro", item });
      pendingTests.push({ item, introIdx });
      continue;
    }
    // Else: only pendingTests remain but lag not satisfied → emit a filler review
    // (re-pull from already-placed reviews, OR break if no fillers available)
    if (pendingTests.length > 0) {
      // Stall: insert the LEAST recently introduced test ignoring lag (best-effort fallback)
      const fallback = pendingTests.shift()!;
      sequence.push({ kind: "test", item: fallback.item });
      continue;
    }
    break;
  }

  return sequence.map(({ kind, item }) => questionFromItem(item, kind));
}
```

**Complexity:** O(n × m) where n = sequence length, m = pendingTests size (typically ≤5). For pool sizes ≤30, this completes in microseconds. Backtracking is rarely needed because the only failure mode is "all remaining items are pendingTests with unmet lag" — which the fallback path handles deterministically.

## Common Pitfalls

### Pitfall 1: Drizzle journal corruption from running `db:generate`
**What goes wrong:** Drizzle's `_journal.json` does not match the actual applied migrations because Phase 11.4-01 hand-wrote 0014 (popularity_rank drift) and Phase 11.5 hand-wrote 0015. Running `db:generate` regenerates a snapshot that conflicts with the live DB shape.

**Why it happens:** The schema.ts diffs include columns that don't exist in `_journal.json` snapshots; Drizzle thinks they're new even though they already exist live.

**How to avoid:** Hand-write `drizzle/0016_dual_card_mastery.sql` directly. Never run `npm run db:generate` for this phase. Apply via existing `tsx scripts/apply-migrations.ts` (Path A precedent from Phase 11.4-01).

**Warning signs:** A `db:generate` invocation that emits an `0016_*.sql` file with `CREATE TABLE vocabulary_items` (full table re-creation) instead of an ALTER. STOP IMMEDIATELY if that happens — the journal is poisoned.

### Pitfall 2: ComfyUI output directory not on the same filesystem as `public/vocab-images/`
**What goes wrong:** Operator runs ComfyUI from `D:/ComfyUI/` but the kitsubeat repo is on `C:/`. `copyFileSync(src, dst)` fails with EXDEV across drives on some Windows configurations, or the script silently writes to ComfyUI's output dir without copying.

**Why it happens:** The batch script's `COMFYUI_OUTPUT_DIR` env var is operator-configurable; if missed, default `output/` is interpreted relative to the script's CWD (kitsubeat), not ComfyUI's CWD.

**How to avoid:**
- The batch script must FAIL FAST if `COMFYUI_OUTPUT_DIR` is unset and `process.cwd()/output/` does not exist
- Use `fs.copyFileSync` (handles cross-volume on Node 24); fallback to `fs.readFileSync` + `fs.writeFileSync` if EXDEV
- Document `COMFYUI_OUTPUT_DIR` in `.env.example`

**Warning signs:** Generated images for the first 10 vocab items succeed (because they wrote to ComfyUI's actual output dir during dev), then later runs return ENOENT.

### Pitfall 3: Verse-dominated animation re-fires on session resume
**What goes wrong:** User completes the tipping answer, animation fires (R15 acceptance). User refreshes page mid-session. Animation fires again because client state lost.

**Why it happens:** `versesDominatedNow` is set on every `recordVocabAnswer` response; if the client doesn't track which verses already animated this page-load, it re-triggers.

**How to avoid:** The server action MUST return `versesDominatedNow: []` on revisits. Implementation: `INSERT ... ON CONFLICT DO NOTHING RETURNING verse_number` — if the row already existed, RETURNING is empty, so the array is empty. Idempotency at the SQL level, not at the client level.

**Warning signs:** Vitest test for R15 passes the first iteration but reload-and-reanswer also returns `versesDominatedNow: [3]` — that's the bug.

### Pitfall 4: Lag-test solver produces zero-length sequence on small pools
**What goes wrong:** A song with only 2 vocab + 1 grammar items + 0 reviews. `intros=3`, `reviews=0`, `lengthCap=10`. The solver places 3 intros at positions 0/1/2, but each one has a pendingTest needing gap ≥3 — and there's nothing to place between them. The `else { break }` branch fires, returning a sequence of 3 intros + 0 tests.

**Why it happens:** When `reviews=0` and `intros < minGap`, the solver has no fillers to satisfy lag.

**How to avoid:** Detect this case explicitly: if `reviews.length + intros.length < minGap`, fall back to "all intros first, then all tests" with a warning log. Beginner pool sizes legitimately produce this case for under-developed songs.

**Warning signs:** A test session emits questions for only 3 of 6 expected items. Vitest must cover this path — pool with 3 intros + 0 reviews → expect 6 items (3 intros + 3 tests, lag-violated but content-complete).

### Pitfall 5: Vercel deploy of empty `public/vocab-images/`
**What goes wrong:** Local dev passes (images load); production 404s every image URL.

**Why it happens:** Directory is gitignored.

**How to avoid:** See "Vercel deploy gotcha" above. Document the one-time un-ignore + push step. Add a `npm run check:vocab-images` script that asserts `public/vocab-images/` count > 0 and warns if running on Vercel build.

### Pitfall 6: Three-ring UI shows 79.99% as locked
**What goes wrong:** `numeric(5,2)` D-03 column rounds 79.999 to 80.00, but the gate compares with `>= 0.80` and a float-precision error shows the ring as locked when DB says 80.

**Why it happens:** Reading `numeric` from Drizzle returns string in some configurations; `parseFloat("80.00") >= 80` is true, but `parseFloat("79.99") >= 80` is false — and if the recompute logic uses int division (correct/total*100), 80% may land at 79.999... before the column truncates.

**How to avoid:** The recompute should use `ROUND(correct::numeric / total::numeric * 100, 2)` in SQL. UI gate should read `pct >= 80` not `pct >= 80.00` (numeric comparison is correct in JS for integers, but use a constant `THRESHOLD = 80`).

**Warning signs:** Vitest acceptance test "8/10 vocab + 4/5 grammar + 5/6 kanji = unlock" → grammar = 4/5 = 80% exactly → must unlock.

### Pitfall 7: All-kana song detection query runs on every render
**What goes wrong:** D-04 says "computed from `vocab_global` materialized view query, no schema column needed." If implemented naively as a per-render query in ExerciseTab, every navigation hits the DB.

**Why it happens:** D-04 is correct in spirit but the implementation must batch with the existing `/songs/[slug]/page.tsx` SSR query.

**How to avoid:** Compute `hasKanjiBearingVocab: boolean` in the SSR data load (same query that fetches lesson + user_song_progress); pass as prop to ExerciseTab. Component is purely conditional render based on prop.

**Warning signs:** Network tab shows a separate `vocab_global` count query each time the user toggles a tab.

### Pitfall 8: Per-track pct recompute is correlated subquery on every answer
**What goes wrong:** D-03 recompute logic in `recordVocabAnswer` runs `SELECT count(*) FROM user_vocab_mastery WHERE ... AND state >= 1` 3 times (one per track) on every answer write. At ~60 answers per session, that's 180 extra queries per session.

**Why it happens:** Naive denormalization implementation: re-compute from source on each write.

**How to avoid:** Single SQL that computes all three percentages in one round trip — JOIN `user_vocab_mastery` against `song_vocab` filtered by song_version_id, GROUP BY card_kind + filter (kanji-bearing for kanji track), one query returning 3 rows. CTE form is fine.

**Warning signs:** A 60-question session with 60 `recordVocabAnswer` calls shows 180+ `count(*)` queries in the Postgres log.

function TrackProgressRing({ pct, label, size = 64, stroke = 8 }: TrackProgressRingProps) {
  const radius = (size - stroke) / 2;
  const circumference = 2 * Math.PI * radius;
  const offset = circumference * (1 - Math.min(100, Math.max(0, pct)) / 100);

          fill="none" stroke="#1F2937" strokeWidth={stroke}
        />
        <circle
          cx={size / 2} cy={size / 2} r={radius}
          fill="none" stroke={ringColor} strokeWidth={stroke}
          strokeDasharray={circumference}

      </svg>
      <span className="text-xs text-muted-foreground">{label}</span>

}

### Known Threat Patterns for {Next.js + Drizzle + ComfyUI batch} stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| SQL injection on cardKind in `recordVocabAnswer` | Tampering | Use Drizzle's parameterized queries (already the project pattern); enum-validate at server-action boundary before any SQL touch |
| ComfyUI HTTP API exposure on 0.0.0.0 instead of 127.0.0.1 | Information disclosure / Remote code exec | D-10 locks `--listen 127.0.0.1`; document in plan + script warns if `COMFYUI_URL` resolves to non-loopback |
| Vocab image URL injection (image_url column) | Tampering / XSS via SVG | The batch script writes `/vocab-images/<uuid>.png` — UUID is server-generated. The plain `<img>` tag (Phase 11.4 D-06) bypasses SVG entirely. Threat is mitigated by construction. |
| User-typed romaji input echoed in DOM | XSS | React's auto-escaping handles it; no `dangerouslySetInnerHTML` planned for this surface (GrammarWriteCard precedent at line 60 uses it for prompt_jp_furigana but that's server-generated lesson content, not user input) |
| Vercel deploy of un-gitignored vocab images leaking secrets | Information disclosure | Images are deterministic AI-generated illustrations; no secrets embedded. Risk: low. |
| Daily new-card cap bypass via dual cardKind exploit | Bypass / Privilege escalation | `consumeNewCardBudget` is called once per `recordReviewAnswer` regardless of cardKind. Test: introducing both kinds in same session burns 2 slots — confirmed in test-plan above. |
